# Cloudgate

A self-hosted deployment platform: users deploy applications and databases onto their own servers, organized by organization → project → environment.

## Language

**How the _Avoid_ columns are enforced, and how they are not.** They bind what
you write *now* — a new name, a comment you are already editing, a test name.
They are **not** a standing work item: an existing comment using a banned
synonym is fixed when you are in that file for another reason, and a grep
across the tree counting occurrences is **not a finding and not a ticket**.
This is written down because it was one — a ticket once counted 37 uses of "build
server" in `backend/src` and proposed a 24-file sweep of comments, which is a
day of unreviewable diff buying no behaviour and no clarity a reader lacked.
Where an entry says the wrong word would make a *reader draw the wrong
conclusion about which machine or which row is meant*, that is a defect on its
own terms and needs no vocabulary rule to justify filing it. Quoted history is
never a violation (§1.2): a docblock quoting wording an earlier ticket
corrected is the record, not a survival.

**Organization**:
The tenant boundary. Every resource belongs to exactly one organization, and members act within it.
_Avoid_: Team, workspace, tenant

**Instance organization**:
The Organization the instance bootstrapped for its first user, **pinned** once in `instance_organization` and never worked out again (ADR-0077). If the pinned Organization no longer exists, nobody holds its authority; it never passes to another Organization. No path in the app deletes it. Its owners and admins — people, never an **Agent**, even one placed in this Organization — are the only callers who may configure the **platform host**: the singleton Traefik this instance runs for itself, its files, the one forward-auth proxy every organization's gated Domain dials, the one access log that Traefik writes every organization's traffic into, the host's own metrics, its Docker daemon and swarm, the cron jobs and shells that run on it, and the deployment queue every organization's builds wait in. It is an Organization like any other in every other respect; what is instance-level is the authority its owner and admins carry, not the Organization. On a single-organization install it is the only Organization, so the distinction costs nothing and only becomes visible once a second one exists (ADR-0013). On the **Hosted instance** it is Octabyte's, made by a command run on the platform host before the sign-up form opens; it holds only the staff who run the Instance, has no Hosted plan and adds no Servers, and Octabyte's own apps live in an ordinary Organization that pays like any customer.
_Avoid_: Root organization, default organization (`member.isDefault` is a per-user preference and is settable), instance role, super admin

**Project**:
A named grouping of related services inside an organization (e.g. one product). Contains environments, nothing else — and its own `env`, which every Service in every Environment beneath it can reference by name at deploy. Not inherited, and the distinction is the mechanism rather than a wording: `prepareEnvironmentVariables` (`docker/docker.utils.ts`) resolves a Service's own `${{project.KEY}}` references against this row and returns the Service's own keys and nothing else, so a key set here and never named reaches no container at all, and removing one that *was* named throws rather than resolving empty — failing the next deploy of every Service that referenced it (ADR-0014). Entitlement is granted per project: the member row's `accessedProjects` names which ones a caller may reach at all.

*Which* projects a caller may reach and *what* they may do to one are separate questions. There is no `project: ['read']` statement, deliberately: a read is answered by `accessedProjects` alone, and every project-scoped query filters on it. **Rewriting** a Project — its name, its description, the `env` its Services reference, and which Tags it wears — is `project: ['update']`. **Minting** and **retiring** one stay `project: ['create']` and `project: ['delete']`, and `create` takes no id because a Project has no parent to be entitled to.

The base **member** role holds *none* of the three. That is the one narrowing of a static role and it is deliberate: `accessedProjects` does not bound what a Project write reaches, so a member granted one Environment and one Service of a Project could rewrite the `env` that every other Environment and Service under it references — changing what every `${{project.KEY}}` already written there resolves to at its next deploy, or failing those deploys outright by removing a key one of them named (ADR-0014). A member works inside a Project and does not administer it; an owner, an admin or a licensed custom role granted `project: ['update']` does.

_Avoid_: App group, workspace; "inherits" or "inherited `env`" for what a Service beneath it reads — the levels are never merged (ADR-0014)

**Project config**:
The one description of what a Project runs: its services, each one's kind and size, and the names of the variables each reads. Every Project has exactly one, stored either *in the repository* or *in Cloudgate*. Its two places are where it is kept, not two copies: the console is a way to edit it, never a second record beside it (ADR-0029). It holds the *what* only: what is the same in every Environment. What differs per Environment, names a host or an account, holds a secret, or is an operational record (backups, schedules, health, Traces) is Cloudgate's, so a Project config never carries a secret or a variable's value, only its name (ADR-0006, ADR-0019). A Service whose kind the config cannot yet express is still listed in it as console-managed, so the config remains the whole list even before it can describe every entry. Every Project created before the config existed was given one at upgrade, kept in Cloudgate and generated from its saved settings so that its first plan in every Environment changes nothing; whatever the config could not say the same way everywhere was written as console-managed, with a comment saying why. A Project spanning several repositories still has one: each Service names its own source (a repository or an image), independent of where the config is kept, so a config in one repository may describe Services built from others. Where it is kept is Cloudgate's, set once per Project, and may be any repository the organization can reach, including one no Service builds from; changing it is `project: ['update']`, since a new location can rewrite every Service. Moving it, into a repository, out of one, or between two, changes only where it is read and applies nothing: the move is refused unless every Environment's copy at the new place can be read, it shows each Environment's plan first, and once confirmed it dismisses the plans made from the old place and leaves the new ones open for an ordinary Apply. Moving out of a repository keeps the one copy the operator picks (the default branch's unless another is chosen), drops the Config branches, and leaves the file in the repository unread. When it is kept in a repository, the console shows each Environment's Config branch copy read-only and never writes to the repository: a config-owned setting, a new variable name, creating a Service of a kind the config describes, or deleting one it lists is refused with a pointer to the file and branch, while everything Cloudgate owns stays editable as before, and a console-managed Service may still be created there, its missing line only noted by the next plan. Kept in a repository, it is a YAML file at the one path the Project stores: a move that names no path takes `cloudgate.yaml` at the root, or `cloudgate.yml` when every Config branch has only that, and keeps the one it found, so no later read falls back from one name to the other (a branch holding both, or branches holding different ones, refuses the move until a path is named); kept in Cloudgate, it is the same text, shown beside the Service pages that edit it. Either way it states the version of its own format and lists each Service under its name, and a field Cloudgate does not know refuses the plan rather than being skipped.
_Avoid_: Config file for the concept (a Cloudgate-stored one has no file), manifest, blueprint, spec

**Config name**:
A Service's fixed name in its Project config: lowercase letters, digits and hyphens, starting with a letter, at most 63 characters. It is what a plan matches a config entry to, so the same config name in two Environments is the same entry. It is made once, from the display name when the Service is created (or, for a Service older than the field, at upgrade), `-2`, `-3` apart across every kind in the Environment, and never follows a rename of the display name, which is Cloudgate's label.
_Avoid_: appName (the instance-wide container name), display name, slug

**Config branch**:
The branch whose copy of a repository-kept Project config an Environment reads, set per Environment in Cloudgate and the repository's default branch when unset. Two Environments may read different branches and so briefly disagree on which Services exist; that gap is a change waiting to be promoted, not a second config. Only a plan reads the config: a build or a Preview deployment uses the settings the last applied plan left on its Application, so a build never needs the config's repository. A push to the config branch prepares a plan and never applies one by itself here; a push that also changes an Application's own entry holds that Application's build until the plan is applied or dismissed. A config branch that cannot be read refuses every plan of its Environment, naming the repository and branch, with no fallback to another branch. A Cloudgate-kept config has no branch: every Environment reads its one copy.
_Avoid_: Config ref, tracked branch (that is an Application's)

**Plan**:
One Environment's list of what applying its Project config would create, change and destroy, found by comparing the config with Cloudgate's saved settings on the fields the config owns, never with what is running on a Server; for a Service in a Cloud account it also reads that cloud (see below). It is made by a push to the Config branch or on request, and an Environment has at most one open plan, a newer one replacing it. A plan whose config commit or compared settings have moved on is refused rather than applied. A console edit to a Cloudgate-kept config is a plan its own Save applies; nothing else applies a plan but an explicit Apply. Applying runs creates, then changes, then destroys, each step succeeding or failing on its own, so a plan can end partly applied and the next plan shows what is left. It writes saved settings and then queues an ordinary Deployment for each Service that needs one; a plan is applied once its settings are written, and a failed build is that Service's Deployment, not the plan's. A destroy is the Service's Delete, confirmed by name. A Service is identified by its name in the config, so a rename or a change of kind is a destroy and a create. A Compose stack is described by the compose file it names in a repository (its `source`, `file` and `type`), never by a copy of it: a plan compares those three fields, a change to the file's contents is a code change its next Deployment picks up and never a plan line, a change of `type` is a destroy and a create, and a stack's destroy names the volumes its Delete removes (ADR-0069). A Compose stack a plan creates where the Deploy target is a Cloud account runs on its own **Stack VM**, and one of `type: stack` there is refused, naming it (ADR-0070). On the fields the config owns, saved settings change only by applying a plan, which is what keeps them the config's applied state rather than a second record (ADR-0029). Applying asks nothing new of the caller: every step is checked against the statements its Service already uses (`service: ['create']` on the Project for a create, `service: ['update']` on a reachable Service for a change, `service: ['delete']` for a destroy, `deployment: ['create']` for each queued Deployment), all before any step runs, and one refused step refuses the whole Apply, so a plan ends partly applied only because a step failed, never because of who applied it. A Cloudgate-kept config's Save is checked the same way. Seeing a plan or asking for one is `environment: ['read']`; dismissing one is `environment: ['update']`. No agent role may change a Service, so an Agent sees and may ask for plans but never applies one. Beside open, applied, partly applied and dismissed, a plan is recorded as superseded when a newer plan replaced it while open, and as unchanged when it found nothing to change, so it was never open. A Service the config does not list is destroyed only when the config in effect before described it; one it listed as console-managed, or never listed, is a note. In a Cloud account it is still one plan, approved by one Apply: each step that touches a cloud Service, or the **Environment network**, also shows what the cloud will create, change and destroy, read from the cloud itself, each size beside the cloud's real CPU and memory. A push's plan reads only the Services it touches, those an open plan it replaces had found **Drift** on, and the network when it must be made or removed; asking for a plan reads every one in the Environment, and a request while one is still reading joins it. A plan whose read failed is shown with the reason, and is refused at Apply until a read succeeds. Drift is listed apart, and Apply always puts back Cloudgate's version; something found in the cloud by Cloudgate's mark is taken back rather than made twice. A plan is unchanged only when neither the config nor the cloud differs, so a plan with only drift stays open, and its Apply redeploys each such Service on its live image.
_Avoid_: Diff, changeset, Deployment (applying a plan queues Deployments; it is not one)

**Console-managed**:
A Service listed in its Project config by name and kind only, because the config does not yet describe it: its kind is one the config cannot express (MongoDB, MariaDB, libsql, MySQL until slice 9, and a Compose stack until ADR-0069), its Compose stack's compose file is not in a repository (raw text, which every template stack's is, or an uploaded archive), or, in a generated config, its Environments disagree on a setting the config would own, or it exists in only some of them. Removing `managed: console` from an entry of a kind the config can express hands it to the config, and the next plan shows what that changes in each Environment. When a kind becomes one the config can express (MySQL does in slice 9, a Compose stack whose compose file is in a repository by ADR-0069), no upgrade rewrites a config to describe its Services: each stays console-managed until its operator hands it over, and every plan notes the entries that now could be. It is changed only in the console: a plan never changes or destroys it, and dropping its line from the config is not a Delete. A plan creates one only from a **Pending setup**, which is how a Template's compose part is made (ADR-0065). A plan does make the **Stack VM** of a Compose stack the console created in a Cloud Environment, and later resizes it from the stack's console setting, but never creates, changes or destroys the stack itself.
_Avoid_: Unmanaged, external (it is fully Cloudgate's, just not the config's)

**Template**:
A ready-made starting point for a Project's Services, read from the catalogue. It is a folder: a Project config (`cloudgate.yaml`) that passes the same check as any user's, a `template.yaml` with what only a template has (name, description, the app's version, tags, links, the values asked for or generated at setup, Domains and files), at most one compose file, the config files it ships, and a logo. Its Domains name only services in its compose file, since its own `web`s get the usual generated one, and never a fixed host: on a Server each starts on a generated host the user may change at setup, and in a Cloud account, where a Stack VM has no generated host, on a host the user types. Its id is its folder's name and never changes. Setting one up copies it once into an Environment the user picks, as an ordinary Plan, and the copy keeps no link to it and gets no updates from it. Its compose stack is console-managed after setup, and its other Services are ordinary config entries. Each part's Config name is a setup name (the template's id unless the user changes it) in front of the template's own name for it, `ghost-app`, `ghost-db`, and a clash takes `-2` on the setup name as a whole. What a setup chose waits as a **Pending setup** until the Apply that creates it, and the setup leaves a **Setup record** on the Project (ADR-0065). Each of its values is generated, asked of the user, fixed by the template, or wired from an Output; all but wired ones are made once at setup and then saved like any typed value, and its compose part never takes an Output (ADR-0064). It can be set up only in an Environment whose Deploy target can make every one of its entries, which Cloudgate works out rather than the template saying so (ADR-0063); a compose part runs in a Cloud Environment on its own Stack VM, never on a Server beside it (ADR-0070).
_Avoid_: Blueprint (the old `template.toml` format being retired), one-click app, manifest, recipe; "template" for the Project config it contains (that becomes the user's Project config, not a Template), or for a Cloud account's setup template (a different thing)

**Existing database**:
A Database Service whose place, fixed when it is created, is a database made outside Cloudgate, for example one made by hand in a cloud's console, chosen in Cloudgate per Environment so the Project config does not change. Cloudgate reads its address, uses the login the operator gives, and hands out the usual Outputs, but never changes it, makes nothing inside it, and leaves it as it was on Delete. The config's database, user, size and version are not applied to it. One Cloudgate made, in any Environment, is never one (ADR-0033). A plan that finds it at a new address changes its Outputs: its Apply saves the address, then redeploys what links to it; one that finds it gone says its cloud cannot find it ("AWS cannot find", "Google Cloud cannot find") on its page. On Google Cloud only a Cloud SQL postgres or a Memorystore for Valkey redis can be one; Cloudgate reaches it through a private address of its own in the Environment's network, which belongs to the Service, is shown with its cost and goes with its Delete, and it checks that the database lets this Environment in rather than taking the operator's word for it (ADR-0033). Switching a Service to or from one is asked for on its page and copies no data. From one to a Cloudgate-made database is one Apply; to one from a Cloudgate-made database is two, since the next plan's Apply runs the old database's Delete and only the plan after that Delete adds the existing one.
_Avoid_: External database, imported, adopted, shared database

**Output**:
A named value a Service of a kind the Project config describes hands to other Services, from a fixed list per kind (a `postgres` or a `mysql` hands out `url`, `host`, `port`, `user`, `password`, `database` and `ca`, a `mysql`'s `url` carrying no TLS setting, on AWS, where it is an RDS for MySQL instance, its `ca` RDS's bundle, and on Google Cloud, where it is a Cloud SQL for MySQL one, the instance's own CA; a `redis` `url`, `host`, `port`, `password` and `ca`; a `bucket` `name`, `region`, `endpoint`, `access_key_id`, `secret_access_key` and `path_style`). Every Output is a secret, and is built by Cloudgate from the Service's own settings and the address its Deploy target reports, so its form is the same on every target. `ca` is the certificate authority an app must trust to reach the Service over TLS: a cloud's public bundle where the cloud signs with one, the instance's own where it does not; a Server hands out no `ca`. A bucket's key has no value on AWS, where the linked Service's own identity gives access, and a variable linked to it is then left unset (ADR-0032); on Google Cloud it has one. Likewise a redis on Memorystore has no `password`, since only its Environment's private network reaches it (ADR-0042). A console-managed Service hands out none (ADR-0031).
_Avoid_: Connection string, export, attribute

**Wired variable**:
A variable whose value is another Service's Output, linked by name in the Project config (`{ DATABASE_URL: pg-1.url }`) and filled in at each deploy, never typed or saved. The link is the config's; the value is never Cloudgate's or the config's to hold. A plan refuses a link it cannot honour, and a changed Output reaches the linked Service at its next deploy (ADR-0031).
_Avoid_: Reference (that is a typed `${{…}}`), linked env, binding

**Size**:
How much CPU and memory a Service may use, as the Project config states it: one of a single list of names for every kind (`xsmall` 0.25 CPU / 512 MB, doubling through `small`, `medium`, `large`, `xlarge`, to `2xlarge` 8 CPU / 16 GB), or a custom pair of CPU and memory, always both. On a Server a size is the Service's cap only; how much a Server sets aside for it stays Cloudgate's, since it depends on the host. A Service whose config entry has no size is not uncapped by the config but uncovered by it: its caps stay Cloudgate's, editable in the console, and a plan leaves them alone; a Service a plan creates without one starts uncapped. On a cloud whose databases come in fixed machine types, a size is the smallest machine type at least as large in both CPU and memory, which the plan names with its real CPU and memory, so two sizes may land on the same machine; for a cache, which a cloud sells by memory, "at least as large" means in memory only; an entry with no size is created on the smallest machine type, after which that choice is Cloudgate's like an uncovered cap. On Cloud Run a size is likewise the smallest allowed CPU and memory pair at least as large in both, never under one CPU, since less would let each copy serve only one request at a time; an entry with no size is created at Cloud Run's own default, after which it too is Cloudgate's. An exact machine type or CPU and memory a size cannot reach, such as a database family Cloudgate never chooses, is set through the Service's Native settings for that cloud; there the native value wins, the size still counts on every other target, and the plan shows the size beside the native value it gives way to. Taking that native value out falls back to the size, or, with no size, leaves the machine where it is and Cloudgate's again, never the smallest; while the config sets it natively the console cannot change it. On a Server a size is already exact, so it has no native form.
_Avoid_: Plan (a Plan is the config-vs-settings diff), tier, instance type, limits (the Server-side form a size takes)

**GPU reservation**:
How many whole GPUs each running copy of an Application holds on its run Server, 0 meaning none: an Application with two copies reserving one GPU holds two cards. Any Application may have one, not only an AI model; a database or a Compose cannot. Cards are never shared or split, and a copy that reserves none is kept off every card, as is every database, and an operator's env cannot put either back on them. A Compose is not kept off the cards and is not refused on a GPU Server, so its containers can still see them: a known gap, not a guarantee. A GPU Server is a Server, or the platform host, whose GPU setup lists each card by its own identity; one set up before that holds no GPU reservation until its setup is run again. A reservation the run Server could never hold is refused when saved; one it cannot hold now because its cards are taken fails the Deployment before anything is released, leaving what ran before running, and is never left waiting to start by itself when a card frees. Stopping or deleting the Application frees its cards at once, and Swarm alone records who holds which card. It differs per Environment, so it is Cloudgate's, never the Project config's.
_Avoid_: GPU limit, GPU size, GPU share, GPU quota

**GPU setup**:
What makes a Server, or the platform host, a GPU Server: it lists each of the machine's cards by its own identity and restarts Docker there, so every Service on that machine stops for a moment. It is run only when an operator asks, after a warning naming the restart, and never by Cloudgate on its own, not on upgrade and not on deploy. On a Server it is run by the owners and admins of the organization that owns the Server; on the platform host, which every organization shares, only by the instance's owners and admins; never by an Agent. It reaches only the Server's own machine, so a GPU on another machine joined to that Server's Swarm is not counted and cannot be reserved. A machine set up before cards were listed one by one reads as needing setup again, not as set up. How many cards a Server has, and how many are free, may be read by anyone who may create a Service on it; what drivers it runs may not.
_Avoid_: GPU support (the card's title, not the act), GPU install, GPU enablement

**Native settings**:
The part of a Service's Project config entry written in the language of its Deploy target rather than the config's own fields, one block per target, of which only the block for the Environment's target is used. On Docker it is not a second copy of the Service's Swarm settings but their home: it holds those that are the same in every Environment (labels, health check, restart policy, update and rollback behaviour, stop grace period, ulimits), spelled exactly as Docker spells them, and each is laid over Cloudgate's own defaults for that kind rather than replacing them. It holds nothing else: placement, networks, published ports, the service mode and the replica count stay Cloudgate's, because they name a host or differ per Environment, so publishing a port is still done only through the Service's port settings. A console-managed entry has none. Using them asks for no statement of its own: they are the Service's settings, so writing or applying them is checked like any other change to the Service, on every target. What keeps them safe is the fields they may not touch and the plan that shows each value before it is applied, not who may write them, so an Agent can never apply one and a role cannot be refused native settings while keeping the right to change the Service. The config owns these settings whether or not the block is written: a key that is absent, or taken out, is Cloudgate's default for the kind, never the last value it had. A plan shows each native change as its own line under the Service's change, marked as native and in the file's own spelling, and it asks for no extra confirmation; a change Cloudgate knows will take the Service down is warned about instead. A value Cloudgate can check is refused by the plan; one only the target can judge fails that Service's Deployment and names the setting. On a cloud the block names each thing the Service makes there by the same address its plan's cloud lines show (its kind of resource and Cloudgate's name for it), and holds only that cloud's own settings for it, never instructions to the tool that makes it. Only what a Service makes once can be named: what it makes once per Domain or per variable belongs to those, not to the config. Each value is laid over Cloudgate's own, a nested group of settings field by field and a list whole, and the one container a cloud `web` runs is set the same way, in the cloud's own spelling. A name the Service does not make, a setting the cloud's tool does not know, or a value of the wrong shape is refused by every plan, whatever the Environment's target, so a mistake shows on the first plan rather than the first deploy to that cloud; a setting the tool is retiring is warned about. Which version of the tool's settings a file is written against is Cloudgate's, moved only by upgrading Cloudgate. A native setting becomes a config field only when it can be said the same way on every target, never because many configs use it; once it does, the native form stays accepted, wins on its own target as with a size, and the plan notes that the field exists, so no file breaks and the config's version does not move. Adding anything optional, a field or a Docker key, never moves the version; only taking something away or changing a meaning does. A key joins the Docker list only when it is the same in every Environment, names no host and cannot reach other tenants, with its locked parts decided at the same time; some keys, such as running privileged, bind mounts, networks, ports, placement, mode and CPU or memory, are never admitted, and refusing one gives its reason. The **Environment network** has no Native settings, since no config entry describes it.
_Avoid_: Overrides, raw spec, pass-through (it adds settings to what Cloudgate generates, never resources of its own, ADR-0044)

**Locked setting**:
A Native setting, or a value inside one, that Cloudgate refuses because Cloudgate itself depends on it or because it reaches beyond the Service: how Cloudgate finds and deletes what it made, routing and ownership, the shared network and other tenants, who the Service runs as, and whether it can be reached from outside. Reach may be narrowed, never widened: closing a Google Cloud `web`'s own `run.app` address so only its Domains and its Environment reach it is open, opening a Private web service to the internet is not. A setting Cloudgate itself sets outside the plan, such as the copy count Stop and Start change, is locked, since a value written there would never be applied. A setting that can only hurt the Service it is on stays open, with one named exception: a database never updates or rolls back by starting its new copy before the old one stops, since two copies writing one volume lose data for good. Every target has one list, which the plan, the console and the deploy all read; a locked value is refused, naming its path and the reason, and never silently dropped or overwritten. On a cloud the list names what is refused and leaves every other provider setting open; every key, kind and generated resource must carry an entry, even an empty one, before it ships.
_Avoid_: Deny-list, blocked field, protected field

**Environment**:
A named slice of a project (e.g. production, staging) that owns the actual services — applications, databases, compose stacks — and its own `env`, which every Service in it can reference by name at deploy. Not inherited, on the same mechanism a Project's is not: a Service's `${{environment.KEY}}` references resolve against this row, an unreferenced key here reaches no container, and an unresolvable reference throws (ADR-0014). Entitlement is granted per environment: the member row's `accessedEnvironments` names which ones a caller may reach at all.

The same three questions as a Project's and a Service's, one level in between. **Reading** an Environment is `environment: ['read']`. **Rewriting** one — its name, its description, the `env` its Services reference — is `environment: ['update']`. **Minting** and **retiring** one stay `environment: ['create']` and `environment: ['delete']`, and a retirement also asks `service: ['delete']` of every Service in it, so a role granted the delete is never refused it for want of the update.

Unlike a Project, the base **member** role holds `['read', 'update']`: the write is bounded by an explicit per-Environment grant, and a member already holds `service: ['update']` on the Services inside it — which is the statement that gates each of those Services' own `env` write, and the reason the `envVars` this sentence used to cite beside it was gating nothing.

_Avoid_: Stage, namespace; "inherits" or "inherited `env`" for what a Service in it reads — the levels are never merged (ADR-0014)

**Deploy target**:
Where an Environment's Services run by default: a Server, the platform host, or a **Cloud account** and a region. The region is chosen per Environment, not fixed on the Cloud account, so two Environments may use one Cloud account in two regions. Every Environment has exactly one, and "the platform host" is a choice made, never an unset one. It is Cloudgate's, never the Project config's. It decides only where a Service is *created*: each Service keeps its own place, fixed when it is created: a **run Server** (or the platform host), or a Cloud account and region. That place may differ from the default, it is where the Service's logs, Stop and Delete go, and changing the default moves nothing that already runs. So one Environment may hold Services in both kinds of place. A plan only ever creates where the Deploy target says: an entry of a kind the Environment's cloud cannot yet make refuses the plan, naming it, and is never put on a Server instead. A console-managed Service is still created on the Server its creator names; in an Environment whose Deploy target is a Cloud account the creator must name one, or the platform host on purpose, since a console create there is refused rather than put on the platform host without asking. A Compose stack is the exception: in such an Environment it names no Server and runs on its own **Stack VM** there (ADR-0070), while one already on a Server keeps its place. The Deploy target may be switched at any time, to or from a cloud or to another Cloud account or region; the switch moves nothing, and a plan made before it is refused at Apply, since it names the old place. Nothing moves a Service: moving a stateless one is taking it out of the config and putting it back, a Delete and then a create. Choosing it is editing the Environment, `environment: ['create']` or `['update']`; choosing a Cloud account also asks `cloudAccount: ['read']` on it, so nobody points an Environment at an account they may not see. Making anything there is still the Apply's `service: ['create']`. On the **Hosted instance** the platform host is never a Deploy target and never a Service's place, for any Organization: a create that names it or names no Server is refused, an Environment cannot be made until its Organization has a Server or a Cloud account to point at, and a Server may not be the box itself (ADR-0053).
_Avoid_: Target on its own, placement, location; Server for the default (the Service's own Server is its run Server)

**Cloud account**:
One Organization's link to one account at one cloud: a name, which cloud, the cloud's own fixed id for that account (an AWS account id, a Google project id), and a credential only that cloud understands. It has no region; each Environment that uses it names one. The cloud's id never changes for the Cloud account's life, because every Service in it records it and its Delete must reach the same account; a wrong one is a new Cloud account. One Organization connects a given cloud account at most once, but two Organizations or two installs may each connect the same one, and everything a Cloud account makes is marked as its own, so one never touches another's. A credential that stops working is found by the next use, which fails before changing anything, and the Cloud account shows when and why until a check passes again. It cannot be deleted while any Environment, Service or Environment network still uses it, and its Delete names each; deleting it never removes what the operator made in the cloud to let Cloudgate in. It is the Organization's own resource, like a Server, under its own statement: `cloudAccount: ['create']` connects one, `['update']` changes its credential, checks it again and hands out its setup template, `['delete']` removes it, and `['read']` lists it and its last check without calling the cloud. Owners and admins hold all four; the base member and both agent roles hold none, and see which Cloud account and region a Service runs in only by reading the Service. An Agent may deploy, restart, start and stop a Service in a Cloud account as on a Server, so it can bring back spend a person stopped, but it never makes anything there, because it never applies a plan; narrowing or suspending the Agent is how an operator stops that, never a rule about who the caller is. A Service it runs keeps its images in that same cloud, in a store of the Service's own that goes with the Service's Delete, so a cloud Service never uses a **Registry**. Each such Service also has an identity of its own in that cloud, made with it and gone with its Delete, which can never do more than the limit the operator's own setup put in place (ADR-0032); it is the only identity Cloudgate makes there, and what lets Cloudgate in is the operator's to make and to remove. A Google one is a project that Cloudgate reaches with no stored Google secret: it signs its own short-lived proof with a key of that Cloud account's own, which the operator's project is set to trust, and then acts as one deploy identity the operator made there and granted Cloudgate's role. Since Google cannot keep that identity from acting as any other identity in the project, the operator is asked to give Cloudgate a project of its own.
_Avoid_: AWS account or GCP project (those are the cloud's own things), provider, integration, connection, credential (one part of it), Server (a Cloud account is never one)

**Environment network**:
The private network and the one load balancer Cloudgate makes for an Environment in a Cloud account and region, which every Service the Environment runs there shares. One per Environment, never shared between Environments, even two in the same Cloud account and region. Nothing is made when the Deploy target is set: the first plan that creates a Service there lists the network as its own creates, with its idle cost, and the same Apply makes both. It stays while the Environment has a Service or its Deploy target there, even with no Service left, so its load balancer's address does not change under a hand-made DNS record. It goes with the Environment's Delete, or with the first plan that finds neither there. If that Delete cannot remove all of it, the Environment is kept, naming each thing left, until the operator retries or lets it go. Cloudgate always makes its own and never adopts a network the operator already has. On Google Cloud it also holds the private link its databases attach through: the first plan that creates a database of a kind adds that kind's part, and the link stays, even with no database left, until the network itself goes. On AWS it holds, by the same rule, the private DNS namespace its Private web services are reached by, added by the first plan that creates one. There the network itself costs nothing, and every Service joins it from its first deploy. Google keeps its addresses for an hour or two after the last Service goes (about 1¾ hours on the first walk), so an Environment's Delete there first ends incomplete, naming what Google still holds and when Cloudgate will try again, and Cloudgate tries again by itself before leaving it to the operator.
_Avoid_: Shared network, VPC (the AWS form it takes), Server

**Cloud run**:
The plan and apply of one cloud Deployment, against one state: the part of a deploy to a Cloud account that comes after the image is built and pushed. It belongs to that Deployment and writes into its Deployment log, so a cloud deploy is still one Deployment from build to apply. Cloud runs wait for a slot of their own, apart from builds: how many run at once is set for the whole install, one unless the operator raises it. Two Cloud runs of one Service never overlap, and one that changes the **Environment network** waits for, and holds back, every other Cloud run in that Environment. It may be cancelled while it waits or plans, never once its apply has begun; from then on it can only be stopped, by a person who may cancel its Deployment or by the install's time limit on it, and a stopped run keeps what it made and ends as an error, never as cancelled. A queued one is still there after Cloudgate restarts. One cut off part-way, by a restart or anything else, is never started again by itself: its Deployment ends as an error saying so, and the next deploy's plan shows what was already made. It always reads the cloud again before it applies, and applies on its own only what a person already approved in a plan, plus the new image of a deploy. Anything else it finds, **Drift** above all, stops it before it changes anything: its Deployment ends as an error saying so, and what it found becomes the Environment's open plan, so a code push, a console Save or an Agent never changes the cloud beyond its image unseen.
_Avoid_: Runner, job, tofu run (the program it uses), build (the step before it)

**Drift**:
A difference between a cloud and Cloudgate's **Infrastructure state** that Cloudgate did not make: a field changed, or a thing deleted, by hand in the cloud's own console. A plan that reads the cloud lists it apart from the config's changes, naming each field with its old and new value (never a secret one), and its Apply always puts back Cloudgate's version; there is no keeping a hand change, which is made by changing the config instead. A Cloud run that finds it stops rather than put it back unseen. On Google Cloud it is found the same way, by each thing's own id, whether or not the thing carries Cloudgate's mark; changes Google makes by itself, and Cloudgate's own Stop and Reload, are never drift.
_Avoid_: Out of sync, divergence; drift for a Server (a plan never compares with what runs there)

**Infrastructure state**:
Cloudgate's record of what it made in a Cloud account, which a plan compares with the cloud to find what to create, change and destroy. There is one for each Service that runs in a Cloud account and one for each **Environment network**, so one broken state never stops another's deploy. It is Cloudgate's, kept encrypted in Cloudgate's own database, and nobody reads or downloads it through any surface: what a person sees is the list of things in it (type, the cloud's id, region, Cloudgate's mark), read with the same statement that reads its Service or Environment. Only one run uses a state at a time, and a run that finds it in use fails rather than waits; nothing outlives its run to hold it. A state goes only once everything in it is destroyed, so a Delete that could not finish keeps it. Everything in a state that the cloud lets carry one bears Cloudgate's mark naming its Cloud account, Environment, state and place in the state, which is how a state that has fallen behind, gone missing or become unreadable is brought back: each plan looks for marked things the state does not know and adopts those it would otherwise create again, so nothing is made twice, and names the rest for the operator to remove. What a search by mark cannot find, such as each Service's own identity in the cloud, is listed as not findable by mark and checked by its id instead. An unreadable state is never written over quietly; a person who may change its Service or Environment rebuilds it from the cloud, confirmed by name. No older copy of a state is kept. A state only moves forward with Cloudgate: it records the tool versions that last wrote it, a newer Cloudgate brings it up to date on its next run, and an older one refuses to touch it, naming both versions, rather than run against what it cannot read.
_Avoid_: Terraform state, tfstate (the tool's words), stack

**Domain**:
A host (and path) a Service answers on, owned by Cloudgate and never by the Project config. On a Server it is a Traefik router, and its host is that Server's: another Organization cannot route the same host on the same Server. In a Cloud account its host is unique only within the Organization: two Organizations may hold one host on their own cloud Services, and DNS and the cloud's certificate decide which one serves it (ADR-0060). In a Cloud account it is the same row, but it becomes a rule on the **Environment network**'s load balancer plus that cloud's own certificate for the host, and the fields only Traefik can honour are refused, naming the field. It is always HTTPS there, each Domain has its own certificate, and a bare name is allowed. Cloudgate never makes its DNS records in a Cloud account: it shows the operator the record that proves the name and the record that points it at the load balancer, then checks for them itself. A deploy never waits on the certificate. The Domain has its own status (waiting for DNS, checking, live, failed), and its certificate is attached when the cloud issues it. Removing one names the DNS records left at the operator's provider, but never blocks on them, nor on the cloud letting go of its certificate: AWS's certificate service calls a certificate in use for up to an hour after CloudFront or a load balancer drops it, so the removal takes it out of the **Infrastructure state** and Cloudgate deletes it once it is let go. A Domain's run never puts back a hand change on what it applies: it stops, naming the **Drift**, and the next plan's Apply puts it back, after which the Domain's change goes on. Adding, editing or removing one runs right away as its own short Deployment, with no plan to approve. A `web` a plan creates in a Cloud account gets no generated Domain. A `static` site on AWS follows the same rules on its own CloudFront distribution instead of the load balancer: its certificate is in `us-east-1`, its host becomes the distribution's alternate domain name once the certificate is issued, and its Domain's Deployment waits for CloudFront to spread the change, at most 30 minutes. A distribution serves one certificate, so a `static` site on AWS takes one Domain, with no path. Its distribution's own `*.cloudfront.net` name is its generated Domain, because that name serves only the one site. On Google Cloud a `web`'s Domain follows the same rules: the record that points it is an address record to the **Environment network**'s fixed address, so a bare name needs nothing special, and every Domain in the Environment is one rule set on that network, so changing one is a run of the network rather than of the Service. A `web` on Google Cloud keeps the address Google gives each service, which is its generated Domain, since that name serves only the one Service. A `static` site on Google Cloud sits on that same load balancer, so it takes any number of Domains and changing one is a run of the network too; it has no generated Domain, since nothing there serves only the one site, so until a Domain is added it is deployed but answers nowhere. The one-Domain limit is CloudFront's alone.
_Avoid_: Route, hostname, router (Traefik's form of it)

**Service**:
An Application, Compose stack, or Database — the deployable thing an environment owns, and what a deployment, backup or schedule belongs to. Entitlement is granted per service: the member row's `accessedServices` names which ones a caller may reach at all.

*Which* services a caller may reach and *what* they may do to one are separate questions, and the second is answered by three different statements. **Reading** a service is `service: ['read']`. **Operating** one — start, stop, reload, deploy, rebuild, remove containers, write its status — is the lifecycle statement `deployment: ['create']`, which is what lets a role run a stack it may not redefine. **Rewriting its definition** is `service: ['update']`: the service's own row, its environment, its published port, its dropped source, its deploy-webhook secret, and the configuration child rows that carry no statement of their own — ports, redirects, basic-auth users, mounts and patches. Minting and destroying one stay `service: ['create']` and `service: ['delete']`, and `create`'s id is the target Project's rather than a service's, because creating a service needs access to the project it lands in.

The distinction that makes the list finite: a Backup, a VolumeBackup, a Schedule, a Domain, a Deployment, a Rollback and a Preview deployment are *not* the service. Each is its own resource with its own actions, so `backup: ['update']` or `deployment: ['cancel']` sets the level of those writes and the service-access check beside them is answering entitlement only — for which `read` is the right level. **The exception is a write whose *effect* does not land on its own parent**: a volume backup names a volume and a database restore names an object key, both off the wire, so registering, re-pointing and restoring either one claims `service: ['update']` on the Service they are aimed at. `VolumeBackupsService.create` and `BackupsService.create` carry the argument. `volume` is likewise the Docker volume rather than the Mount that references it, which is why a Mount is on the definition side of the line and a VolumeBackup is not.

The same distinction places a **Tag**. A Tag is its own resource — `tag: ['create', 'update', 'delete']` mint, rename and destroy the label. But *which Projects wear a label* is not the label, and it is on the Project side: assigning and unassigning a Tag is `project: ['update']`, because the write is keyed on the projectId and nothing in the `tag` statement is about a Project.

_Avoid_: Using it for Application alone; workload; "service permission" for whichever of the four actions is meant

**Application**:
A deployable service built from a source (git provider, docker image, or raw files) and run as a container on a server.
_Avoid_: App, workload

**Bucket**:
A Service, written `kind: bucket` in the Project config, that holds files other Services read and write, and runs nothing itself. Its entry says only its kind and description: no size, since a size is CPU and memory and a bucket has neither, no variable names, since it reads none, and no place, since it lives where its Environment's Deploy target says. Its real name in the cloud is Cloudgate's, made once when the bucket is created so that no other account can ever take it, shown in the plan and never written in the config; which web pages may upload to it straight from a browser is Cloudgate's too, set per Environment and empty until set, since it names hosts. A Service that links any of its Outputs may read and write its files, but not change the bucket itself; any number of Services may link one bucket, sharing one key on a Server and on Google Cloud, and each reaching it through its own identity on AWS (ADR-0032); what happens to its files on Delete is the **Delete** entry's. On a Server each bucket is its own storage container on the Environment's Server, with its files on a volume; it is reached at its Domain while it has one, and its key can be rotated, which redeploys every Service that links it (ADR-0037). On AWS it is an S3 bucket in the Cloud account and region it was created in, its name made in the account's regional namespace (`<name>-<8 random>-<account-id>-<region>-an`), with versioning off, S3's default encryption and Block Public Access on; it is made, changed and put back by its own Cloud run in its own Infrastructure state, and its trusted web pages are its CORS, written by the Apply of the plan that shows them. A cloud Service that links it reaches it through its own task role, which its deploy gives read and write on that bucket's objects and nothing else; its key Outputs have no value there, so a variable linked to one is left unset. An Environment on AWS may instead use an **existing bucket**, an S3 bucket made outside Cloudgate and named in the console, which takes the **Existing database** shape: every plan looks it up, it hands out the same Outputs and access, Cloudgate never changes it (no CORS, versioning or encryption), and its Delete leaves it and its files as they were; one carrying Cloudgate's tags is refused (ADR-0033). On Google Cloud it is a Cloud Storage bucket in the Environment's project and region, named `cloudgate-<the Service's key>-<8 random>` once at create, since Cloud Storage names are one world-wide namespace that anyone may take, with Google's soft delete off so that a deleted file is gone, as on AWS. The S3 SDK cannot use a Cloud Run service's own identity, so there, as on a Server, the bucket has its own key, held by a Google service account of the bucket's own that may read and write only that bucket, and its Outputs say `endpoint` `https://storage.googleapis.com`, `region` `auto` and `path_style` `true`; the linking Service's own identity gets no access, and the key is rotated as on a Server (ADR-0032). An Environment on Google Cloud may also use an **existing bucket**, in any project and location: it is reached by a key of its own as above, once the operator grants that key's service account access on the bucket, which Cloudgate shows and checks but never makes; its Delete leaves the bucket, its files and that grant (ADR-0033). A `static` site's own storage is not a Bucket: it belongs to that site and is a copy of its build.
_Avoid_: Storage, S3 (the AWS form of it), volume (a Server's disk, not a Service)

**Cron service**:
A Service, written `kind: cron` in the Project config, that runs a command on a timetable, each time in a fresh container started from its own built image, which exits when the command does. Each firing is a **run**, recorded as a Run record. It is a Service in full: its own source, build, size, variable names and Config name, its own access entry, created and destroyed by a plan. Its timetable is a five-field unix cron expression read in one time zone (UTC unless named), the same in every Environment; pausing it is per Environment and Cloudgate's. A run that outlives its time limit is stopped and counts as failed; a failed run is not retried, and a run still going at the next tick does not stop the next one starting. On every target Cloudgate itself keeps the timetable and starts each run (on AWS a one-off task, on Google Cloud an execution of the Cron service's job, never the cloud's own scheduler): a time that does not exist that day is skipped and a time that happens twice fires once, and a tick missed while Cloudgate is down is not made up. Each run uses the image of the last build that succeeded, so it never waits for a build in progress and a run in flight keeps its image; until a first build succeeds, nothing fires. A run may also be started by hand ("Run now"), by whoever may deploy the Service, paused or not, and its record names who. Each run's output is its own Deployment log, opened with what started it and closed with its exit code or that it timed out; a run Cloudgate loses track of while restarting is picked up again with its time limit counted from its start. It is not a **Schedule**, which runs a command inside a container that is already running, or a script on a host, and belongs to a Service rather than being one; both keep working side by side (ADR-0034).
_Avoid_: Schedule, scheduled job, cron job, job, task (a run is a Run record, not a job)

**Worker**:
A Service, written `kind: worker` in the Project config, that runs all the time with no Domain and no promised address. It holds what a `web` holds except a port, and on a Server it is an Application in every other respect, so its Deployments, logs, mounts, Schedules and published ports are an Application's. In an AWS Cloud account it is a `web`'s ECS service with nothing routing to it: no target group, listener rule or inbound rule; in a Google Cloud project, a Cloud Run worker pool, which has no port and lets nothing in. It never gets a Domain or a pull-request preview, from a plan or from the console. Other Services may happen to reach it on the network, but nothing promises it; a Service meant to be called has an address of its own. Healthy means only that it is running (and, on a Server or in an AWS Cloud account, passing its container `HEALTHCHECK` if one is set; Google Cloud cannot run one), never that it is doing its work, and with no Domain it can have no HTTP Uptime check and no Error rate. A `web` that has no Domain is still a `web`, not a Worker, and nothing turns one into the other except a kind change, which replaces the Service.
_Avoid_: Background job, job, daemon, worker pool (GCP's resource for it), web with no Domain

**Private web service**:
A Service, written `kind: web-private` in the Project config, that answers HTTP on its `port` only to other Services, never from outside: it holds a `web`'s fields with `port` required, and it can never have a Domain, a published port, an uptime check or a preview. Private means by network alone, with no token asked of a caller: on a Server, reachable by any Service on that Server, every Project's included; in a Cloud account, only by the Services of its own Environment. Another Service finds it through the variable it names for it, whose value is the Private web service's **internal address**: a base URL (`scheme://host[:port]`, no path) to be used whole, whose scheme, host and port differ by target. In an AWS Cloud account it is `http://<Config name>.cloudgate.internal:<port>`, the name its tasks are listed under, each healthy one, in its Environment network's private DNS namespace. In a Google Cloud project it is the Cloud Run service's own `https://…run.app` address, which only callers in its Environment network reach.
_Avoid_: web-private (the kind's spelling, not the name), internal service, private app

**AI model**:
An Application that serves one model through an inference runtime, reached through the gateway. It is an Application in every respect — its deploys, Deployments, Domains, entitlement and statements are an Application's — and is one from create for life: a plain Application never becomes an AI model, and an AI model never stops being one. "Model" on its own names *which* model it serves (e.g. `smollm2:135m`), never the Application. The one carve-out from "an Application in every respect": an AI model has no Domains and no published ports, and no other Service can reach it on the network, so the gateway is the only way in. An Agent may deploy, start, stop and read an AI model like any Application, but only a person creates or deletes one, and an Agent calls one only through the gateway, never through `/mcp`. Its audit trail is an Application's, with no kind of its own, and a call through the gateway is recorded once, as Token spend, never in the audit trail. Because it can have no Uptime check, the one thing that tells anyone it is down is the gateway: when it is meant to be running and the gateway cannot reach it, its Organization hears once that it is not answering, and hears again only after a call has got through; a deliberate Stop, and every refusal that is the caller's own mistake, tells nobody. That is an episode, not an **Incident**, and keeps no history.
_Avoid_: Model (for the Application), AI provider (that is Cloudgate's own AI settings, which may point at an AI model but are not one), model service, LLM, inference server, endpoint (that is its URL)

**Inference runtime**:
The server software an AI model runs to serve its model: one of a closed list the platform knows how to configure (Ollama, vLLM, llama.cpp), chosen at create and fixed for the AI model's life. Which model it serves can change; which runtime serves it cannot.
_Avoid_: Runtime alone (that is Docker's container runtime, as in the nvidia runtime GPU setup installs), engine, backend, inference server

**Gateway**:
The one place every call to an AI model enters: part of Cloudgate itself, not a Service, fronting every AI model on every Server. It forwards only the OpenAI-compatible calls, holds each call to the model its AI model serves, and records one usage row per call. Anything that reaches an AI model without passing through it is unmetered.
_Avoid_: Proxy, LLM gateway (that is a template component a user may deploy), router, endpoint (that is an AI model's URL on the gateway)

**Token spend**:
The tokens an AI model's calls consumed, counted at the gateway and belonging to the AI model: it adds up to the model's own Project and Environment, never the caller's, and is broken down by the Agent that called. An Application in another Project that calls the model spends the model's Project's tokens. Whoever can read the AI model can read its token spend, so an Environment's or Project's token spend is the sum over the AI models the reader can read, and two readers may see different totals. A call refused before the caller is known spends nothing and leaves no trace. Token spend outlives the Agent that called and goes with the AI model when it is deleted. It is read by UTC day and no finer: each call is kept 90 days, and after that only its day's totals by Agent and model served remain, for the AI model's life.
_Avoid_: Cost, bill, usage (for the total, since a usage row is one call), quota

**AI provider**:
An Organization's setting for Cloudgate's own AI features: a URL, a key and a model. It may point at an AI model through the gateway, and then it is one more caller: its key is an Agent key, and its calls are that Agent's token spend. The platform doesn't know it points at an AI model, so suspending or removing that Agent, or deleting the AI model, leaves it in place and its next call is refused.
_Avoid_: AI settings (that is the page), provider on its own

**Deployment**:
One row of the `deployment` table: a single attempt at one thing, with its own log, status and timings. Two of its eight parents make it a **Build deployment** — one attempt to build and release a specific Application (or compose stack) version — three make it a **Run record**, two make it a **Cloud run** of something that builds nothing (an **Environment network**, a database in a Cloud account), and the eighth is the **Parentless deployment**. The one exception is a run of a **Cron service**: it hangs off the Service like a build but is a Run record (ADR-0034). A queued Build deployment is still there after Cloudgate restarts; one cut off part-way by a restart is never started again by itself, and ends as an error saying so, as a **Cloud run** does. Deployments are records; what a Deployment is *about* is whichever parent it hangs off, never the row itself. This entry used to state the build sense alone, which excluded `backupId`, `volumeBackupId` and `scheduleId` — three of the parents `deployment_at_most_one_parent` counts, each of which both console feeds title a row under and `ownerOf` answers a `type` for.
_Avoid_: Release; build on its own (build is a *phase* — the record is a Build deployment); "deployment" for the container that ends up running

**Deployment parent**:
Which of eight kinds a Deployment hangs off, said by the writer as a tag rather than left for a reader to infer from which of seven nullable foreign keys is non-null: `application`, `compose`, `schedule`, `volumeBackup`, `backup`, `postgres`, `environmentNetwork`, or `none` (`DeploymentParent`, ADR-0017). The **Environment network** is the parent of a Cloud run that touches the network alone: its create, made first by an Apply before any Service in it, and its removal, by the Environment's Delete once no cloud Service is left or by applying a plan that finds nothing there any more. A `postgres` is the parent of its own Cloud run when it lives in a Cloud account, since a database builds nothing. At most one is ever set, and the read side ranks the seven in one order — application, compose, schedule, volumeBackup, backup, postgres, environmentNetwork — which decides both what a feed row is titled and which Service it is listed under; a network's run is listed under no Service, and is titled by the network's region.
_Avoid_: Owner for the write side (`ownerOf` and `DeploymentOwnerType` are the read side's word for the same seven kinds, and have no name for the parentless one); service (four of the seven are not one)

**Run record**:
A Deployment whose parent is a Backup, a VolumeBackup or a Schedule, or one that is a run of a **Cron service**, hanging off that Service marked as a run rather than a build — one run of something scheduled or fired by hand, not a build of a version. It carries the same log, status and console feed row as a Build deployment, and it is written by `BackupRunRecorderService.start` rather than by the engine, whose `create` takes only the two buildable parents because it names a log directory after the owning Service's `appName`.
_Avoid_: Deployment on its own where the build sense is meant; job, task, execution

**Parentless deployment**:
A Deployment with none of its five parents set. The table permits it (`num_nonnulls(…) <= 1`, not an XOR) and `DeploymentParent`'s `none` arm names it, and nothing writes one today — it is a shape a *reader* has to answer for rather than an orphan to clean up: `ownerOf` raises not found, and reading its log is therefore a 404 — which is the half `test/deployments/run-history.e2e-spec.ts` inserts one by hand to pin, asserting the status and the message `GET /deployments/:id/logs` answers with. `ownerOf`'s own raise is pinned only through that read, never directly.
_Avoid_: Orphan, corrupt row (it is a shape the type names and the read side handles)

**Rollback**:
Putting a Service back onto what an earlier Deployment produced. Its rollback points exist only while rollbacks are turned on for the Service, one per Deployment, each kept until someone removes it. What comes back depends on where the Service runs: on a Server, that Deployment's image and its settings, at once and with no Deployment of its own; for a `static` site on AWS, that Deployment's files only, never the distribution's settings, which stay what the Project config says, and the switch runs as a Deployment of the Service with its own log; on Google Cloud the same, except that it copies that Deployment's kept files into the site's one live folder and clears the cache, with no run of the **Environment network**, since the network's rules always point at that folder.
_Avoid_: Revert, undo

**Preview deployment**:
A copy of one git-sourced Application built from a branch and run beside it under its own `appName` and host, sharing its parent's storage (ADR-0021). What made it is its **trigger**, and there are two: a pull request or a request. It is not a Service and not a Deployment, and not a Deployment parent: its builds are Deployments of its parent Application, each naming the Preview deployment it built, so they stay in the parent's history after the preview is gone. An Application in a Cloud account has none, of either trigger: it has no Server for a copy to run beside, so one would run on the platform host, and both triggers are refused for it (ADR-0053).
_Avoid_: Preview environment, ephemeral environment (it copies one Application, never an Environment's set of Services); preview on its own where the kind matters

**Pull-request preview**:
A Preview deployment whose trigger is a pull request: opened by the pull request, one per pull request, gone when it closes. GitHub-sourced Applications only.
_Avoid_: PR deployment

**Requested preview**:
A Preview deployment whose trigger is a request: asked for by a caller, its **requester**, rather than opened by a pull request, and gone at its **expiry**. The expiry is a time the request chose within the instance's maximum, moved later only by an explicit extend — never by a redeploy or a read — and once it passes the preview is **expired**: nothing more is built into it, and it stays visible as expired until its running copy is really gone. Deleting one is expiring it now. Identified by itself alone, so two may build the same branch. Its requester is who asked for it, not who may reach it: reach to any Preview deployment is the caller's grant on its parent. Asking for one is deploying its parent from a branch of the parent's own repository, so whoever may deploy the parent may ask, person or agent alike — but only of an Application whose operator allows requested previews, since one runs a branch against its parent's storage and environment. An Application holds at most as many at once as its operator allows, counted apart from its pull-request previews so that neither kind crowds out the other, and an expired one still counts until its running copy is gone.
_Avoid_: Task deployment, agent deployment, sandbox (a task is Swarm's word, and a Deployment is one build)

**Uptime check**:
A Service's standing instruction to make one request from outside it on an interval and record a verdict of up or down. The owning Service is what grants entitlement to it, and the Service's Delete takes it away. It is aimed only at that Service's own targets: an HTTP check at one of its Domains, a TCP check at one of its published ports. A Database has no Domain, so it can have only a TCP check, and only once it has an external port. Every check is probed from the platform host, the one vantage point Cloudgate owns, so up means the platform host can reach it, not that the internet can: an HTTP check resolves the Domain as any client would, and a TCP check dials the port on its Server's address. A port that is not published cannot be checked. A Server that cannot be reached makes its checks down, never unknown. It never probes a free URL. A check aimed at a Domain goes wherever that Domain is edited to point, and is deleted when the Domain is. A check aimed at a port holds the number, not what publishes it: when its Service stops publishing that port — the Application's port row is edited or removed, the Compose file no longer publishes it, or the database's external port changes or is withdrawn — Cloudgate turns the check off, says why on the check, and never dials it again until the operator aims it at a published port and turns it back on. It is never retargeted to a different port, because nothing says which port replaced it. A Stop or Remove containers leaves it in place. A keyword required in the body is part of an HTTP check, not a separate kind. An uptime check is Cloudgate probing from outside and does not read the container's own `HEALTHCHECK`, which exists only so Swarm, or ECS for an always-running Service in a Cloud account, knows when to replace a task. Adding, editing, turning off and deleting one rewrites the Service's definition, so it takes `service: ['update']`, and reading it, its probes and its Incidents is reading the Service, `service: ['read']`, never `monitoring: ['read']`, which is a Server's own metrics. So an Agent can read a check but never configure one, and nobody reads one on a Service they are not entitled to.
_Avoid_: Health check (that is the container's Swarm `HEALTHCHECK`), monitor, probe (that is one execution of the check)

**Incident**:
The stretch during which one **Uptime check** is held to be down, or one **Error-rate threshold** is held to be breached, kept as a record of its own so that someone hears about it once. It belongs to exactly one of the two, and each has at most one open Incident. A check's opens after its operator-set number of consecutive down probes, 3 by default, and closes on the first up probe. A threshold's opens on the first evaluation whose window breaches and closes on the first whose window is judged and below the threshold; a window too quiet to judge neither opens nor closes it. A Stop of the owning Service, or turning the check or threshold off, closes an open one and says so, and neither probing nor judging happens while the Service is Stopped or the rule is off, so a deliberate Stop never opens one. Editing the rule while an Incident is open does not close it: the next judgement uses the new rule. A deploy in flight gets no exemption. A stretch in which nothing was probed, as while the backend is down, is neither up nor down: it neither opens nor closes an Incident, and one that spans it stays one. Every check that fails in the same moment opens its own Incident, even when the cause is shared. There is no flap detection and no maintenance window; the consecutive-failure count and the window are the only damping. Probes and error-rate samples are kept for a week and the Incident itself for the life of its check or threshold. Each Incident is announced to its Organization's channels exactly twice, once when it opens and once when it closes, and the close says why, whether it recovered, was Stopped, was turned off, or lost its port; one whose check, threshold or Service is Deleted goes with it and announces nothing.
_Avoid_: Outage (the platform host's view is not the internet's), episode (the in-memory "already told" mark for a rate-limited Agent, a stuck teardown or an AI model not answering, which keeps no history), alert (that is the Notification), downtime, breach (for the record; a breach is the condition an Incident is held open by)

**Error rate**:
The share of a Service's requests that its Server's Traefik answered with a 5xx, over a window, needing nothing from the app. It is counted per Domain and summed over the Service's Domains, so an Application without a Domain and every Database have none, and the console says so rather than showing zero. A request that matches no Domain belongs to no Service. A 5xx that Traefik answers itself, as when the containers are down, counts. It is read from Traefik's own request counts, not from the access log, on the platform host as on any Server, so reading it is never a read of the platform host's access log. A Server whose Traefik has not been switched to keep those counts, which takes a Traefik restart the operator asks for, has no error rate for its Services until it does.
_Avoid_: Error tracking (that is exception capture, which this is not), 5xx count (a count without its denominator is not a rate)

**Error-rate threshold**:
A Service's standing condition on its **Error rate**: a percentage, 5 % by default, over a trailing window of 1, 5, 15 or 30 minutes, 5 by default, judged only when the window holds at least a minimum number of requests, 20 by default. A Service has at most one, added by the operator, never created for it, and it is judged on the rate summed over the Service's Domains. A breach opens an **Incident**, the same record a failing **Uptime check** opens, holding the rate and request count that opened it and the worst rate while it was open. A window below the minimum is quiet, neither breaching nor clear, so a Service nobody is calling neither pages nor recovers. A Database, which can never have an Error rate, cannot have one; a Service that has no Error rate yet can, and it reads as not available until it does. The share of slow requests is shown beside the Error rate but never opens an Incident. It is configured and read under the same statements as an Uptime check, and so is the Error rate itself. Switching a Server's Traefik to keep request counts is a Traefik restart, and takes the authority any Traefik restart on that Server does.
_Avoid_: Error-rate alert (an alert is the Notification), error-rate check (a check makes a request; this makes none), rule

**Server threshold**:
A Server's CPU or memory percentage, set per Server and for the platform host, that a collected sample is compared against; 0 means off. A breach is held per Server and per metric: it opens on the first sample above the threshold and closes on the first sample at or under it, and it is announced exactly twice, once when it opens and once when it closes, the close saying whether it recovered or was turned off. Setting the threshold to 0 while breached closes it; raising it does not, the next sample decides. A stretch with no samples neither opens nor closes one, and the breach is stored, so a restart of the backend does not announce it again. It is not an **Incident**, which belongs only to a Service's Uptime check or Error-rate threshold, and it keeps no history. A Server deleted while breached announces nothing.
_Avoid_: Server incident (an Incident is a Service's), server alert (an alert is the Notification)

**Trace store**:
The place one Service's traces are kept and read, belonging to that Service alone and running on the same Server as it. Only an Application or a Compose can have one, never a Database or a Preview deployment, and only when its operator turns traces on; a Compose's inner services share its one store. The platform gives the Service where to send and a credential of its own when it next deploys, and what lands in the store is what that credential sent, so one Service's spans never land in another's store. An app that sends nothing has an empty store: the platform never instruments code. Traces are kept for 1, 3 or 7 days, 3 by default, and a change applies only to traces sent after it. The store is not a Service: it appears in no Project and is reached only through the console, which reads it as reading the Service, `service: ['read']`, while turning it on or off or changing how long it keeps traces takes `service: ['update']`. What the store serves is not trusted, since its Server may be the customer's: the console shows it sandboxed, where it never has the viewer's session, and its requests are let through by a short-lived link minted for that viewer and re-checked on each request (ADR-0075). An Agent reads no traces. A Stop leaves it running, so a Service that is down can still be read; turning traces off, a Delete, or moving the Service to another Server removes it and its traces from the machine that held them, and traces never follow the Service to a new Server (no operation moves a Service yet).
_Avoid_: Collector (that is only the part that receives), tracing Service (it is not a Service), sidecar, Jaeger (that is what runs it today)

**Server**:
A machine (local or remote over SSH) that workloads are deployed onto. Remote servers are reached exclusively through the remote-execution layer.
_Avoid_: Host, node, machine

**Maintenance**:
A Server's state while its operator works on it: nothing new starts a Service's containers on it, as its run Server or its build Server. Every deploy, redeploy, rebuild, rollback, Start, restart (a Compose restart, an Application reload, a container's start or restart) and a Cron service's Run now is refused, and queued builds for it are refused when picked up. What is already running carries on, and so do scheduled Cron service runs, backups and Uptime checks, and Cloudgate's own setup on it (Server setup, monitoring setup, Traefik reload), which are the operator's maintenance tools. An Owner or Admin starts and ends it.
_Avoid_: Pause, paused, on hold, inactive Server, disabled

**Host key**:
SSH's own name for the key a **Server** presents when Cloudgate connects to it, which says which machine answered. It is the Server's, never Cloudgate's: the **SSH key** a Server uses is the one Cloudgate signs in with. Cloudgate records its fingerprint (`SHA256:…`, as `ssh-keygen -lf` prints it) on the first connect and refuses any later connect that presents another, until an operator forgets it, after a reinstall or by changing the Server's address (ADR-0074).
_Avoid_: Server key, server fingerprint, known host

**Setup run**:
One running of a Server's setup on its machine. It belongs to the Server, not to whoever watches it. It starts only when an operator confirms *Run setup*, or, for a **Bought Server**, by itself once its machine answers after **Buy** (run once more by itself if a restart cut it off), never because its log was opened, reopened, docked or reconnected, and once started it cannot be stopped. Watching or closing its log never changes it, and how it ended is kept on the Server.
_Avoid_: Provisioning (as a noun), setup socket, setup log (that is what shows it)

**Build host**:
The machine an Application's *build* happens on, and therefore the machine every artifact a build leaves behind lives on — the source tree's `code` half under `applicationsDirectoryOn(buildHostServerId)`, the `${appName}` images, the buildkit cache. It is `buildServerId || serverId`, stated once in `buildHostServerId` (`deployment-engine/build-host.ts`) and asked rather than re-derived (ADR-0018). A `null` `buildServerId` means *no dedicated build Server*, so the build ran wherever the Service runs and the answer falls through to the **run Server** — `application.serverId`, where the converge, the Swarm service, the presence probe, the Traefik dynamic config and that same tree's `files` half (`fileMountsDirectoryOnRunServer`) all belong. So `{root}/applications/{appName}` is one path spanning two machines. The two answers coincide on the default single-Server install, which is the whole mechanism of the defect ADR-0018 is about: every call site that reached for the run Server when it meant the build host was green in every test that exercised it, because `rm -rf` reads the same whichever machine it is sent to. So a write, a read or a reclaim says which of the two it means, and a Delete reaching two machines for one Service is the shape of the thing rather than a misconfiguration.
_Avoid_: Build server for the answer (`buildServerId` is one of the two *inputs* and is null on most installs, so it is not the name of the machine); build machine, builder; Server on its own where the run/build distinction is what is at stake. The Server entry's _Avoid_ on **host** still holds for a bare synonym — *build host* and *platform host* are compounds naming the **role** a machine plays in one operation, which is what `buildHostServerId` says by ending in `ServerId`: the answer is always some Server.

**Member**:
A user's participation in one organization, carrying a role and the set of projects, environments and services they may reach. Distinct from a user, which is the account itself.
_Avoid_: User, account, collaborator

**Agent**:
A member that is not a person: bound to one organization for life, holding only an agent role, and outliving whoever created it. An agent role is never held by a person, so the role an audit entry records says whether its actor was a person or an agent. An entry written with no caller, as when an expired **Requested preview** is torn down, names the platform as its actor, never the agent the thing belonged to. An agent never holds owner or admin, and never carries the authority over the **platform host** that the instance organization's owners and admins do. An agent can be suspended: every one of its keys is refused while it keeps its keys and its grant, until it is resumed. Suspending is how an operator stops an agent now and decides later; removing it is final.
_Avoid_: Bot, service account, integration

**Personal key**:
A credential that acts as the person who minted it, with everything they can do. It carries no boundary of its own: it acts in whichever of the person's Organizations a request names, and in their default one when none is named. One is minted by hand in the console, or by `cloudgate login` when the person approves it in the browser; either kind works in CI. The MCP endpoint and the gateway both refuse it.
_Avoid_: API key, token, personal access token

**Agent key**:
One of an agent's credentials. Every agent key reads the agent's one grant, and it is valid only at the MCP endpoint and the gateway. What a key can do at each is its agent's role, never the key: a caller agent can call the AI models in its grant and does nothing at the MCP endpoint.
_Avoid_: Agent credential, API key

**Instance**:
One running Cloudgate, named by its address (`https://cloudgate.octabyte.app`, or a self-hoster's own): what the Cloudgate CLI logs in to and talks to. An Instance runs on its **platform host** and deploys onto its **Servers**; it is never one of them. The CLI can be logged in to several Instances at once, as one person on each.
_Avoid_: Server (that is a machine workloads run on), host, site

**Hosted instance**:
The one Instance Octabyte runs and sells, where every customer is an Organization paying through a Stripe plan. Its platform host only manages: customers' Services run and build on their own Servers and Cloud accounts, and nothing a customer asks for runs there, not even a connection test. The Instance organization still manages the box and has no Services on it (ADR-0053). It is the same code as a Self-hosted instance with hosted mode on.
_Avoid_: Cloud version, SaaS, managed instance, tenant

**Hosted mode**:
The one setting that makes an Instance the Hosted instance. The Instance remembers which mode it first started in and refuses to start in the other, so hosted mode is never half on or lost by a redeploy (ADR-0049).
_Avoid_: Cloud mode, IS_CLOUD

**Self-hosted instance**:
An Instance a customer installs and runs on their own machine, unlocking paid features with an **Enterprise license**.
_Avoid_: On-prem, community edition

**Cloudgate version**:
One tested version of Cloudgate itself, `vX.Y.Z`, published as a prebuilt tarball on the GitHub Release for its tag once its E2E run is green. It is the only thing the install puts on a platform host: a Self-hosted instance and the Hosted instance both install and upgrade to a Cloudgate version, never a branch (ADR-0082).
_Avoid_: Release on its own (that word is avoided for a Deployment), build, image, checkout

**Hosted plan**:
One of the two plans a self-serve Organization buys on the Hosted instance, **Starter** or **Business**, paid monthly: 3 Servers and 3 **Cloud Environments**, raised together by **Add-ons**. Members, Projects, Environments on Servers and Cloud accounts are never counted. An Organization buys one, or starts its **Free trial**, before adding its first Server or its first Cloud Environment. When a count is full, adding one more is refused and nothing already running is stopped. Moving up to Business takes effect at once and is charged today, prorated; moving down to Starter takes effect at the end of the paid month and can be taken back until then. A person owns at most one Organization that pays for itself; on Business or Enterprise it can also pay for **Attached Organizations**, which share its counts (ADR-0048, ADR-0054, ADR-0059).
_Avoid_: Tier, Pro, Professional, hobby, startup, legacy (the plans it replaced), subscription (Stripe's record of paying for it)

**Starter**:
The 15 USD **Hosted plan**: the counts and **Add-ons** only, without the paid features. An Organization that moves down to it, or to no plan, keeps every paid-feature setting, and those settings stop working without locking anyone out: SSO sign-in stops ("Forgot password" lets an SSO-only person in), SCIM refuses adds but still removes, a custom role grants nothing, and forward auth keeps protecting what it protects but refuses new setups and edits. A Starter Organization pays for itself only, never for **Attached Organizations**, so moving down to it is refused while any are attached (ADR-0054, ADR-0059).
_Avoid_: Basic, free, the Hosted plan (there are two)

**Business**:
The 35 USD **Hosted plan**: the same counts and Add-ons as **Starter**, plus the paid features SSO, SCIM, custom roles and forward auth, and the right to pay for any number of **Attached Organizations** that share its one pool of counts. On the Hosted instance **Enterprise** always counts as Business (ADR-0054, ADR-0059).
_Avoid_: Pro, Professional, Enterprise (that is a custom deal)

**Free trial**:
The first 30 days of a **Hosted plan**, through Stripe's own subscription trial: a card is needed to start it, it counts as paid for that plan's counts, Add-ons cost nothing until it ends, and Starter and Business can be switched both ways at once while the clock keeps running. An Organization gets one only if it has never held a subscription or been Enterprise, the person starting it has never had one by their email, and the card has never had one; the Instance keeps the emails and card fingerprints in a trial history that outlives the Organization. Anyone not eligible subscribes in the same Checkout and pays today. Ending it with no card, or by a cancel, is a lapse with no charge (ADR-0054). A **Bought Server** is never free during it: it is charged at once, up to the trial's end (ADR-0071).
_Avoid_: Free plan, free tier, trial key (that is a Self-hosted **Enterprise license** given for 30 days by hand)

**Add-on**:
One more Server and one more Cloud Environment on top of either Hosted plan, 5 USD on both, always sold together. An Organization can never hold fewer than it already uses.
_Avoid_: Extra server, seat

**Bought Server**:
A Server an Organization on the Hosted instance buys from Cloudgate. Octabyte owns the machine and pays its provider, and the Organization pays Octabyte monthly in advance on its one Hosted plan invoice. It counts as a Server, has no trial, and is deleted with its data and backups once it stops being paid for. The provider is never named to the customer (ADR-0071). It shows one stage at a time: Waiting for payment, Creating, Setting up, Ready, Changing, Deleting, Deleted, or Failed (paid but never made, so refunded). Nothing can be deployed to it until it is Ready. A deletion date set by a failed payment, a suspension or a coming lapse is a warning on a Ready server, not a stage; while it shows, nothing that costs more can be bought. Deleted for non-payment, its record stays, marked Deleted, with its Services still listed.
_Avoid_: VPS, purchased server, managed server, Hetzner server; Server alone where the difference from a customer's own machine matters

**Server markup**:
The percentage an Operator sets that Cloudgate adds to the provider's cost to price a **Bought Server**, its backups and its extra storage. It is never shown to customers (ADR-0071).
_Avoid_: Margin, commission, fee

**Cloud Environment**:
An Environment that uses a cloud: its Deploy target is a Cloud account, or it still has a Service in one. It counts once against the Hosted plan however many Cloud accounts or regions it uses, and stops counting only when it has nothing in a cloud and its target is not one, or is deleted. Connecting a Cloud account counts nothing.
_Avoid_: Cloud slot, cloud account (connecting one is free), cloud environment as a count of Cloud accounts

**Enterprise**:
An Organization on the Hosted instance billed by agreement outside Stripe, with its Server and Cloud Environment counts set by an **Operator**. It always counts as **Business**, so it has the paid features: SSO, SCIM, custom roles and forward auth. It never holds a Stripe subscription at the same time, and turning it off is a lapse, like a subscription ending. Settings that reach the whole Instance, such as white-labelling, are Octabyte's and never sold (ADR-0050, ADR-0054).
_Avoid_: Enterprise license (that is the Self-hosted instance's key), enterprise cloud

**Paying Organization**:
An Organization on the Hosted instance on **Business** or **Enterprise**, not attached itself, that pays for one or more **Attached Organizations**. It alone manages the plan; they all share its one pool of Server and Cloud Environment counts, and freeze and lapse with it. It cannot be deleted, or moved down to **Starter**, while any Organization is attached to it (ADR-0059).
_Avoid_: Parent organization, billing organization, account

**Attached Organization**:
An Organization on the Hosted instance whose plan is its **Paying Organization**'s, made new by an owner or admin there, who becomes its owner; it has its own members and never a plan or Attached Organizations of its own. It stops being attached when its owner starts paying for it themselves, or when the Paying Organization stops paying for it, which is a lapse. A person owns any number of these, but at most one Organization that is not attached. Having been attached counts as having held a plan, so it never gets a **Free trial** (ADR-0059).
_Avoid_: Child organization, sub-organization, extra organization

**Enterprise license**:
The key that unlocks all seven licensed features on a **Self-hosted instance**: SSO, SCIM, custom roles, forward auth, white-labelling, parallel builds and cloud runs, and more than one Organization. Only the **Instance organization's** license counts for creating Organizations; without it the instance may hold one. Octabyte agrees its price and billing period with each customer, invoices it through Stripe by hand, and issues it on the license server with a `validUntil` 14 days after the paid period ends; renewal keeps the same key with a later date. Past `validUntil` its settings are kept and the features stop, as on **Starter**; for Organizations that means none are removed and new ones are refused with `ORGANIZATION_LIMIT` (ADR-0054, ADR-0059).
_Avoid_: Enterprise (that is a Hosted Organization's deal), subscription, Business

**Proven domain**:
An email domain an Organization has shown it owns with a DNS record, on the Hosted instance. Only a proven domain routes sign-ins to that Organization's SSO provider, and an SSO sign-in is accepted only for an email in one of them; a domain merely listed on a provider proves nothing (ADR-0051).
_Avoid_: Claimed domain, verified domain (that reads as email confirmation), SSO domain

**Trusted origin**:
An origin an Organization's owner or admin adds on the SSO page, so the SSO plugin may fetch an identity provider there and a browser may call `/api/auth` from it. On a Self-hosted instance every Organization's list counts on every request. On the Hosted instance the Instance organization's list counts everywhere, and a customer's only on its own SSO requests, and a customer's must be a public address (ADR-0076).
_Avoid_: Allowed origin, whitelisted origin

**Operator**:
An owner or admin of the Instance organization, a person and never an Agent, acting on another Organization on the Hosted instance. An Operator sees only an Organization's account facts, never what is inside its Projects, and can suspend it, lift a suspension, and set it Enterprise with its counts (refused while a Stripe subscription can still charge; turning it off is a lapse). It reads each Organization's plan (Starter, Business, Enterprise or None), its state and whether its **Free trial** is used, and never extends a trial, grants one or clears trial history. Every such act is in that Organization's own audit log. An **Attached Organization** reads "Paid by" its **Paying Organization** and can never be set Enterprise while attached; an Operator never attaches, detaches or re-points an Organization, and suspends one Organization at a time. An Operator never signs in as a customer; support inside a customer's Projects means being invited as a member (ADR-0050, ADR-0059).
_Avoid_: Super admin, staff, support user, admin (that is an Organization role)

**Frozen Organization**:
An Organization on the Hosted instance for which Cloudgate does no new work and touches nothing already running. It is frozen for one or both of two causes, each recorded on its own and lifted only by its own trigger: **lapsed**, when its plan is gone (Stripe stopped retrying a failed payment, a cancel reached the end of the paid month or of a **Free trial**, or an Operator turned Enterprise off), lifted by paying again; and **suspended**, by an Operator with a reason the customer sees, lifted only by an Operator. It stays frozen until every cause is lifted, so a payment never lifts a suspension. While frozen, no deploy, Cron service run, backup, Uptime check, Server threshold, cleanup or cloud run starts, and work already started finishes; its Services keep running on its own Servers and in its own clouds, and the Gateway keeps forwarding their AI calls. Its members can still sign in, see everything, pay, download configs and remove things (Delete a Service, an Environment or a Server, disconnect a Cloud account), and nothing else. A lapsed Organization that is not suspended is deleted 30 days after it lapsed; a suspension stops that clock, and an Operator never deletes one (ADR-0052). An **Attached Organization** is also lapsed while its **Paying Organization** is, read through the link and lifted when it pays again, and is deleted together with it on day 30, suspended or not; the Paying Organization's suspension never reaches it (ADR-0059). **Bought Servers** are the exception to "touches nothing": they are deleted when the Organization lapses, and 7 days after a suspension or a failed payment for them (ADR-0071).
_Avoid_: Stopped (that is a Service's Stop), inactive Server, deactivated, suspended or lapsed for the state as a whole (each names one cause), past due (Stripe still retrying, which freezes nothing)

**Folder link**:
A local folder's record of where the Cloudgate CLI deploys it: one **Instance**, and on it one Organization, one Project, a default Environment and one Service named by its **Config name**, so the same link reaches that Service's entry in any other Environment of the Project. It is the person's, kept beside the code and never committed, and it is never part of the **Project config**, which says what a Project runs and not where a folder goes. A link made against one Instance is refused against another. A link names one Service, or names none and makes the folder a **Project folder**; a folder inside it may hold a link of its own, and the nearest one wins. Where there is no link, as in CI, the same four are given each time.
_Avoid_: Project link (a Project is not what it names), binding, context, linked project

**Project folder**:
A folder linked to a whole Project rather than one Service, usually a monorepo's root. It holds a working copy of the Project's **Project config**, downloaded by `cloudgate link` and sent back as a plan by `cloudgate deploy`, which is refused when the config changed in Cloudgate since the download (ADR-0080). The config stays kept in Cloudgate; the working copy is never a place it is kept and Cloudgate never works from it. A deploy there uploads the whole folder to every app whose config entry names a subfolder of it as its source, and each builds from that subfolder; apps from a repository or an image are left alone. Only a Project whose config is kept in Cloudgate can have one, and the working copy is never committed.
_Avoid_: Monorepo link, workspace, local config (for the record, which is Cloudgate's)

**Config version**:
A counter on a Project's **Project config** that every Apply (a console Save is one) and every stored change of its text moves; storing the text it already holds moves nothing. A whole-YAML edit may name the version it started from, and is refused when the config has moved on since, so a **Project folder**'s working copy never undoes a teammate's change (ADR-0080). It counts changes to one Project's config, never the config format's own `version:` line.
_Avoid_: Revision, etag, config format version (that is the `version:` line)

**Deployment log**:
The append-only file one deployment writes on whichever server ran it. It is addressed by its deployment, never by a path a caller supplies. It is Cloudgate's account of the attempt, never the app's own output: a cloud deploy whose new copy fails to start adds the cloud's reason and that copy's last lines before it ends as an error, and a deploy that works quotes nothing from the app.
_Avoid_: Build log, log file

**Runtime log**:
What a running Service itself writes, read in its log tab with `service: ['read']`. On a Server or the platform host it is Docker's output for the Service's containers, every running copy merged by time and each line naming its copy; in a Cloud account it is the cloud's log store, one per Service, which Cloudgate makes and marks itself, keeps for 90 days like a Deployment log, reads on the Service's behalf so the cloud's login never reaches the browser, and follows a few seconds behind, every running copy merged by time and each line naming its copy. It goes with the Service's Delete. On Google Cloud it is the exception: Cloudgate makes no log store there but reads the project's own, filtered to the Service, kept as long as the project keeps it (30 days unless its owner changed that), and left to expire after a Delete rather than removed. It holds the app's own output and Cloud Run's messages about the Service, marked as such, never a line per request, and its reads share the project's small fixed allowance, so it may fall further behind and say so.
_Avoid_: Deployment log (that is Cloudgate's record of one attempt), CloudWatch log (the AWS form it takes), container log

**Access log**:
The line per request that a Server's Traefik writes for every request it answers: the visitor's IP, the method, the path with its query, the status, the timing and the User-Agent, and no other request header. Each line belongs to the Service whose Domain it matched, or to none. Reading a Server's access log is reading its Services: a person sees only the lines of the Services they hold `service: ['read']` on, and the lines that matched no Service only with `server: ['read']`; `monitoring: ['read']`, which is a Server's own metrics, never reaches it. Query values are shown hidden and their names kept. Members of a **Frozen Organization** still read it. An **Operator** never reads a customer's, and no **Agent** reads one at all. The platform host's access log is one file holding every Organization's traffic, and it is read the same way, as its Services, with one difference: a line that matched no Domain, or whose host more than one Organization holds there, is read only with the Instance organization's authority (ADR-0061). Its query values are hidden for every reader, the Instance organization's authority included. An access log is never where the **Error rate** comes from (ADR-0055).
_Avoid_: Request log, traffic log, Runtime log (that is the app's own output)

**Managed container**:
A container whose Docker labels trace it back to a Service in this instance's database — `com.docker.swarm.service.name`, `com.docker.compose.project` or `com.docker.stack.namespace` carrying an `appName` the Service relation knows, or a preview deployment's `appName` resolving to its parent Application. On the **platform host** the Service must also run there: a label naming a Service on a Server or in a Cloud account is a claim any container on the shared machine could make, so that container is unmanaged there. A swarm *service* is addressed by name rather than by label, and names its Service either outright or through its stack namespace. Reaching one is governed by entitlement to that Service. An **unmanaged** container — anything an operator started by hand — belongs to no Service and is reached through machine-level Docker access instead **on a named Server**, and on the **platform host** through machine-level Docker access *plus* instance authority (ADR-0013): the machine there is the one every organization's services share, it has no `server` row for an organization check to find, and the `docker` statement is an organization capability a licensed custom role can hold — so an owner or admin of any organization reached an operator's own sidecar on it, `cloudgate-monitoring` included by construction. The **listing** asks the same pair: `GET /docker/containers` hides the platform host's unmanaged rows from whoever those two checks would refuse, so the rows it offers are the containers the routes will act on rather than ids they answer "not found or not permitted" for. It decides *unmanaged* the way this entry defines it — the labels a row carries resolved against the Service relation — and not by whether the row carries a label at all: a container an operator started with `docker compose -p my-monitoring up` carries one and belongs to no Service, so the label reading would have kept a row every container route refuses. A **managed** container on the platform host is untouched by either: it has a Service, so entitlement answers it. The exception to all of the above is **the ones this instance runs for itself**: an unmanaged container whose name carries `cloudgate` — `cloudgate-traefik`, `cloudgate-backend` and `cloudgate-console` today, and any other the platform comes to run — is refused on the container routes, the sockets and the swarm routes outright, and is managed through the platform's own surfaces (`/settings/traefik/*`, the runtime probes) instead. The one exception is `cloudgate-monitoring`, which the operator sets up and manages from the console — and on the platform host the operator who manages it is exactly who instance authority admits, so the sentence above costs it nothing. The test is on the name rather than a label, and it is deliberately a rule rather than a list, so a container the platform gains later is refused by default rather than reachable until someone remembers to name it; on the container routes and sockets it is applied only to a target that resolves to no Service, so a member's own Application called `my-cloudgate-thing` carries owner labels and is governed by entitlement like anything else. The swarm routes are the one place it is not so confined: `SwarmService` asks the daemon rather than the database and has no Service resolution to defer to, so a swarm service whose name merely carries `cloudgate` is hidden and refused there. That is a deliberate fail-closed widening rather than an oversight — a second, narrower copy of the test is how the listing and the acting came to disagree in the first place — and the console reaches an Application's tasks through `getServiceContainersByAppName`, which is unaffected.
_Avoid_: Owned container, service container

**Shell tab**:
The tab on an Application, a database or a Compose stack that opens `sh` inside one of the Service's own running containers, found by the Service rather than by picking it out of a Server's Docker listing; Overview's **Open a shell** goes to it. It lists only the containers running on the Service's own machine (its Server, the platform host, or a Compose stack's own **Stack VM**, reached through its cloud's tunnel, ADR-0070) and offers a choice when there is more than one, preselecting the first; a Compose stack's entries name their compose service. Opening a shell takes `service: ['update']` on the Service, because a shell writes inside the workload, and the tab is absent for a role without it and for any other Service in a Cloud account, which has no container to open one in (ADR-0008). Leaving the tab ends the shell and coming back opens a fresh one.
_Avoid_: Console, exec tab, container terminal

**Dock**:
The panel along the bottom of the console, full width under the rail and the page, that holds Docked shells and Docked logs as tabs and keeps them running while the operator moves between pages. It belongs to one sign-in in one Organization: switching Organization or signing out ends everything in it, and a reload brings it back empty.
_Avoid_: Terminal dock (it holds logs too), drawer, bottom panel

**Docked shell**:
A live shell moved into the Dock, or opened there, holding its container or SSH session open until its tab is closed. At most four at once.
_Avoid_: Docked terminal

**Docked log**:
A log moved into the Dock from the page that showed it (a Deployment log, a Runtime log, or a Server's setup run), still following new lines after that page is gone. A log that has already finished can be docked too: its tab holds the lines read when it was docked, shows it as ended, and offers Reload to read the stored record again. It is moved, never copied, and when what writes it finishes it stays as the record until its tab is closed. Losing access to it while docked — or what it shows being deleted — ends it the way a Docked shell ends: "No longer authorized", every line kept, nothing retried. A log is in the Dock at most once: docking it again shows the tab already there. At most four at once, counted apart from Docked shells. Docking it, or its reconnecting, never starts what it shows: a docked **Setup run** is only watched.
_Avoid_: Log tab, pinned log

**Stop**:
Returning a service to zero *running* containers. Whether an exited container remains afterwards is the runtime's business rather than the product's — a swarm service leaves none behind, a compose project of the `docker-compose` type does. A Database on a cloud has no container, so Stop there is the provider's own stop where one exists: an RDS instance is stopped with a warning that AWS starts it again after 7 days and that storage and backups still bill, and Cloudgate records that date rather than stopping it again; an ElastiCache cache cannot be stopped, so Stop and Start are refused with the reason, Delete being the only way to stop paying. A database the Environment uses but did not make is never stopped, started or rebuilt by Cloudgate. A change the plan would make to a stopped instance is blocked until it is started, because Cloudgate never starts a database on its own. A **Cron service**'s Stop is its pause in that Environment: no run fires until Start, and a run in flight is stopped and recorded as stopped. Cancelling one run in flight is cancelling its Run record and leaves the timetable running. A `web` in a Cloud account is stopped by running none of its copies, and started by running its usual number again; a plan never counts that as a change. Stop warns that it lowers the bill without ending it, naming what still costs money (the **Environment network** the Service shares, its stored images and its Runtime log) and that its Domains answer an error until Start. A Deploy starts a stopped Service, on a cloud as on a Server, and Reload, which swaps every running copy for a fresh one of the same version, is refused with the reason while it is stopped. On Cloud Run, Stop switches the service to no copies at all, so it refuses traffic rather than waiting idle, and Start hands it back its usual range of copies; Reload there is a fresh revision of the same version. A Cloud SQL instance is stopped and started with Google's own switch, which Apply leaves alone; Google never starts it again by itself, so Stop records no date and warns only that storage, backups and its private address still bill. A Memorystore cache cannot be stopped, so Stop and Start are refused as for ElastiCache; every other rule for a cloud database is AWS's.
_Avoid_: Pause, halt, shut down

**Remove containers**:
Removing a service's containers outright, leaving its network, project directory, volumes and Cloudgate record intact. The rung between Stop, which may leave exited containers still holding a volume, and Delete, which destroys the service itself; it exists because a volume cannot be restored while any container, running or exited, still references it. A Database offers no such rung, on a Server or a cloud: its actions are Deploy, Start, Stop, Rebuild and Delete, and on a cloud it has no container at all. A **Cron service** offers no such rung either: a run's container is gone once it ends, so Stop already leaves none. Nor does any Service in a Cloud account: a copy that stops leaves nothing behind, so its actions are Deploy, Start, Stop, Reload and Delete.
_Avoid_: Tear down (that is Delete's mechanism), down, reset

**Delete**:
Destroying the service itself — its Cloudgate record, its containers, its network and its project directory — with its volumes destroyed only on request. An AI model's weights are not one of those volumes: they are a cache of what its model name can always fetch again, not the Service's data, so its Delete always reclaims them. A bucket's files are the same as a volume's data, on every target: a bucket that holds any file, old copy or delete marker is kept and named as left behind, and Cloudgate forgets it, unless that one bucket's Delete or Plan destroy asked for its files to go; an empty bucket is deleted, an Environment's Delete never asks, and a `static` site's own bucket, a copy of its build, is always emptied and deleted. On a cloud, a Database's data is kept the same way, as a **final snapshot** taken by the Delete (a final backup on Google Cloud, taken by Cloudgate just before the destroy and kept until it is deleted there), unless that one Delete or Plan destroy asked for its data to go; an Environment's Delete never asks. The snapshot is named once as kept, with what it costs, and Cloudgate never removes it later. In a Cloud account a Delete is a Cloud run that only destroys, recorded as a Deployment like any other, while the Service or Environment reads as deleting. Its report has two lists: what was **kept** on purpose, named once with what it costs and then forgotten, and what was **left** although it should have gone, found by Cloudgate's mark and, for what no mark search can find, by the cloud's own id. A bucket on AWS that holds files is kept there, in its account and region with Cloudgate's mark, and touched no further; one whose emptying stopped partway is left, "partly emptied". A `static` site's own bucket on AWS is emptied by its Delete's own run; if that stops partway, its CloudFront distribution and what else serves it still go, and the bucket is left the same way. Anything left keeps the row as **Delete incomplete**, unlike a Server's Delete, which drops the row and names what it left: it can then only be retried, or forgotten, which drops the row and records the list in the audit log, where it outlives the row (ADR-0038). On Google Cloud, where most things take no label, each thing Cloudgate makes has a fixed name built from Cloudgate's ids, which Google never lets anyone change, and that name is its mark. What Google itself makes for a database there, its private addresses and Cloud SQL's private name zone, carries no mark of Cloudgate's and goes with the instance. A Service's Delete there first takes its Domains off the Environment network and stops if that fails, and its logs stay in the project to expire on their own. A bucket there follows the same keep-or-delete rule, and its key and its own service account always go, even when the bucket is kept for its files, so no live key outlives Cloudgate's memory of it.
_Avoid_: Remove, destroy, tear down

**Volume lock**:
The mutual exclusion held over one Docker volume, named after the volume itself rather than any service that mounts it. Five operations take it — backing the volume up, restoring it, Remove containers on a compose stack whose backup rows name it, an Application Delete asked to remove its volumes, and a Database Delete on a Server asked to delete its data — because each one is only correct while the others are not running. A scheduled backup waits for it; anything answering an HTTP request is refused with a 409 naming the busy volume instead of holding the response open for the length of a tar — except a Delete, which keeps that volume and names it as left behind rather than failing.
_Avoid_: Backup lock (it is not the backup's, and five operations share it), mutex, semaphore

**Authorization lease**:
The renewable grant a WebSocket holds over its own authorization. Every authorized socket takes one at connect and it is renewed on a clock by re-running the same authorization the connection handler ran; a renewal that is refused ends it at once, a renewal that merely fails leaves it standing until it expires. The socket closes when it ends. It exists because a socket is a standing subscription rather than a long-lived request — entitlement is checked for every frame sent, not once at connect — and its duration, not its renewal interval, is the promise: no socket sends a frame more than one lease past the last authorization that actually succeeded.
_Avoid_: Session check (it is the whole entitlement, not the session), heartbeat (that is the keep-alive ping, a different mechanism pointing the other way), token refresh (nothing is refreshed and no token is involved), revalidation poll

**Stack VM**:
The VM Cloudgate makes in a Cloud account and region to run one Compose stack, inside the Environment network, made by the plan that creates the stack and removed by its Delete; for a stack the console creates in a Cloud Environment, which asks for no Server, it is made by the Environment's next plan, sized by the stack's console setting, since no plan creates a console-managed stack itself. It is part of the stack's place, which is the Cloud account and region, and never a Server: nothing else is deployed onto it, and it is reached only through the cloud's own tunnel. Its named volumes live on a disk of its own, which outlives a replaced VM and becomes a final snapshot at Delete unless its data is deleted too. Its Domains are rules on the Environment network's load balancer, and it has no generated host (ADR-0070). A Domain's port is still the port its service listens on in its container; the Deployment publishes that port on the Stack VM at the same number, where the load balancer alone may reach it, so two services' Domains cannot share a port. The load balancer pieces that reach the Stack VM live in the stack's own Infrastructure state.
_Avoid_: Server, host, node, instance, machine

**Pending setup**:
What one Template setup chose, kept encrypted on its Environment until applied: the setup name, its values, the Domain hosts picked, its compose file and config files. Each Apply takes out what it creates; it is also dropped when cancelled, when its plan is dismissed on a Cloudgate-kept config, or after 30 days (ADR-0064, ADR-0065).
_Avoid_: Draft, pending set, staged template

**Setup record**:
The fact, kept on a Project, that some of its Config names came from a Template: the template's id, its catalogue revision, the setup name and those names. It is never a link, so nothing updates from it; a plan holds back its parts in an Environment that has none of them until the template is set up there too (ADR-0065).
_Avoid_: Template link, origin, installation

**Template catalogue**:
The published list of Templates an install offers, read from one address set for the whole install, the official one unless its operator changes or turns it off (ADR-0062). Each published version is fixed once published, and an install reads the newest one it can use.
_Avoid_: Marketplace, blueprint repo, registry (a **Registry** is something else)
