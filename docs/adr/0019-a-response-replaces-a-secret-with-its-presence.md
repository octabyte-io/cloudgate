# A response replaces a secret with its presence, at the depth the secret lived at

ADR 0006 governs a secret **at rest** and deliberately says nothing about what an API response contains — the metrics-config change put that in as many words while encrypting `MetricsConfig.server.token`: at-rest encryption is orthogonal to API exposure, and a column that decrypts on read is *more* exposed to a controller than a plain one, not less. So the exposure half has been decided four separate times by four issues that were looking at the same page — `ssh_key.privateKey`, notification credentials, `webServerSettings.sshPrivateKey` and the metrics agent token on the same row — each arriving at the same answer with no written rule they were instances of. The metrics token is why that is now a problem rather than a tidiness note: it sat *beside* the key already stripped, on a route open to any authenticated member, and it was missed because `stripSshPrivateKey` was named for one column and there was nowhere for a second secret to be declared.

**The rule.** A response that would carry a secret carries, in the secret's place, a boolean saying whether one is set — named `has` + the field it replaced, and **positioned at the depth the field was**, not lifted to the top of the row. `sshPrivateKey` → `hasSshPrivateKey` on the row (until the column, which had no reader, was dropped); `metricsConfig.server.token` → `metricsConfig.server.hasToken` inside the blob. Not the value, and not a masked or truncated value either: a mask is still a disclosure budget and it invites a screen to render the thing, whereas presence is the *only* fact any screen ever read these values for — `configCollects` and `isCollecting` in the console are both "a token is set", and `MonitoringService.registerTarget` returns early without one. Keeping the flag at the secret's own depth is what lets one predicate serve both shapes of a config — a `server` row as `GET /servers` still answers with it, carrying `token`, and every other response carrying that blob, which carries `hasToken` — instead of threading a second argument through every call site.

**Consequences.**

- **The write path has to carry what the read no longer can, and the three cases must stay distinguishable.** Once the console cannot read a token back it cannot re-submit it, so a partial write stops being a convenience and becomes load-bearing: **omitted** keeps the stored value, **`''`** clears it (which is the only way to stop collecting), and **anything else** sets or rotates. That rules out `.default('')` on the field and `||` in the service — `token: input.token ?? current.token` — and it is the same contract `updateSlackSchema.partial()` already carries on the notification channel credentials. The invariant being preserved is the old one: saving a threshold tweak must not rotate a token an operator configured an external agent with.
- **The enumeration is a property over the schema, not a TypeScript type.** `Omit<Row, 'secret'>` *retains* every other key and a sanitizer supplies them through `...rest`, with no excess-property check on a spread of typed keys — so a new secret column compiles and is served, and a docblock claiming otherwise is worse than no docblock. `backend/test/coding-standards/web-server-settings-projection.spec.ts` is the holder for the settings singleton: it derives the requirement from the schema (every encrypted-at-rest column, and every field of a declared blob default whose name matches the credential vocabulary, must be withheld and must have its presence flag at the same depth), asserts no withheld value was merely *relocated* elsewhere in the response, and fails by name. Its completeness argument is `secret-bearing-columns.spec.ts` next door: a secret here must be encrypted at rest (ADR 0006), and everything encrypted must be projected — neither property makes that claim alone. What the types do enforce is worth keeping and is narrower than it looked: a rename or removal of a projected field breaks the build, and no controller can answer with the raw row.
- **The client-side strip stays, as a second line of defence rather than the defence.** `settingsApi.webServer()` deletes both fields at the client boundary and derives each flag from the value *before* dropping it, because a narrowed TypeScript type does not stop TanStack holding whatever the response parsed to — the value would still sit in the query cache and in every devtools panel over it. Deriving is the fallback for a backend that predates the projection only; when the server sends the flag, the server wins. The order matters: derive first, or an older backend reads as "never set up" and the sampling switch silently inverts.
- **This is not an authorization decision and does not substitute for one.** The metrics-token fix left `GET /settings/web-server` open to any authenticated member on purpose — a plain member's Monitoring screen legitimately reads the host's sampling configuration off that row, and every *write* to it already takes instance authority (ADR 0013, H-63). The rule applies whatever the boundary is: a response that a caller is entitled to still does not carry the credential, because entitlement to see a resource is not entitlement to hold the key that authenticates as it.

**Amended: the residue recorded here is closed, and the answer was a second rule rather than this one applied again.** A `server` row's own `metricsConfig.server.token` was still returned whole by the nested `server` on `GET /applications/:id`, `GET /compose/:id` and every database service read, which a base member with one accessed service reaches. The metrics-token fix said correctly that this was *"a different question: what a nested relation on a service read is entitled to include"*, and it is answered in `src/common/service-read-relations.ts`:

> A relation included on a service read carries the related row **minus its secrets**, withheld at the finest granularity that removes the secret and nothing else — the whole column where the column *is* the credential, the field where the column is mostly configuration. Which columns those are is derived from the schema by `test/coding-standards/service-read-relations.spec.ts`, not listed at the call site.

Two things about that are worth keeping distinct from the rule above. First, **a nested relation is not where a secret's presence gets reported.** ADR 0019 governs the route that *owns* the row; a caller authorized for a *Service* is not thereby entitled to facts about a Registry, an SSH key or a Server it merely references — the base `memberRole` holds `registry: []`, `sshKeys: []`, `gitProviders: []` and `server: []` — so a withheld whole column is simply absent, and `GET /registries/:id` and `GET /ssh-keys` are where presence is answered. The flag would have had to be lifted to the top of the nested row, which is the lift this ADR already forbids. `metricsConfig` keeps its `hasToken` precisely because it is *not* a withheld column: the blob is returned and the field is withheld, so there is a depth for the flag to stand at, and one predicate in the console still serves every shape of the config.

Second, **the per-site projection was the defect and not the fix.** Those nine reads already carried hand-written denylists, and the hand was wrong in four places: `customGitSSHKey` was `true` (the whole `ssh_key` row, private half included), `github` withheld two of three and not `webhookSecret`, `gitlab` withheld its tokens and not its OAuth `secret`, and the `server` row was spread whole. That is `stripSshPrivateKey`'s finding at nine times the scale — a list named for the columns somebody happened to think of, with nowhere for the next one to be declared.

Three consequences of this ADR's first application are worth having written down, because each is a claim somebody will otherwise have to re-derive.

- **`POST /monitoring/servers/:serverId/setup` was sanitized rather than argued as a second exception, and the write path is why.** It echoed the raw row, which made `nested-server.ts`'s *"`GET /servers` is the one asymmetry left"* false. On the gate alone the leak is nil: it is `server:create`, which no base member holds, and while `token` was a required field the response only repeated what the caller had put in the body a line earlier — a same-role echo. But that change also gave this route the omitted-means-keep write the first consequence above demands, for the same reason: a *read* now exists that projects the token out, so the console can hold a config it cannot re-submit the credential from, and `toMetricsConfig` already omits the field for exactly that shape. An omitted token turns the echo into a disclosure of a value the caller never supplied — and `CustomRolesService.validatePermissions` accepts `server: ['create']` with no `read`, so that caller can be one `GET /servers/:id` refuses. The two changes are one decision. Its twin `AdminService.setupMonitoring` had answered sanitized on a narrower argument (*"there is no caller it is safe to echo it to"*, true of the instance-wide copy), and two spellings of one route disagreeing is the defect this whole ADR is about; `test/monitoring/setup-schemas-agree.spec.ts` now pins that the two bodies agree member for member, which nothing did — the console had declared one input type for both routes on that ground while the two zod schemas had silently disagreed about `token`.
- **`GET /servers` and `GET /servers/:id` are the one asymmetry left, and it rests on two conditions rather than one.** `server:read` — which `permission.service.ts` bypasses for owner/admin only — *and* the console's setup form having nowhere else to read the value it must re-submit, so that saving a threshold tweak does not rotate a token an operator configured an external agent with. The second condition is the one that would have to go first, by giving that form the same omitted-means-keep write the two setup routes now carry; that is the shape of the work and not a promise it will be done.
- **The guardrail for the nested `server` is a property of the spec, not of a type, and that is a limit rather than an oversight.** Every other entry in `withoutSecrets` withholds a whole column, so the withheld value is absent from drizzle's inferred row and unreachable by construction. `server`'s secret is a field inside a column that has to be returned, so the projection is a call-site step: structural for the six database engines, which share one annotated `BaseDatabaseService.findOne`, and hand-written in `ApplicationsService.findOne` and `ComposeService.findOne`, whose inferred return types let a forgotten wrap compile. Naming those inferred rows to close it costs a paragraph of drizzle generics in front of the two reads the rule exists to keep legible, and a wrapper type that refuses a raw `Server` only relocates the step a new call site can forget. What has to hold is that *a read cannot be added without something going red*, which is a property of the spec — so it was closed there: `service-read-relations.spec.ts` reds on any `with:` block naming one of these relations that it does not know, and also on a read declared as answering a caller that its own assertions never drive, which is the gap its two halves used to leave between them. `realtime/server-access.ts` hands the raw row to four socket gateways and is deliberately not this seam: all four read one field off it (`sshKeyId`, or `organizationId` for the setup gateway) and none frames the row, so a gateway that streamed one would be a new decision about what a socket may answer with.

**Tightened for one surface by ADR-0024.** A tool result at `/mcp` is a response under this ADR, unamended, but it comes to rest in a copy nobody can recall, so it meets a stricter test than entitlement: only declared projection fields, declared error text and a masked log window, masked against every stored secret reachable from the target.
