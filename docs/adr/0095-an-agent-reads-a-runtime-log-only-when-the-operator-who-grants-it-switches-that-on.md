# An Agent reads a Runtime log only when the operator who grants it switches that on

An Agent can see that a Service is down (`get_service_health`) and why a deploy failed (`read_deployment_log`), but not why a running Service is crashing. The Runtime log answers that, and ADR-0024 lets a tool return log text from one source only: a Deployment log window. A Runtime log fails ADR-0024's test far more often than a Deployment log does. It is the app's own output, and apps print customer emails, request bodies and tokens that Cloudgate never stored, so the stored-secret mask cannot catch them, and a tool result is kept by the model host for good.

**Decision.** ADR-0024's list of sources gains a fourth: **a Runtime log window of an Application or Compose**, read with the same stored-secret mask and the same window as a Deployment log (100 lines unless asked, 500 at most, optionally only lines after a time). An Agent reads it only when its **Can read runtime logs** switch is on. The switch belongs to the Agent, is off by default, is set when the Agent is created and can be changed later by whoever may change the Agent's role, and each change is audited. It is not a role and not a statement: a Reader or an Operator with the switch on reads the Runtime log of exactly the Services its grant reaches, and a Caller never does.

**Considered options.** Every Reader and Operator reads it, with a warning, as with the Deployment log: rejected because the Deployment log is Cloudgate's own account of a build, while a Runtime log is whatever the app's users sent it. Operators only: rejected because reading a log is a read, and tying it to deploy authority would push people to grant Operator just to debug.

**Consequences.** ADR-0024 is amended, not replaced: the projection, the error tables and the mask still apply, and the mask's stated limit is written beside the switch where the operator turns it on. ADR-0055 (no Agent reads an Access log) and ADR-0028 (an Agent reads no traces) are unchanged.
