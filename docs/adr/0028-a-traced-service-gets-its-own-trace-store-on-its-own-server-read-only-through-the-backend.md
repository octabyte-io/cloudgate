# A traced Service gets its own Trace store on its own Server, read only through the backend

Built in five parts: the store on the platform host, the proxy, the Traces tab and the memory figure, Compose, and remote Servers.

The PRD asks for somewhere a Service can send OTLP traces without a vendor account, readable by whoever can read the Service and by nobody else, and removed when the Service is Deleted. No shipped trace viewer can check a Cloudgate entitlement, and a per-Service Delete exists only as "a store per Service" or "a tenant per Service". So **the platform runs one Jaeger v2 process (Collector, Badger and UI, Apache-2.0) per traced Service, on that Service's own Server.** That process is its **Trace store**. Its UI is reached only through a backend proxy that checks `service: ['read']` on the Service, the one check from ADR-0023. There is no shared store, no viewer we build, and no template.

**Considered options.**

- **One shared store for the platform**: Tempo with a tenant per Service. Rejected because Tempo is AGPL, its tenant header is unauthenticated, its local backend is documented as for dev and test, and reading it needs Grafana or a viewer we'd build and then authorize.
- **A template or a docs page**, where the operator deploys a collector as their own Service. Rejected because whoever reads that Service reads every sender's traces, which fails the entitlement goal, and its spans outlive a traced Service's Delete. The catalogue also has no default host.
- **Ruling tracing out of scope.** Held in reserve if the cost of one process per traced Service is refused later.

Do not "consolidate" the stores into one. The per-Service process *is* the entitlement boundary and the Delete boundary.

**Consequences.**

- **A Trace store is not a Service.** It is in no Project, has no published port and no Domain, and its container name carries `cloudgate` with no owner labels, so the container routes refuse it by the existing rule.
- **Only an Application or a Compose can have one, and only when the operator opts in.** A Compose's inner services share one store, told apart by `service.name`. A Database or a preview never has one.
- **A Compose's store is on a network of its own**, `cloudgate-traces-<appName>`, which the deploy joins every inner service to in the converted file, beside the three variables and an `OTEL_SERVICE_NAME` defaulting to the inner service's name. Not `cloudgate-network`: only a routed inner service is on it, and joining every inner service would put a Compose's `db` on the network every Service shares, under the name another Compose's `db` answers to. The network also keeps an isolated Compose isolated. An Application's store stays on `cloudgate-network`, where its Service is.
- **A store is named after its Service's kind and `appName`**, `cloudgate-trace-store-<application|compose>-<appName>`. `appName` is unique within Applications and within Composes but not across them, and the kind keeps an Application and a Compose of one `appName` from sharing, and so starting, restarting and removing, one container. A Compose's store network needs no kind: only a Compose has one.
- **Wiring is injected at deploy time, never stored as env rows.** `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_EXPORTER_OTLP_HEADERS` carry a generated per-Service `basicauth` credential, which is encrypted at rest and only ever shown as present (ADR-0006, ADR-0019). `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf` goes with them, because the store's one receiver is OTLP/HTTP and an SDK may default to gRPC. Turning traces on takes effect on the next deploy. The platform never instruments code.
- **Nothing is exposed on any Server's public edge.** On the platform host the backend reaches Jaeger through a loopback-published port. On a remote Server the store's UI port is published on *that* Server's loopback in the same way, and the backend reaches it through an SSH `forwardOut` channel (`remote/ssh-forward.service.ts`'s `SshForwardService`), a transport new to this repo and the one way the backend opens a stream to a port on a remote Server. The `docker port` read and the channel go over one ssh2 connection per Server, kept by `SshForwardService` and shared by concurrent requests, because a UI page fires a dozen requests at once and OpenSSH's default `MaxStartups 10:30:100` drops unauthenticated connections past ten, so a connection per request would make a page fail at random. Concurrent first requests share one handshake. Each request re-reads the Server's connection details, so a changed key, host, port or user retires the old connection (ended once nothing holds it) and dials a new one, and a deleted Server keeps none. A connection that closes or stops answering keepalives is evicted, with the channels on it, and the next request dials again. An unused connection is ended after 30 seconds, and app shutdown ends them all. `RemoteExecService` still opens a connection per exec; only this caller pools. The Server's sshd must allow TCP forwarding (OpenSSH's default); where it does not, reading that store answers 502 and nothing else changes.
- **The store's UI runs under a strict Content-Security-Policy**. *Amended by [ADR-0075](0075-a-trace-store-is-untrusted-so-its-ui-is-served-sandboxed-and-its-frame-is-authorized-by-a-token-in-the-path.md): this bullet assumed the store is trusted, which it is not on the Hosted instance, where its Server is the customer's. Every answer is now served sandboxed into an opaque origin, the console's frame carries the same `sandbox`, and the frame's requests are authorized by a short-lived frame token in their path rather than the session. The policy below stays as defence in depth.* The console frames it same-origin, with no `sandbox`, because a sandbox without `allow-same-origin` drops the session cookie the proxy authorizes on. It also renders span data the traced Service sends, so an XSS in it would run as the viewer. The proxy serves every answer with `script-src 'self'` plus the `sha256` of each inline script in the head of the page it forwards, computed per response so an image bump cannot break the page. It allows no `'unsafe-inline'` or `'unsafe-eval'` for scripts, sends `nosniff`, and drops the store's own policy and framing headers. A separate origin was rejected because a self-hosted install has one host and one certificate.
- **The store follows ADR-0018 and doesn't amend it.** A Stop leaves the store running, so a Service that is down can still be read. Turning traces off or a Delete removes the container and its directory on the machine that made them. Moving the Service to another Server reclaims the old store and starts an empty one on the new Server. Traces are never migrated. **No operation moves a Service today**: `serverId` is set when an Application or a Compose is created, and both update routes drop it (pinned by `test/traces/traces-remote.e2e-spec.ts`). So this rule is unbuilt, and the Trace store code assumes a Service's Server never changes; whatever first lets a Service change Server must build it with that change. An unreachable Server at Delete follows ADR-0018 as written: the Delete is refused unless forced, and a forced one names the store's container and directory it could not remove as `unreclaimedArtifacts` of kind `trace-store` on that Server.
- **Budget.** Retention is 1, 3 or 7 days (3 by default) as Badger's `ttl.spans`, and a change applies only to spans sent afterwards. The container has a fixed memory limit of 512 MiB, measured when the Traces tab was built: at 256 MiB a store taking 3,000 spans/s was killed by the kernel within a minute, and at 512 MiB its peak was 428 MiB at that rate and 461 MiB at 24,000 spans/s. Most of that is Badger's memtables, which Jaeger does not let us size. `memory_limiter` holds the Go heap at 220 MiB and refuses spans past it, so an overloaded store refuses spans instead of being killed. Badger has no disk cap, so the console shows the store's size.
- **An Agent reads no traces.** No MCP tool reaches a Trace store, and neither agent role changes. This is a bound set by the tool surface, in the shape ADR-0023's third consequence describes.
- **Configuration takes `service: ['update']`** and writes an audit row.
