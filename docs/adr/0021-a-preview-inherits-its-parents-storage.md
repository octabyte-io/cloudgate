# A preview deployment inherits every artifact its parent's rows address, and owns only the ones its own `appName` names

ADR-0018 settled which **machine** each of a Service's artifacts belongs to. This asks the question one column over, about a preview deployment: `PreviewDeploymentsService.deployPreview` builds a whole deployment by spreading the parent Application's row over `{ appName: preview.appName }`, so every artifact the product addresses by `appName` silently becomes the preview's — and one of them is the directory a `file` mount's body is materialized in, which `MountsService` writes under the **parent's** name and never under a preview's. The spec handed to the daemon therefore named `{root}/applications/{preview.appName}/files/config.json`, Docker mints a missing bind source as a *directory*, and the preview came up with an empty directory where its config file belongs. Nothing failed, so it took a probe to find.

The fix is a one-line question with three defensible answers — materialize a copy under the preview's name, mount the parent's, or carry no file mounts at all — and answering it once, for the class, is what this ADR is for. The next `preview*` column and the next artifact keyed by `appName` should not each get argued from scratch.

**The rule.** A preview **owns** exactly the artifacts its own `appName` mints: its Swarm service, its source tree under `{applicationsDirectoryOn(buildHost)}/{preview.appName}`, its built image tag, its Traefik router and its build leftovers. It **inherits**, unchanged, every artifact addressed by a row it borrows rather than by its own name — which today is the whole of a Service's storage: the named Docker volume a `volume` mount points at, the host directory a `bind` mount points at, and the file body a `file` mount points at. Where a preview may diverge from production is exactly where an operator has said so, in a `preview*` column; a preview does not diverge by an inference the engine makes on its behalf.

**The measurement that settles it, rather than the symmetry that suggests otherwise.** `docker/docker.utils.ts` composes the three mount kinds three ways. `generateVolumeMounts` names `mount.volumeName`; `generateBindMounts` names `mount.hostPath`; **neither carries an `appName` at all**, so a preview has always mounted the parent's named volume and the parent's host directory verbatim, and always will unless somebody decides otherwise for those kinds too. Only `generateFileMounts` takes a directory the caller composes out of a Service name — because a `file` mount's body has no location of its own until Cloudgate picks one. That composition is the entire reason a `file` mount ever looked like the preview's own. Answering "materialize a copy" would have made `file` the single mount kind a preview isolates, sitting beside a `volume` mount still pointed at production's data: not isolation, an inconsistency with the shape of one.

**Why a copy is the wrong answer even taken on its own terms.** `mount.content` is `encryptedText` under ADR-0015 precisely because *a file body is where an operator puts a credential*, and an earlier fix took that column **off** the deploy path on purpose — `ApplicationsService.findDeployable` projects `mounts` to `ServiceMount`'s five declared fields after the rollback-context fix found a decrypted body served over HTTP out of `rollback.full_context`. Materializing a preview's own copy means decrypting that column back onto the deploy path and writing a **second plaintext copy** of the operator's credential onto the machine. What it buys in exchange is nothing: there is no `previewMounts` column and no per-preview mount row, so the copy is re-materialized byte-identical from the same rows on every deploy. That is duplication, not divergence. It also multiplies ADR-0018's atomicity set from one writer to one per live preview — `MountsService.remove` addresses `{parent.appName}` alone, so a deleted mount's copies would outlive the row inside every preview of it, as the last plaintext copies in existence of a body whose ciphertext the cascade has already dropped. ADR-0018 made that leftover tree a fourth `UnreclaimedArtifact` kind on exactly that argument; this decision is what stops there being N more of them.

**Why carrying no file mounts is worse than either.** It gives up the operator's declared configuration without giving up anything that configuration endangers, because the volume and the bind would still be production's — and an application that needs its config file to start would not start. It is the only one of the three answers that changes a preview's behaviour from *wrong in a way an operator can reason about* to *absent*.

**What `previewEnv` and `previewBuildArgs` mean, since the question turns on it.** The preview spec says it outright: they are "how a preview gets pointed at a staging database instead of the production one it would otherwise inherit". The model is *inherit production, and diverge where the operator says*. It is bounded to those two columns by construction and not by omission — the preview spec enumerates all eleven preview settings columns, and **none of them is a mount**. So the notion of a preview diverging from production is real, is operator-authored, and does not extend to storage.

## Consequences, all deliberate

- **Two containers share one bind source, and that is not a new state.** A preview binds the same file its parent's tasks bind. So does every replica of the parent already: `application.replicas` defaults to 1 but is not constrained to it, and `generateConfigContainer` pins a Service *with mounts* to `node.role==manager` rather than to one task. `generateFileMounts` binds **per file** — `path.join(dir, mount.filePath)` — not the directory, so what is shared is exactly the bodies the operator declared and nothing else in the tree. An application that writes back to its own config file can affect production from a preview; an operator who cannot accept that is in the same position for the parent's volume, and the lever is `previewEnv`.

- **A preview's `file` mounts reach the spec as `bind` mounts, and that is the accurate word.** `PreviewDeploymentsService`' `inheritedMounts` converts them at the one boundary where both `app.appName` and `preview.appName` are in scope. The two kinds emit the identical spec entry, and `docker/docker.types.ts` reads `bind` as *the host path* — which is exactly what the parent's materialized file is to a preview: a path on the run Server this deployment did not create and does not own. The conversion calls `generateFileMounts` rather than re-joining the directory and the `filePath`, so the composition of that path stays in one place (ADR-0018's root rule), and a change to it reaches a preview without anyone remembering this function exists.

- **`previewTeardownSteps` stays three steps, and ADR-0018's paragraph on it stops being provisional.** Nothing in the product writes `{preview.appName}/files`, so there is no tree to reclaim and a fourth step would be an `rm -rf` at a path no writer has. That is now a decision rather than a deferral.

- **The invariant `mechanize.ts` depends on is stated where it is depended on.** `buildServiceSettings` resolves the file-mounts directory from `appName` — the same column it names the Swarm service with — and that is correct only because `appName` there is also the Service that *owns* the mount rows. Those are two questions with one answer everywhere except a preview, which is the whole defect; the call site now says so and names the boundary that keeps it true.

- **The rule is enforced by a test rather than by a type.** A field on `DeployableApplication` naming the mounts' owner was the shape tried first, and `test/coding-standards/deployable-query-result-types.spec.ts` refuses it: that type is what `findDeployable` returns and every field of it must be one a query fills. So what holds the decision is `test/mounts/file-mount-source-roots.e2e-spec.ts`, which takes the preview's bind `Source` from the parent's own write dispatch and asserts that **no command in the whole preview deploy names `{preview.appName}/files`** — the ticket's falsifiable claim from both ends.

- **Not decided here: whether a preview should ever get storage of its own.** If it should, the answer is a `previewMounts`-shaped column an operator writes — divergence they can see, edit and reason about — and not an engine that copies rows the operator did not ask to have copied. The rule above is what such a column would have to be argued against, which is the point of writing it down.

**A second trigger inherits the same way, behind a switch (ADR-0026).** A Requested preview inherits exactly as a pull-request preview does, unamended. Because the branch code is unmerged and unreviewed, it may exist only on an Application whose operator set `requestedPreviewsAllowed`, which no Agent can write.
