# A template setup waits as a pending setup, and a plan creates its compose part from it

Status: accepted. Builds on [ADR-0029](0029-the-project-config-is-the-one-record-of-what-a-project-runs-and-the-console-edits-it.md) (one Project config, changed only by applying a plan), [ADR-0063](0063-a-template-is-offered-only-where-its-deploy-target-can-make-every-entry-and-a-compose-part-needs-a-server.md) and [ADR-0064](0064-a-templates-values-are-made-once-at-setup-and-saved-where-typed-values-are-a-compose-part-never-takes-an-output.md), whose pending set this widens. Makes one exception to **Console-managed** in `CONTEXT.md`. Decided in [How does setting up a template become a Plan?](https://github.com/octabyte-io/cloudgate/issues/1352). Amended by the owner's decision on #1369 (dismiss against supersede): on a Cloudgate-kept config a setup's entries are held only in its open plan's text until Apply, so a newer plan made from the stored text (Check for changes, another whole-YAML save, an Agent's `request_plan`, a stopped Service's deploy) carries the open plan's template entries forward: every entry the open plan's text lists under a Config name a Pending setup in that Environment still holds, and the new text does not. Every other line is the new text's. A superseded plan therefore never orphans its Pending setup, and dismissing the plan that holds those entries still drops it, together with a Setup record that then records nothing (no Pending setup points at it and none of its Config names is in the stored text). A plan a config move dismisses is not a dismiss: its Pending setups wait for the repository's push. Amended by #1374 (where the 30-day note goes): the sweep leaves an `expired_setup` row on the Environment naming the setup, its template and the Config names it still held, listed beside the Environment's Pending setups and removed after 30 days of its own. A plan note was rejected because a repository-kept config may have no plan until the push the setup waited for, and the audit trail because the base member who sets a template up cannot read it. Cancelling a Pending setup whose parts the open plan of a Cloudgate-kept config creates plans that Environment again, so the plan on screen no longer offers them. Amended by the owner's decision on #1379 (a compose part in a Cloud Environment): the stack runs on its own Stack VM, which an asynchronous Cloud run makes after the Apply, and the cloud Domain path refuses a Domain until that Stack VM exists. So the all-or-nothing compose step covers what the Apply writes, the stack's row, its compose file, its `.env` values, its file mounts (rows, written onto the Stack VM once it answers) and its Infrastructure state, and deletes the row again if any of it fails. Its Domains are not part of that step: they stay in the Pending setup, on a part that now names the stack, and the Cloud run adds them through the cloud Domain path once the Stack VM is made, before the stack's first Deployment, then takes the part out. A Domain that path refuses then is named in the run's log. The Apply also saves the template's minimum size as the stack's console size, so a later plan never resizes it back down to `medium`.

Setting up a **Template** is an ordinary **Plan** the user reviews and Applies. A template's compose part is listed in its config as `kind: compose, managed: console`, and until now a plan never created a console-managed Service: it refused a console-managed line with no Service behind it. For a repository-kept config the plan comes from a push, possibly days after the setup, so whatever the setup chose has to wait somewhere between the two.

## Decision

- **A pending setup.** A setup is kept on its Environment as one encrypted **pending setup**: the setup name, every value ADR-0064 makes, the Domain hosts the user picked, the compose file and the config files. It is ADR-0064's pending set, widened. Each Apply takes out what it creates.
- **A plan creates the compose part from it.** A plan that finds a console-managed line with no Service, and a pending setup holding a stack under that Config name and kind, shows a create (`create compose stack ghost-app, from the Ghost template`) instead of refusing. Once made, the stack is console-managed like any other: no later plan changes or destroys it. This is the only way a plan creates a console-managed Service.
- **Names.** Every part's Config name is the setup name, a hyphen and the template's own name for it (`ghost-app`, `ghost-db`). A part named like the template is not doubled. The setup name starts as the template's id and the user may change it. If any resulting name is taken in the config or in any Environment, the setup name as a whole takes `-2`, `-3`, so a setup's parts always share one prefix. Links, `{{domains.<name>}}` references and the pending setup's keys are renamed with it.
- **Matching.** A push-made plan matches a pending setup strictly by Config name and kind. A part renamed in the pasted YAML gets nothing from it, and the plan notes the values that went unused.
- **When it is dropped.** A pending setup is deleted once every part is created, when the user cancels it (it is listed on the Environment; `environment: ['update']`), when its plan is dismissed on a Cloudgate-kept config (whose text changes only at Apply, so nothing else needs undoing), or after 30 days, with a note. A plan superseded by a newer one does not drop it.
- **A setup record.** Every setup also leaves a plain record on the Project: the template's id, its catalogue revision, the setup name and the Config names it made. It is a fact, never a link: the copy still gets no updates.
- **Other Environments.** A plan holds back every part on a setup record, together and with a note, in an Environment where none of them exists and no pending setup covers them. Setting up the same template there reuses those names and makes only that Environment's values, hosts and stack. That is how a setup is promoted.
- **A new Project.** "New Project from a template" is an ordinary new Project with a Cloudgate-kept config and one Environment, `production`, whose Deploy target is picked in the same form. Both are made when the user presses Set up; a dismissed plan leaves an empty Project, and the form says so.
- **Failures.** Parts already created stay, and the pending setup keeps the rest for the next plan. The compose step is all or nothing: hosts are checked before anything is written, and if writing its Domains or files fails after the stack's row exists, that row is deleted again. It was never deployed and holds no data.
- **Permissions.** Setup asks, at setup, every statement its Apply will ask: `service: ['create']` on the Project, `domain: ['create']` when there are Domains, `volume: ['create']` when there are files, `deployment: ['create']`, and `project: ['create']` and `environment: ['create']` for a new Project. No agent sets up a template: a pending setup holds secrets, and an agent never applies.

## Considered options

- **Create the compose stack at setup, outside the plan.** Rejected: the user gets a stack they never reviewed, and it stays behind when the plan is dismissed (the shape of #523).
- **Wait for `kind: compose` (#1343).** Rejected: a template's stack is raw, and that work refuses raw sources, so it stays console-managed either way.
- **Keep the template's own names and add `-2` per clash.** Rejected: one setup's parts could end up `app` and `db-2`, and nothing would show they belong together.
- **Let other Environments create the parts on their next plan.** Rejected: they would get a database with empty passwords and a refused stack line, a half-made app.
- **Mark a half-made stack as incomplete instead of deleting it.** Rejected for templates: the row was never deployed, so deleting it loses nothing, and "incomplete" would mean something new to every screen. This settles #303's open option for templates only.

## Consequences

- `plan-environment.ts`'s refusal of a console-managed line with no Service gains the pending-setup case and the setup-record hold-back.
- The setup record is what a later "a newer version of this template exists" feature could read; that stays undecided.

**Amended 2026-11-11 ([ADR-0073](0073-a-get-started-wizard-setup-is-applied-by-cloudgate-once-its-server-is-ready.md)):** a setup made by the get-started wizard (`autoApply: true`) is applied by Cloudgate itself, as the person who set it up, once its Server is Ready and set up, and only when its Plan holds nothing but that setup's creates. Every other setup still waits for Apply as above.
