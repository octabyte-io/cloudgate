# A Private web service on Google Cloud is reached through a private `run.app` zone on the Environment network

Status: accepted, from the "Private web service on Google Cloud" spec, proved live and then built.

A `web-private` on Google Cloud is a Cloud Run service with ingress `INGRESS_TRAFFIC_INTERNAL_ONLY` and the invoker check off. Cloud Run takes a request as "internal" only when it arrives from a VPC network of the same project through Private Google Access or a Private Service Connect endpoint. Every Cloud Run service, worker pool and job of an Environment already leaves through Direct VPC egress `PRIVATE_RANGES_ONLY` on the Environment network's subnet, and the subnet already has Private Google Access on. But a public `*.run.app` address resolves to a public Google address, which `PRIVATE_RANGES_ONLY` sends straight to the internet, so the call arrives as external and is refused with a 404.

**Decided: each Environment network that holds a Private web service also holds a private Cloud DNS zone for `run.app.`, bound to the network's VPC, with a `*.run.app` and a `run.app` A record to `private.googleapis.com`'s four addresses, `199.36.153.8`–`199.36.153.11`.** Inside the Environment every `*.run.app` name then resolves to those addresses, which `PRIVATE_RANGES_ONLY` already sends into the VPC, and Private Google Access carries the call to Cloud Run as internal. Nothing else changes: no Service's egress, no Cloud NAT, no router, no firewall rule.

- **The zone lives in the Environment network's Infrastructure state.** The first plan that creates a `web-private` in a network adds it on the network step, as "Private DNS zone `run.app`: create, for this Environment's Private web services, about $0.20/month". A later one does not show it again. It stays after the last `web-private` is gone and is removed only with the network, the AWS namespace's rule, so a later `web-private` does not make and unmake it. The network's row keeps it as the link kind `run-app-zone` beside its databases' private links.
- **The address handed over is the service's own URL**, `https://<service>-<project number>.<region>.run.app`, read after its first apply from the Cloud Run service's `urls` (Cloud Run v2 lists that form first and the older `https://<service>-<hash>-<region code>.a.run.app` beside it, which `uri` holds; both reach it through the zone, as the live proof measured). It is a base URL used whole. It is not known before the first deploy, since it carries the project number and Cloudgate's own service name.

## Consequences

- **Every `*.run.app` lookup inside the Environment goes through Private Google Access**, including calls to the operator's own public `web`s and to other projects' Cloud Run services. The live proof measured that both still answer (a public service from inside and outside, and another project's public service from inside). A Cloud Run service of another project with ingress `internal` still refuses these callers, as it should: they are not in its project.
- **It is hard to reverse.** Once Environments hold the zone, taking it away breaks every Private web service in them, and a different route would have to be added to each made network first.
- **Callers get 404 for the first few minutes.** For about 1.5 to 3.5 minutes after a Private web service (or a caller) is first made, callers inside the Environment get the same 404 an outside caller gets, then 200 for good. DNS is right throughout; Google is rolling out the ingress and egress settings. No deploy waits for it. The docs and the walk say to allow a few minutes before a 404 from inside counts as a failure.
- The deploy role already holds the Cloud DNS permissions the zone needs (version 4: `dns.managedZones.*`, `dns.resourceRecordSets.*`, `dns.changes.{create,get}` and `dns.networks.bindPrivateDNSZone`).

## Considered and rejected

- **`ALL_TRAFFIC` egress plus Cloud NAT.** Sending all of a Service's traffic into the VPC also makes `run.app` calls internal (the live proof saw it work), but it changes every Service's internet traffic in the Environment, needs a Cloud Router and Cloud NAT at a standing cost per Environment, and bills NAT data processing on every outside call, to fix calls to one service.
- **An internal Application Load Balancer** in front of each Private web service. It gives a private IP and its own name, but it costs about as much as the Environment's public load balancer per Environment, needs a proxy-only subnet and a serverless NEG and backend service per Service, and a certificate for HTTPS, all to reach a service Google already serves.
- **A Private Service Connect endpoint for Google APIs**, with a private zone pointing at it. It does the same job as the zone over `private.googleapis.com`, but adds a reserved global address and a forwarding rule per network, and a PSC endpoint for all Google APIs reaches far beyond Cloud Run, for no gain here.
