# A shell on the platform host is an owner-and-admin action, not an authenticated one

`/terminal` has two branches. One resolves a `server` row through `findAuthorizedServer` and dials it; the other, `serverId=local`, dials the machine Cloudgate itself runs on. The handler authenticated and then took that branch on nothing else — so every signed-in user of every organization on the instance could open a **root shell on the platform host** by hand-building one WebSocket URL. It is the same shape ADR-0008 found on the container sockets, on the one socket that ADR did not cover: there, the local branch was "no `serverId`, meaning the platform's own machine", and wide open. Here the local branch is named rather than implied, which is why it survived the sweep. The fleet screen's "This host" card then turned a hand-built URL into a button for every member.

`findAuthorizedServer` cannot be applied to it. The platform host has no `server` row — that is the entire reason the branch exists — and `checkServerAccess`'s contract across the whole HTTP surface is that an absent server id means "no row to check" (ADR-0008's second consequence). So the question has to change shape: not *may you reach this row*, but *do you administer this instance*. Cloudgate answers it with **the caller's role in their active organization, and admits only `owner` and `admin`** — the owner-or-admin check that `settings`, `ai`, `custom-roles`, `billing` and `access-log` already share, reading the member row rather than the admin plugin's global `user.role`, which is `'user'` for everybody on a self-hosted install. The refusal closes `4403` with `HOST_SHELL_REFUSAL` and a journal line naming the caller.

Consequences, all deliberate, and the first two are the ones a future change should not "correct" back:

- **Owner-or-admin outright, not a statement from the entitlement vocabulary.** `server:create` was the near miss: the setup socket gates on it, and `POST /monitoring/servers/:id/setup` rides it for the host itself. It is wrong here for one reason — a statement can be granted to a licensed custom role, and a role named "Deploy engineer" that says `server: ["create"]` would silently carry a root shell on the machine holding every organization's containers, its database and `APP_ENCRYPTION_SECRET`. A shell on the host is strictly more than anything `statements` names, so it is gated by the thing that sits above all of them rather than by the nearest one below. `docker:read` fails the same test and is weaker besides: ADR-0008 uses it for *reading* an unmanaged container on this host.
- **This refusal says why, and does not join `socket-access.ts`'s byte-identical denial frame.** That frame exists so a caller cannot tell "no such id" from "not yours" and walk another organization's id space (ADR-0007, ADR-0008). `local` is not an id: it is a literal, naming the machine that is serving the console, whose existence the caller has already proved by connecting to it. There is no id space to enumerate here and nothing a specific reason discloses, while a silent close is exactly what was filed as undiagnosable — indistinguishable from a proxy dropping the connection. `4403` rather than a second spelling of `4003`: this gateway's codes read as their HTTP statuses with a 4000 offset (`4400`, `4500`), and `4003` is spoken for.
- **The Server branch gained the entitlement its own routes require, and refuses in silence.** `GET /servers/:id` carries `@RequirePermission('server', 'read')`, `memberRole` grants no `server` action at all, and Nest guards never run for a raw `ws` upgrade — so a base member who cannot so much as list the fleet could still be handed a root SSH shell on any machine in it by naming its id. The socket now checks `server:['read']` by hand, exactly as the setup socket checks `server:['create']`. Unlike the local branch this one **keeps the silent codeless close**, byte-identical to an id that does not exist, because to a caller who may not see the fleet "you may not have this one" confirms the id. The journal keeps the difference.
- **There is no instance-level authority in this codebase to gate on, and this decision does not invent one.** The admin plugin's global `user.role` is `'user'` for every user on a self-hosted install; the only role that means anything is per organization. So an owner or admin of *any* organization on the instance passes — including a second organization, though creating one already requires being an owner or admin of the first (`OrganizationsService.create`). That is the existing ceiling rather than a new hole: the same role already changes this host's web server settings, runs its Docker cleanup and updates the platform through `SettingsService.requireOwnerOrAdmin`, and is the only static role holding `traefikFiles:write`, which writes files into its Traefik directory. If an instance-level role is ever introduced, this is one of the call sites that should move to it.
- **The gate runs before the parameter checks and before `setupSshKey`.** The local branch's first act was to generate an SSH key pair on the host and write it under `CLOUDGATE_DIRECTORY`; an unentitled caller must not reach a side effect on the way to being refused, and must not be told which parameters the request wants either.
- **The console says who this is for and gates nothing.** `local-shell-card.tsx` carries a sentence naming owner and admin, and still renders the form for everyone: the refusal is the gateway's and arrives as a close frame the terminal already renders. A form hidden behind a role read in the browser is a claim about authority made where the caller controls the answer.
- **Authorization still happens only at connection open.** A session revoked, or a member demoted, mid-shell keeps the shell — an open defect, and true of all six gateways rather than of this one.
