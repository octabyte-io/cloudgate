# A SCIM `DELETE` tombstones the user, and a create for the same address revives only a tombstone

The two SCIM routes were found disagreeing about one row. For an organization-scoped token — the only kind `ScimService` issues — better-auth's SCIM plugin answers `DELETE /scim/v2/Users/:id` by removing the membership and the provider's `account` link and **keeping the `user` row**, still banned if the directory had deactivated it first. `GET` finds a SCIM user through that link, so it answers 404. `POST` looks the address up in `user` *before* it looks for a link, finds the row, and refuses `409 uniqueness` unless `linkExistingUsers` allows linking, which by default it never does. So the same address was refused for ever, a rehire could not be provisioned, and an identity provider that moves a person between groups by delete-and-recreate was stuck. Nothing in the console reaches a user who is not a member, so there was no way out.

The ticket asked for this to be decided and recorded, because "what does DELETE mean" has three defensible answers: hard-delete the row, keep it and let a create take it back, or keep it and refuse for ever. This ADR records the answer for the class.

**The rule.** A SCIM `DELETE` **tombstones** the user: membership and provider link gone, `user` row kept. A later create for the same address **revives the tombstone**, with the same id, as a member again. It revives **only** a tombstone, meaning a `user` row with **no `account` of any kind and no membership in any Organization**. Everything else keeps answering 409, as before. The check is `reviveScimTombstone` in `backend/src/enterprise/scim/scim-tombstone.ts`, handed to the plugin as `linkExistingUsers.shouldLinkUser`.

**Why keep the row rather than hard-delete it.** Removing a member anywhere else in Cloudgate keeps the `user` row, because the audit trail's `user_id` and every other history column point at it. A SCIM delete is a member removal said by a directory, and should not be the one path that erases a person's history. RFC 7644 §3.6 only requires that a deleted resource is no longer returned and "SHALL NOT" count towards conflicts. It does not require the row to be gone.

**Why the narrowing is the whole safety argument.** The plugin's default refuses to link by email because linking by address alone would hand a SCIM token control of an account it never provisioned, such as a person who signed up with a password. A tombstone has no password, no SSO link and no Organization, so there is nothing of anyone's for the token to take over. A row with any sign-in method, or any membership, is somebody's live account and is refused exactly as the plugin would refuse it.

## Consequences, all deliberate

- **Only SCIM's own ban is lifted.** A tombstone left by `active: false` then `DELETE` still carries the ban, with reason `Deactivated via SCIM`. Reviving it clears that ban, both on the row and on the object the plugin builds its response from, so a create that says `active: true` answers `active: true`. A create that says `active: false` is re-banned by the plugin straight after, as a new user would be. A ban with **any other reason** was put there by someone else and is not SCIM's to lift, so that user is refused 409 rather than silently reinstated.
- **`GET` 404 beside `POST` 409 still happens in two narrow cases**: that foreign ban, and a user who still has an account or membership somewhere else. In both, refusing to link is the safe answer, and the disagreement is the price of it. The 409 in those cases is the plugin's own `uniqueness` error.
- **Rows left by deletes before this decision are revived by the next create too**, because they are the same shape. No data migration is needed.
- **Not decided here: a console control to see or clear a banned account.** It was raised as optional. Nothing in the console lists users who are not members, and building that screen is its own decision.
