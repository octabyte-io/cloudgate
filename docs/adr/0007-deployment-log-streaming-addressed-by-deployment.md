# Deployment log streaming is addressed by deployment, not by path

Originally, `/listen-deployment` took a caller-supplied `logPath` and authorized it by containment alone — `readValidDirectory` checked the path resolved under the platform directory and nothing else. Since that directory also holds `ssh/`, `traefik/` and `patch-repos/`, any authenticated caller could read the host's SSH private key off the socket. Cloudgate instead **addresses the socket by `deploymentId`**: the gateway resolves the deployment row, authorizes it through the same `checkServiceAccess` path the HTTP log read already used, and derives both the log path and the build server itself. A caller-supplied path can only ever be validated negatively — every future subtree written under `CLOUDGATE_DIRECTORY` would inherit an obligation to be forbidden — whereas a deployment id inverts it: the only readable file is one a deployment row points at, and that row carries the ownership chain.

Consequences, all deliberate, which a future change should not "correct" back:

- **`logPath` and `serverId` are no longer accepted.** The wire contract broke once, on purpose; the client held the deployment id at every call site already.
- **No `IS_CLOUD` gate on the local branch.** Per-service entitlement is strictly stronger and more precise than refusing local reads wholesale, and `IS_CLOUD` stays a billing flag here rather than a feature gate. Revisit only if a `remoteServersOnly` mode is ever added.
- **`readValidDirectory` survives as a defense-in-depth assertion, not the security boundary.** It resolves through `resolveThroughSymlinks`, not bare `path.resolve`, because a planted symlink escapes the latter, and guards against a tainted stored path — `APP_NAME_REGEX` admits `..`, so a composed log path can climb one segment. It takes a `serverId` argument to pick the right root, because a remote build's log path is rooted on `REMOTE_CLOUDGATE_DIRECTORY` while the local one follows `CLOUDGATE_DIRECTORY`.
- **Denial is a single close code for both "not found" and "not permitted"**, so the socket is not a deployment-id enumeration oracle; the distinction goes to the journal, where only an operator sees it.
- **Authentication runs before the query is read at all.** Cloudgate's other gateways validate parameters first, so their `4000` answers an anonymous caller. Here the parameter close is only reachable once a caller is established: an unauthenticated connection gets one bare close whatever the URL said, and learns nothing about the gateway's contract or about which deployment ids exist. The ordering is the cheap half of the property — it also means no check added later can drift ahead of the guard without the anonymous-caller test failing. *Authorization* deliberately stays after the parameter read: a session with no active organization gets the `4000` for a missing `deploymentId` rather than the denial, because the malformed half is the more useful answer and it tells that caller nothing they did not already know about their own session.
