# An Agent is a Member, and is authorized by the one check

Cloudgate's MCP endpoint lets a coding agent operate an Organization's Services. The obvious shape, and the one most platforms ship, is a second authorization path for machines: an agent table, agent scopes on the credential, an agent guard, an "agent mode" branch in the check. Cloudgate has none of those, and the absence is the decision. **An Agent is a Member**: its own `user` row, declared an agent on the row and never holding an `account`, and its own `member` row in exactly one Organization for life, on one of three unlicensed static roles, `agentReader`, `agentOperator` or `agentCaller` (the third added later; see below). Every tool call builds a `PermissionCtx` for that user and runs the same `PermissionService.checkPermission` and `checkServiceAccess` the equivalent HTTP route runs. **There is one implementation of the check.** It is reached from three entry points, `PermissionsGuard` on HTTP, the socket context builder (`realtime/socket-access.ts`, `permissionCtxOrDeny`) and the tool dispatcher, and from inside the service methods all three call. The MCP surface is the third entry point to an existing pattern, not an invention. **Amended: four.** The Gateway (ADR-0040) runs `checkPermission` plus `checkServiceAccess` on the AI model's Application, for `service: ['call']`. It is another entry point to the one check, not a second path.

**Considered options.**

- **A separate agent authorization path**, with scopes on the credential and an agent guard. Rejected because it is a second implementation of "may this caller do this", and two implementations drift. The drift would be invisible here because the HTTP guard fails open (below), so no census could hold the two against each other.
- **A delegated credential**, meaning a key hanging off a human's `member` and bounded by it. Rejected because `findMember` must return a *row*, and the intersection of a human's grant with a credential's bound is a value no table holds. Computing it is the second path under another name. better-auth's api-key plugin also resolves a key to its owner and nothing else, with no hook, and `audit_log` holds one actor in `NOT NULL` `user_email`/`user_role`. A bound snapshotted at mint was rejected as worse than either: it *looks* bounded by a human and drifts silently as the human is narrowed.
- **Per-key statements** (`apikey.permissions`). Rejected because they put authority on the key rather than the principal, so an Agent holding two keys has two answers to "what can it reach". They would also be an unlicensed per-statement grant mechanism beside the licensed one. Agent keys are equivalent, and all of them read the one grant.
- **A custom role for an Agent.** Rejected because `resolveRole` refuses every non-static role on licence lapse, and a custom role would erase the agent-only role that tells an audit entry's agent from its person.

**Consequences.**

- **The two surfaces have opposite defaults, on purpose.** `PermissionsGuard` fails *open*: a handler with no `@RequirePermission` passes, because 113 of 307 mutating handlers already existed gated in the service layer. That default is documented, censused by `route-permissions.spec.ts` and frozen. The tool dispatcher fails *closed*: a tool with no permission declaration refuses to register at boot and is refused at dispatch. The difference is historical, not philosophical. A tool registry starts empty, so fail-closed costs nothing now and could never be introduced later once tools existed. Do not "harmonize" either default toward the other. The guard's fail-open is not widened, relied on or reproduced by this feature, and this ADR does not amend it.
- **"The same check" is held by a census, not by care.** `tool-permissions.spec.ts` binds each tool to its HTTP twin. A tool's declared permissions must be *identical* to the metadata reflected off the twin, an undecorated twin must be written down, and every tool's service method must take `ctx: PermissionCtx` first. **Amended: "an undecorated twin must already be in `BASELINE`" holds only for a write.** `BASELINE` lists undecorated *mutating* handlers, and every read twin in this tree is an undecorated `GET` gated in its service (`GET /environments/:id`'s `environment: ['read']` is `EnvironmentsService.findOwned`'s `checkEnvironmentAccess(ctx, environmentId, 'read')`). So an undecorated mutating twin must be in `BASELINE` (now `route-permissions.baseline.ts`, so both censuses read one list), and an undecorated read twin must name the in-service call that enforces its statement; the census reads that method out of the file and checks the call asks for exactly the tool's permissions, or for `findMember(ctx)` and a grant column when the tool declares none. The last assertion catches a tool wired to the ctx-less, unchecked member of a pair (`runManual`/`runScheduled`), which no declaration census can see. The ungated count is frozen at zero and reads are censused too. A tool calls the service method, never the controller, because `@RequirePermission` is inert metadata that only the guard reads.
- **An Agent's reach is bounded by the tool surface, not by the statement alone.** This claim is weaker than the rest of this ADR makes, and it is stated so that nobody discovers it. `agentOperator` holds `deployment: ['create']`, which in the statement vocabulary also buys database `rebuild` (it destroys the data volume), compose `removeContainers` and `rollback`. Only the absence of a tool keeps an Agent away from them. Splitting the statement would reopen the line between operating and redefining a Service and silently narrow every stored custom role. The tool count and the no-twin count are therefore frozen, so a twelfth tool is something a reviewer argues about rather than something that appears.
- **Amended: three agent roles, not two.** `agentCaller` holds `service: ['call']` and nothing else. `call` is a new action on `service` that spends on an AI model through the Gateway; owner and admin hold it, the base member does not, a stored custom role lacks it, and `agentReader` and `agentOperator` do not gain it, so an operator who wants a key that both reads and spends creates two Agents. It is static and unlicensed for the same reasons as the other two, minting, revoking and suspending one are unchanged (`member: ['create']`, `['update']`, `['delete']`), and creating one writes the same `createAgent` and `addAgentKey` audit rows with its role. At `/mcp` its key gets an empty `tools/list` and every `tools/call` is refused. Holding no read statement is not enough for that, because the row-scoped tools (`list_projects`, `list_environments`, `get_project_config`) declare no statement and filter by the grant columns, which a caller Agent's grant fills with the AI models it may call. So the dispatcher also reads `GATEWAY_ONLY_ROLES` off the member row and refuses that role every tool before the statement check. That is a question about the caller's *role*, the same input the one check reads, never about who the caller is, so it is a narrowing of the tool surface and not the second path rejected above. The Gateway's own entry point (above) and the second surface for an Agent key (below) are amended with the Gateway, ADR-0040.
- **An Agent never has instance authority, whatever its role.** This narrows ADR-0013. `checkInstanceAuthority` refuses any user whose row declares it an Agent, even one written directly to `admin` in the instance organization. Every `member.role` write goes through one writer (`rbac/member-role.ts`) that keeps Agents on agent roles and people off them, and better-auth's `/organization/update-member-role` is closed, as are its `/organization/invite-member`, `/organization/remove-member` and `/organization/leave`, so an invitation too carries only a role Cloudgate validated. Either layer alone would be enough today; both exist because `member.role` had two writers and one of them skipped every Cloudgate rule. An operator who wants platform-host automation uses a personal key, which carries their own authority, openly.
- **This decision does not extend to personal keys, deliberately.** A personal key, the API key that existed before Agents, keeps its owner's full authority, has no rate limit and has an optional expiry. A personal key is a person acting, and an Agent key is an Agent acting. Bounding a personal key would mean a grant on the REST surface, and that can't be enforced while the guard fails open for 113 handlers. It would also rebuild the supported public REST surface already ruled out. Each credential has exactly one surface: an Agent key is refused on REST and on better-auth's own `/api/auth/*`, and a personal key is refused at `/mcp`. **Amended: an Agent key has two, `/mcp` and the Gateway (ADR-0040), and a Personal key is refused at both.** What a key does at each is its Agent's role, never the key. So "an Agent cannot exceed its grant" holds for everything that connects to MCP, beside a credential that can exceed any grant in the same settings screen. That contrast is intended. The same fix closed one hole on both kinds: no key may reach key management (`/api-key/*` is in `disabledPaths`, and `/users/me/api-keys` requires an interactive session).
- **The Agent is permanent and only its keys expire.** better-auth deletes a key row it finds past the plugin's own `expiresAt`, on verification and in a sweep it runs whenever anyone creates, lists or deletes a key, so an Agent key keeps its expiry in a column the plugin never reads (`apikey.agent_expires_at`) and whatever authenticates an Agent key checks that column itself. An expired Agent key therefore stays a row until an operator removes it, and still the `member` row is the durable record: it keeps an Agent's grant and audit trail visible after its last key has gone. Removing the Agent means deleting its user, which cascades to that row and its keys, the same operation that removes a person's account; the audit rows survive on `set null` beside the denormalized email and role. Suspending reuses the member-deactivation ban and keeps keys and grant.

**What would falsify this.** Three requirements would force a second path. When one arrives, it is a new decision that supersedes this ADR, not a branch added to the check.

- **Delegation**: a third-party agent acting *on behalf of a human*, which is the OAuth consent shape. The check would then have to intersect two principals, and `PermissionCtx` holds one `user`. Ruled out of this effort.
- **An Agent spanning Organizations.** `member` is per Organization, and `validateApiKey` resolves a key's Organization through the owner's default membership, with no organization argument. One Agent in two Organizations would be silently routed to whichever row sorted first. That is two Agents, or something new. A unique index on `member (user_id, organization_id)` stops the same Organization twice; one membership in total is `AgentsService`'s to keep.
- **Restricting one key below its Agent's grant.** If operators insist on it, keys stop being equivalent and the key becomes a principal, which is the per-key-statement option above.

**The tripwire that fires first** is a tool with no HTTP twin that needs a statement no route declares. `tool-permissions.spec.ts` makes that a frozen-list edit. Whoever makes it is starting agent-only permissions and should read this ADR before continuing.

**Pinned by** `test/rbac/agent-roles.e2e-spec.ts` (the three roles unlicensed, `service: ['call']` held by owner, admin and `agentCaller` alone, instance authority refused to an Agent written straight to `admin`, the role route), `test/agents/agents.e2e-spec.ts` (an Agent refused on REST and on every `/api/auth/*` endpoint, unable to sign in, an expired key kept), `test/coding-standards/member-role-writes.spec.ts` (one writer of `member.role`), `test/coding-standards/tool-permissions.spec.ts` (each tool against its twin, the ctx-first target, the frozen tool, row-scoped, ungated and no-twin counts) and `test/mcp/mcp-dispatcher-stages.e2e-spec.ts` (the permission refusal and the role-filtered `tools/list`, through the one check, and the empty `tools/list` and refused calls of an `agentCaller` key).

**Not a second path: ADR-0026's switch.** `requestedPreviewsAllowed` refuses a caller who holds `deployment: ['create']`, but it is a precondition on the Application, checked after the grant and applied to people and Agents alike. It never asks who the caller is. A rule that did, such as "only the requester may touch its preview", would be the path this ADR rejects.
