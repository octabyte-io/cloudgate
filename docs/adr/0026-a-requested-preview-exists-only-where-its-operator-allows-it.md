# A requested preview exists only where its operator allows it, and is reached through its parent's grant

A **Requested preview** is a Preview deployment that a caller asked for, usually an Agent, rather than one a pull request opened. It is a copy of one git-sourced Application built from a branch, running under its own `appName` and host until its expiry. Like every preview, it **inherits its parent's storage and environment** (ADR-0021, unamended). What is new is who can cause it. An `agentOperator` could already roll back or rebuild production, but only with code that has shipped before. A requested preview runs **unmerged branch code against production's volumes, binds and env**, with no pull request and no human review in between.

Cloudgate's answer: **a requested preview may exist only on an Application whose operator allows them.** `requestedPreviewsAllowed` is a boolean on the Application, `false` by default and backfilled as `false`. Writing it takes `service: ['update']`, which neither agent role holds, so no Agent can allow requested previews for itself. **Reach is the parent's grant and nothing else.** Asking for one takes `deployment: ['create']` on the parent. Every preview route already authorizes against the parent through `checkServiceAccess`. The requester is recorded, not checked.

**This is a precondition on the Application, not a second authorization path.** ADR-0023 rejects a check that asks *who* the caller is beside the grant. The switch asks what state the *resource* is in. It applies to a person who holds the grant exactly as it does to an Agent. It runs **after** the grant, so an ungranted caller gets the usual refusal and learns nothing about the setting. A granted caller gets `409 Requested previews are not allowed on this Application`, the same text over HTTP and MCP. The MCP tool list does not change per Application.

**The refusal order, as built**: the key, the rate bucket, the `deployment: ['create']` permission, the grant on the parent, the switch, input validation, and last the cap. The cap is last because it is the only step that changes with time, so a caller who waits it out never then learns its request was invalid. **One correction to the order as it was first written:** the request's *shape* (a branch git can check out, a whole positive TTL) is refused by the global validation pipe, which runs before the handler and so before the grant. That tells an ungranted caller nothing, because it reads nothing stored. The "input validation" step of the chain is the part that needs the Application and the instance: a branch-bearing source type, and a TTL within the maximum. `PreviewDeploymentsService.admitRequestedCreate` is the one place create's order is written. **Extend and redeploy do not call it, and neither reaches the cap**, since only create takes a slot. Each writes its own prefix of the chain: the permission, the grant on the preview's parent and the switch, then `409 This preview has expired and is being torn down; ask for a new one` for an expired preview. Extend goes on to validate its TTL against the maximum. Redeploy has no input to validate, and the switch and the expired refusal govern only a requested preview's redeploy.

**Considered options.**

- **The grant alone.** Rejected, because granting `agentOperator` on a production Application would silently mean "run any branch against production data".
- **Require `previewEnv`.** Rejected, because it proves the operator typed something, not that the preview is isolated. `previewEnv` replaces the env wholesale and is often a copy of production's. It would also give an existing column a hidden second meaning.
- **Refuse when the parent has mounts.** Rejected, because it misses the main hazard: the production database is usually a separate Service reached through env, not a mount. It would also refuse harmless config-file mounts.
- **Isolated storage (`previewMounts`).** Rejected as out of scope. ADR-0021 records what that answer would look like.
- **A requester-only rule**, under which an Agent may touch only the previews it asked for. Rejected, because it is a check on who a row belongs to, beside the grant, which is ADR-0023's rejected second path. And since a preview shares its parent's storage, "may reach the preview but not its parent" is not a meaningful grant.

**Consequences.**

- **The lifetime bounds the copy, not the reach.** A requested preview has an expiry chosen at create (60 minutes by default). It is refused over an instance-wide maximum (24 h by default, `requested_preview_max_ttl_minutes` on `web_server_settings`, which instance authority sets), and only an explicit extend moves it: `now + ttl`, under `deployment: ['create']`. A redeploy or a read never moves it. Once the row is gone, a call about it answers `404 Preview deployment not found`, with no tombstone. Losing the grant ends the reach; it does not end the copy. What "nothing outlives it" guarantees is the **running copy**. Its Deployments and audit rows are kept, under ADR-0020's retention.
- **One table, discriminated by trigger.** A requested preview is a `preview_deployment` row with `trigger = 'requested'`, a `requester` (`user`, `ON DELETE SET NULL`) and an expiry. The `pullRequest*` columns are nullable, under a check constraint that they are set exactly when the trigger is `pullRequest`, **and the expiry exactly when it is `requested`** — the build extended the constraint to the expiry, so the sweep can never select a pull-request preview and a requested one can never lack a clock. A second table would have to be taught to every reader of the first: `container-access.service.ts`, `previewTeardownSteps`, the cascade from Application and the audit resource type. That is the "second copy goes wrong" failure ADR-0016 and ADR-0018 record. A requested preview is identified by its own id alone, since two may build the same branch. Its printed link is every preview's: `https` only when a certificate of its Organization **on the same Server** covers its host. A certificate stored with no Server is written only to the platform host's Traefik, so it never covers a preview routed on a Server, whatever the first wording of the ticket said.
- **The two triggers have separate switches and separate caps.** `isPreviewDeploymentsActive` still governs only the pull-request webhook, and `previewLimit` counts only pull-request previews. `requestedPreviewLimit` (default 3, `service: ['update']`) counts requested ones, including an expired row whose copy is not yet gone. Nothing changes for an operator who never allows requested previews.
- **Turning the switch off refuses and never tears down.** From that moment, create, extend and redeploy are refused. Live previews run to their expiry and stay listed, so they can be deleted. A settings write never becomes a teardown across Servers that can stop halfway.
- **Expiry is a mark, and absence is the end.** ADR-0020's shape is reused: one instance-wide `@nestjs/schedule` cron, every minute, with no overlapping ticks.
  - The mark is `expired_at`, set once, beside its `expiry_cause` (`expiry` or `delete`). A check (`preview_deployment_expired_is_requested`) sets the two together and only on a requested row.
  - At expiry the sweep marks the row expired and cancels its builds, or waits them out once they are past the cancel window.
  - It then tears the preview down through `previewTeardownSteps`, on the machine that made each artifact (ADR-0018).
  - An unreachable Server leaves the row *expired, teardown pending*, retried until the copy is gone.
  - Deleting a requested preview **is** expiring it now, so a kill and a timeout leave by one path.
- **The platform is the actor when no caller is.** The sweep writes one `delete previewDeployment` row when the copy is gone, with `user_role = 'system'`, no user, no email (`audit_log.user_email` is nullable for this row alone, since a fixed address would be an identity the trail's email filter could match), and `user_name` Cloudgate. No Member may hold `system`, alone or inside a role list. The database refuses it on every `member` row (`member_role_is_not_the_platform`), and two checks refuse it before the database is reached: a role change or an invitation answers `403 The system role is the platform's own and no Member can hold it`, and no custom role can be named `system`. The Agent is named in metadata as *requester*, never as actor, so the row doesn't depend on the Agent still existing. A kill therefore writes two true rows: the caller's `delete` and then the platform's. This is the first audit row with no caller. The next writer that needs one reuses this shape rather than inventing a second.
- **The platform is also the actor that tells an operator its own sweep is stuck.** An expired row holds its slot until its copy is gone, so leftovers on a dead Server would quietly refuse every later create. One opt-in Notification, `preview-teardown-stuck` (off by default like every flag), fires **once per Server per episode**: when that Server's oldest pending teardown has been retried for 15 minutes. It names the Server, how many requested previews are stuck there and the Applications holding those slots, and it goes to the Server's own Organization. The platform host belongs to no one Organization, so there an episode is kept **per Organization**, and it goes to the Organization whose previews are stuck: no Organization hears about another's Applications. The episode closes when the Server has no pending teardown left. The mark is kept in memory beside the sweep, because the pending rows are the durable record: a restart re-arms the 15 minutes rather than firing. The sweep never waits on a sender. An expiry and a cap refusal notify nobody. Pinned by `backend/test/preview-deployments/teardown-stuck-episodes.spec.ts` (the episode, on the pass's injected now) and `requested-preview-expiry.e2e-spec.ts`, *the stuck-teardown Notification*.
- **An Agent's reach grows by six tools, on requested previews only.** `create_preview`, `list_previews`, `get_preview`, `extend_preview`, `redeploy_preview` and `delete_preview` each have an HTTP twin. `FROZEN_TOOLS` goes from 11 to 17 under ADR-0023, and a pull-request preview's id answers 404 on every one. ADR-0024 and ADR-0025 hold unchanged, and ADR-0024 is why the cap's refusal is the one text that differs from its twin's: a tool failure is fixed text, so where the HTTP refusal names the soonest expiry, `create_preview`'s points to `list_previews`, which lists each preview's `expiresAt`.

**What would falsify this.** Each of these is a new decision that supersedes this ADR, not a branch added to the code.

- **Isolated storage for previews.** If a preview can get storage of its own, the premise of the switch is gone. The switch should then be reconsidered rather than kept out of habit.
- **A requested preview of a Compose stack, or of a set of Services.** It needs a throwaway database, which crosses ADR-0021's line.
- **An expiry moved by activity**, such as a preview kept alive while it is in use. The row's clock would stop being a value anyone chose.

**The tripwire that fires first** is reach that differs from the parent's grant, e.g. "an Agent may touch only its own previews". It will be asked for, because it sounds like least privilege. It is ADR-0023's rejected requester check, and whoever builds it is starting a second authorization path.
