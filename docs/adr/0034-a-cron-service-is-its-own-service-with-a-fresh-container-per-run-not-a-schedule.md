# A Cron service is its own Service with a fresh container per run, not a Schedule

Status: accepted. Amends ADR-0017.

A Project config needs a way to say "run this command on a timetable", for example a `nightly-report` that runs `node dist/report.js` at 03:00 Berlin time, and to deploy that same file to a Server, AWS or GCP. **We make it a Service of its own, written `kind: cron`: a Cron service.** It has its own source, build, size, variable names, Config name and access entry, created and destroyed by a plan like a `web`, plus a required `command`, a five-field unix `schedule`, a `timezone` and a `timeout`. Each firing is a **run**, and every run starts a **fresh container** from the Cron service's last successful build, which exits when the command does, on every target: a one-off Swarm job on a Server, an ECS task on AWS, a Cloud Run job execution on GCP.

## Considered options

- **Reuse today's Schedules as the config's cron.** A Schedule (`backend/src/scheduling/schedules/`) runs a command with `docker exec` inside a container that is already running, or a script on a host, and belongs to a Service rather than being one. Rejected: a cloud has no "exec into the running container on a timer" (EventBridge Scheduler and Cloud Scheduler both start a fresh task or job), so a Schedule could not mean the same thing on every target, and one file must deploy anywhere. It also has no image, build, size or variables of its own, so it could not be the thing a plan creates and destroys. Schedules stay exactly as they are and stay Cloudgate's records, not config; both keep working side by side, and turning one into the other is out of scope because they can behave differently (shared state in the running container, the container's own environment).
- **A `cron` block nested under a `web`**, running in that `web`'s image. Rejected for this cut: it makes the cron a child of another Service, so it could not have its own size, variables, access entry or plan lifecycle. Sharing another entry's image can be added later as an extra field. The cost is named in the spec: right after a push, a Cron service can run older code than the `web` built from the same repository.
- **Reuse `SchedulingService` and the `cron` library for the Server's timetable.** Rejected: that library does not follow the AWS daylight-saving rule (it fires a missing time an hour late and can fire a repeated time twice). A Cron service works out its own fire times, with `croner` plus a check that skips a firing whose local time the timetable does not name. `SchedulingService` was left untouched; its own bug was fixed later by moving it off the `cron` library onto the same fire times (`backend/src/scheduling/fire-times.ts`), so Schedules and backups now follow this daylight-saving rule too.
- **A `docker run` or the Server's crontab** for each run. Rejected: the backend already fires Schedules and backups, and a Swarm job from the same spec a `web` deploys with gets its variables, size limits, network, registry login and placement for free, and its container is a Managed container.

## What it keeps in common with a Schedule

Both are timetables kept by Cloudgate's backend on a Server, so a tick missed while the backend is down is not made up. Both record each firing as a **Run record** with its own Deployment log, kept for the usual window (ADR-0020), in the same console feeds. Both may overlap (a run still going at the next tick does not stop the next one) and neither retries. Both can be paused by Cloudgate: a Schedule's `enabled`, a Cron service's per-Environment Stop and Start. Neither pause lives in the Project config.

## Consequences

- **ADR-0017 is amended.** A Cron service is stored like an Application, and a run hangs off the Cron service itself, marked as a run rather than a build. So the `application` parent is no longer only a build: a row with that parent is a Build deployment or, when marked as a run, a Run record. The two-writer split changes with it: the run recorder now also writes a row whose parent is a buildable Service (a Cron service), which the engine's `create` still never writes runs for. There is no hidden Schedule row and no new table. The test that the two writers partition the parent columns (`test/backups/run-recorder-parent.spec.ts`) must be updated to state the new split rather than deleted.
- Run now is `deployment: ['create']`, like Deploy; cancelling a run in flight is `deployment: ['cancel']`.
- Stop is the pause and stops a run in flight; Remove containers is not offered, since a finished run leaves no container; Delete takes the Service's Run records and logs with it (ADR-0016, ADR-0018).
- Every target must honour the same rules from the one file: refuse anything but five-field unix cron, skip a missing local time and fire a repeated one once, enforce `timeout` (Cloudgate enforces it itself where the platform has none, as on ECS), and never retry (Cloud Run's `maxRetries: 0`).

- **On AWS too, Cloudgate's backend fires the runs**: the same timetable starts each run as a one-off ECS task from the Cron service's task definition, and watches, logs, times out, cancels and recovers it as on a Server. EventBridge Scheduler was rejected: it would fire while Cloudgate is down, but nothing would enforce `timeout` then, the Run record would be rebuilt from ECS (which forgets a stopped task after about an hour), and it needs its own role and `cron()` translation. The cost is accepted: a run happens only while Cloudgate is up, on AWS as on a Server; a timeout is enforced late if Cloudgate is down when it falls due; and a task ECS has forgotten by the time Cloudgate is back ends as failed, result unknown.
- **Google Cloud follows AWS**: the same timetable starts each run as one execution of the Cron service's Cloud Run job, with no Cloud Scheduler.
