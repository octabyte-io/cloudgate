# A deployment log is kept for a fixed window and reaped by a sweep of the tree, not by the delete that destroys its row

ADR-0016 settled _when_ a machine-side artifact is reclaimed — by the delete that destroys the row naming it — and ADR-0018 settled _which machine_ and _what was left when it could not be_. Both of their non-goal lists end on the same item: _"every deployment log file"_, left where it was, with ADR-0018 adding that these _"want a retention decision before any teardown step — they are stranded from birth rather than by the cascade, since nothing in the product deletes a `deployment.logPath` on any path"_. This is that decision.

The state it is deciding from is total. `DeploymentsService.initializeLog` creates `{logsDirectoryOn(buildHost)}/{appName}/{deploymentId}.log` on the machine that runs the build, one file per Deployment, and **nothing in the product had ever deleted one**: there is no `delete(deployment)` anywhere in the tree, the only log cron rotates Traefik's own access log (`LogCleanupService`), and every Maintenance sweep on `CleanupService` is a `docker` prune that never touches the platform's tree. Every build log every Application ever wrote is still on its build host.

**Cloudgate keeps a deployment log for `DEPLOYMENT_LOG_RETENTION_DAYS` — 90 — and a nightly cron reaps what is older on the platform host and on every Server, by the file's age rather than by anything on its row.** `deployments/log-retention.ts` holds the window and the sweep; `DeploymentLogRetentionService` arms it.

## Why retention and not a step in the delete

Structurally this looks exactly like ADR-0016's question: a row cascades away and a file on a machine becomes unnameable. It is not that, and the difference decides the whole design. **The cascade is not what strands a log file** — nothing has ever deleted one, so a log is stranded from birth, and the population of unreclaimed logs on any existing install is overwhelmingly the logs of Deployments whose rows are _still there_.

So a delete-time reclamation would answer the wrong question twice over. It would silently make _"how far back can I look?"_ mean _"as far back as your oldest surviving Application"_ — a retention policy nobody chose, expressed as a side effect of an unrelated act. And it would leave every log already on disk under a since-deleted Application there for ever, because after the cascade there is no row left to hang a reclamation off.

The corollary is the mechanism: **the predicate is age on the file, and it is deliberately not status on the row.** A `find` over the logs tree reaches both populations at once — the logs whose Deployment rows are still there and the logs whose rows the cascade destroyed years ago — and it is the only predicate that reaches the second. A row-driven pass structurally cannot see them.

## Why one window, when a failed deployment's log is the one an operator re-reads

The obvious design is two windows: a short one for a Deployment that succeeded and a long one for one that failed, because a failed build's log is the one somebody comes back to. That asymmetry is _intended here_ and is delivered by the **size of the constant** rather than by a second mechanism, and the reason is that status lives only on the row while the sweep deliberately asks the tree:

- A row-driven pass cannot replace the sweep — it cannot see a log whose row is gone — so implementing status means a _second_ pass beside it, not a different one.
- Expressed as a second `find`, the short window would have to exclude the failed Deployments' filenames, and that exclusion list is unbounded in the number of failed Deployments in the gap between the two windows: a command-length failure on exactly the install that has the most logs.
- Expressed as a query, it needs each row's machine, which means a second copy of `DeploymentsService.resolveLogServer`'s five-parent fan-out with no `PermissionCtx` to scope it. Two copies of a "which machine" rule is the failure `buildHostServerId` and `preservedImageServerId` were each written to end (ADR-0018).

**90 days**, then, is the _failed_ log's window applied to every log. A quarter is the longest span over which an operator plausibly asks _"what did that build do?"_; a successful build's log would justify 30. The cost of the longer number is disk on the build host and it is small: a build log is the build's whole stdout, order half a megabyte, so an Application deploying three times a day holds ~140 MB at 90 days and a ten-Application install ~1.4 GB — against an unbounded tree today.

## Why a constant and not a setting

Neither existing surface is nearly free. `web_server_settings.logCleanupCron` is about _when_ the Traefik rotation fires rather than how long anything is kept, and it is instance-wide while these files sit on many Servers. `server.metricsConfig.retentionDays` is per-Server but is monitoring's own contract about metric samples the agent collects, and borrowing it would make a deployment-log window mean something to `MonitoringService`. What is left is a new column and a migration for a number nobody has asked to change. If one ever does, `web_server_settings` is where it goes, beside `logCleanupCron`.

## Consequences, all deliberate

- **The row and the file are two lifetimes, and the read says which it is looking at.** ADR-0007 makes `GET /deployments/:id/logs` answer _for the Deployment_, so a Deployment whose log has been reaped has to answer something coherent. `readLogs` ends its command `2>/dev/null || echo ""`, which has always made a missing file and an empty file the same answer — the right answer for a queued build (_"nothing written yet"_) and the wrong one for a log the platform deleted on purpose. The row's own `createdAt` separates them: past the window, an empty answer becomes a sentence naming the window (`reapedLogNotice`). **A `404` was rejected** — the Deployment exists and `ownerOf` resolves it, and this route already spends `404` on _"no such deployment"_, including the parentless row `run-history.e2e-spec.ts` inserts by hand; answering `404` for a row the caller can see in its own history would make one status code mean two things on one route. An unreadable `createdAt` reads as _inside_ the window, because telling an operator their log was reaped when the truth is that the route cannot tell is worse than saying nothing.

- **A file whose row cascaded away is reaped on the same rule**, which is the half no teardown step could ever have reached and the reason the sweep is a filesystem predicate.

- **The log-streaming socket says the same thing the read says, and says it as a _close_.** ADR-0007's `/listen-deployment` follows the same `logPath`, and for a reaped log it followed a file that was not there and streamed nothing — so the same Deployment read two ways disagreed about whether its log's absence was explicable. It was filed rather than fixed here and is fixed now: the gateway closes `4013` carrying `reapedLogNotice`'s own sentence, reusing both rather than restating either. **It asks the read's whole question, and the first fix shipped only half of it** — `isPastLogRetention` alone, where the read asks absence *and* age. That inverted the very disagreement this bullet is about: past the window with the file still on the machine — a nightly sweep, `-mtime +N` erring long by construction, and a Server unreachable at 04:20 skipped altogether — the read streamed the log while the socket said it had been reaped. A later fix made the socket confirm the file is gone, through a program that names its answer on stdout rather than an exit code, because `RemoteExecService` rejects on a non-zero exit and *the file is gone* and *no route to the host* must not arrive as the same rejection (`common/workload-presence.ts`' H-95). It probes only once the age test has passed, so the common case pays nothing, and an answer it cannot establish reads as *present* — never claim a log was reaped on the strength of not knowing. **A frame was rejected**, and not on taste: the console appends every string frame this socket sends into the log well, so a notice delivered as a frame renders as though the build had printed it, and no envelope rescues that — `realtime/terminal-protocol.ts` already refuses a server→browser envelope on the ground that applies here too, that a program may print any byte at all including the reserved one, so a frame the console must treat specially is a frame a build can forge. A 4xxx close lands on the console's refusal surface instead and stops the redial, which would only re-ask a question whose answer cannot change. The one cost, measured: a close frame's reason carries **123 bytes** (RFC 6455 §5.5, and `ws` throws rather than truncating) against the notice's **149**, so the socket's sentence is the route's elided at a word boundary — which keeps the clause naming the window, the half not discoverable from any route. `4013` sits with `4011` and `4012` in the band that is not a judgement of the request: this caller is entitled, the row resolved, and the answer is true.

- **The sweep names `*.log` under the logs root and nothing else.** The tree is the platform's, but "the platform's tree" is not a licence to delete whatever is in it: an operator's own file there survives, and — more to the point — so does any subtree the platform grows under `CLOUDGATE_DIRECTORY` later. This is ADR-0016's objection to a maintenance surface answered rather than repeated: that predicate failed because `<word>:v<digits>` is a _shape this platform may not claim_ on a shared Docker host, whereas `{logs}/{appName}/{id}.log` is a path only this platform writes, so an age predicate over it is safe with no naming row at all.

- **`-mtime` and not a stored timestamp**, for two reasons. It is the only such fact available on a Server that holds no database; and it makes a build that is still writing structurally unselectable, because its log's mtime is _now_ — which is why the sweep needs no lock and no coordination with the deployment queue. `find`'s `-mtime +N` is _strictly more than_ N 24-hour periods, so the window errs by keeping a log up to a day longer than the constant says.

- **One instance-wide cron that enumerates `server` when it fires, not one job per Server.** `DockerCleanupService` registers per Server because each carries its own `enableDockerCleanup` flag and its own notification target; retention has neither, so a job per Server would be N crons that always agree and a Server enrolled at runtime would need one registered for it. Enumerating at fire time is also what makes a Server added since boot swept on the next run. It runs at `20 4 * * *` — deliberately not the access log's `0 0 * * *` and not the docker prune's `50 23 * * *`, because this one reaches every Server and must not stack an unreachable machine's SSH connect timeouts on another sweep's.

- **Every Server, across every organization, with no `PermissionCtx`, and that is not a tenancy hole.** The sweep is not a read and returns nothing an organization owns: it names files under this platform's own logs root by age and deletes them, on machines this instance provisioned — housekeeping on the platform's own tree, in the same sense as `DockerCleanupService`'s boot re-registration over every `server` row.

- **Best effort per machine, journalled and never thrown.** An unreachable Server must not cost the machines after it, and nothing is waiting on the answer. The command prints what it reaped before deleting it, so the journal line is a count rather than a claim and a run that says nothing reaped nothing.

- **A shell `find` on both branches rather than `node:fs` locally.** `CleanupService.cleanMonitoring` uses `fs` because the monitoring store only ever exists on the platform host. Deployment logs are not like that — an Application that builds on a Server wrote its log there — so the sweep has to reach every machine, `execOnServer` already dispatches one command shape to both, and two mechanisms would be two behaviours to keep in agreement for no gain.

- **What this does not do.** It does not bound a single log's _size_: a runaway build can still write an arbitrarily large file inside the window, and the answer to that is a cap in the writer rather than a shorter window here. And it deletes no `deployment` row: history stays complete, and a Deployment past the window is a row whose log is gone rather than a row that is gone — which is the whole point of separating the two lifetimes instead of collapsing them.

- **Amended: the delete now reclaims too, and the sweep stays.** This ADR rejected a delete-time reclamation *as the answer* — alone it could not reach the logs whose rows were already gone, and it would have made "how far back can I look" a side effect of deleting. Neither objection applies to a delete removing *its own* owner's logs alongside the sweep: an operator who deletes an Application, a Compose stack, an Application schedule, a database backup or a volume backup has chosen that its history goes, and leaving `{logs}/{appName}` readable from no screen for 90 days serves nobody. So each of those five deletes and the Project/Environment cascade now `rm -rf` that directory on the machine its writer chose — and a Service delete (Application, Compose stack, any database engine, and the cascade over them) does the same for the schedules, backups and volume backups whose rows cascade from it, each under its own `appName` on the Service's run Server (`common/run-log-owners.ts`) (`common/teardown-steps.ts`' `reclaimDeploymentLogs`, one path expression shared with the writers, `deploymentLogsDirectoryOn`), after any presence refusal, and name it as `kind: 'deployment-logs'` in `unreclaimedArtifacts` when the machine would not give it up. The sweep remains the answer for everything the delete cannot reach — logs on a machine that was unreachable at delete time, logs an Application wrote on a build Server it has since moved off, and every log whose owner is still alive.
