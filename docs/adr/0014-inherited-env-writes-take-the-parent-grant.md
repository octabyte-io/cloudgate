# An inherited env write is bounded by the grant that names the parent, not by the narrowest entitlement beneath it

A Project and an Environment each own an `env` column that every Service beneath it reads at deploy — "inherits" is the shorthand this decision's title keeps, and the glossary deliberately no longer uses it, because the platform never merges the levels: `prepareEnvironmentVariables` (`docker/docker.utils.ts`) takes the Service's own env, its Environment's and its Project's, and resolves every `${{project.KEY}}` and `${{environment.KEY}}` reference against the two parent rows — for a Service's container env, for a Compose stack's `.env` and its `env -i` prefix, for a Database's env, and for a build's `--build-arg` and `--secret` flags. So `PATCH /projects/:id` and `PATCH /environments/:id` write one row whose effect lands on rows the caller may not be entitled to at all: `checkProjectAccess`'s row-level branch consults `accessedProjects` alone, `checkEnvironmentAccess`'s consults `accessedEnvironments` alone, and neither knows anything about `accessedServices`. A caller holding `project: ['update']` and **one** Environment of that Project can change what every `${{project.KEY}}` reference in every other Environment resolves to at its next deploy — a refused Service's `DB_PASSWORD=${{project.DB_PASSWORD}}` included — and, because an unresolvable reference *throws*, can fail another Environment's next deploy outright by renaming or removing a key it referenced. The permission change fixed the *level* on both routes (a write claims `update` rather than riding on a read) and left this question open; the ticket asking it complained is not the reach so much as that nobody had decided about it.

Cloudgate's answer: **the grant means what it says.** Holding `project: ['update']` is authority over everything under that Project, and `environment: ['update']` is authority over everything in that Environment. The entitlement columns partition *reads and direct writes*; they do not bound what an inherited value reaches, and this decision declines to make them do so. Nothing narrows: no new entitlement check stands in front of either route, and `prepareEnvironmentVariables` is unchanged. What changes is that the blast radius is now stated where somebody meets it — in the two statement docblocks, in the operator-facing notes on `PermissionService.checkProjectAccess` and `checkEnvironmentAccess`, at `prepareEnvironmentVariables` itself, and on the roles screen, which previously offered the grant with nothing on it to say how far the grant reached.

The alternative was to **bound an inherited write by the narrowest entitlement**: require entitlement to every Environment and Service that inherits the row before `project.env` may be written. It is defensible — it is what the entitlement columns look like they promise — and it is rejected because it makes a common operation fail in ways that are hard to explain. The natural use of a Project-level variable is to hold the one value every Environment shares, so the operator who most wants to write it is the one entitled to a subset; they would meet a 403 on a Project they can see, name and administer, and nothing in the refusal could name *which* of the rows beneath it they lack, because saying so would make the route an oracle for a Project's shape (§2.2, ADR-0008). The failure would also move with the data rather than with the role: adding an Environment somebody else may not reach would silently revoke a grant that worked yesterday. A third option — making inherited variables a separately-gated operation rather than a parent-row write — was rejected because the finer grain is not wanted, and two statements that tried to express it (`projectEnvVars`, `environmentEnvVars`) sat unconsulted in `statements` for their whole life.

Consequences, all deliberate:

- **The base member role holds neither `project: ['update']` nor the ability to reach it.** The permission change's one narrowing of a static role stands and is the other half of this decision: a *member* does not get an authority this wide, so the grant is held by an owner, an admin, or a licensed custom role somebody deliberately gave it to. `memberRole` keeps `environment: ['update']`, because there the grant is per Environment and names exactly the rows the write reaches.
- **The roles screen says so, and that copy is load-bearing rather than decoration.** `permission-grid.tsx` annotates the `project` and `environment` rows with what the update reaches, because a toggle whose name is "Projects — update" reads as authority over a Project's own row. Removing the note would put the screen back in the state the issue objected to.
- **It is not a licence to widen the next channel, and the sweep asked for alongside it says why that matters.** This decision is about the two `env` columns, whose reach is the product feature — a child is *meant* to see a parent's value. On the Project and Environment rows themselves `env` is indeed the only fan-out: a rename reaches nothing a child derives, because `appName` is fixed at create and is immutable on update, and the names are read only into notification payloads. But elsewhere the sweep found six writes with the same shape — a per-row entitlement column exists and the write's effect crosses it — none of them an inherited value: a Service's `registryId`/`gitProviderId`/`customGitSSHKeyId` (the platform then authenticates with a credential row the caller may hold no statement for), a volume backup's and a restore's caller-named `volumeName`, a database restore's arbitrary `backupFile` key, a Mount's `hostPath`/`volumeName`, and a published host port. They are recorded rather than decided here: each is a *side effect* of a write rather than a value a child asked for, so none of them can cite this decision, and the answer that fits `env` is not obviously the answer that fits a credential pointer.
- **The refusal a narrower role meets is still the same refusal.** A role holding no `project` action is refused `PATCH /projects/:id` by `checkPermission`, and a member whose row does not name the Project is refused by the row-level branch; both answer 403. (The row-level refusal now carries `code: PROJECT_ACCESS_NOT_GRANTED` / `ENVIRONMENT_ACCESS_NOT_GRANTED` so the console can point at Manage access instead of the role; it still never tells an unentitled id from an absent one.) Nothing here adds a third kind of refusal, which is what bounding the write would have needed.
- **A future change should not "correct" this by adding the entitlement sweep.** The sweep is the rejected option, not a missing one, and the paragraph above is the reason. What *would* re-open the decision is inherited variables gaining a second reader — something that consumes a parent's `env` without a child's own reference asking for it — because the mechanism this decision reasons about is a substitution into a reference the child wrote, not a merge into rows the child never opted into. Both halves of that are pinned by `test/docker/docker.utils.spec.ts` rather than left to this paragraph: the output pairs are the service's own keys, and an unresolvable reference throws.
