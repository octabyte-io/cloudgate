# An existing database is used as given, never changed, and left on Delete

Status: accepted. Built for a `postgres` on AWS: the place is an `existing_database` row beside the postgres Service, the lookup a `tofu plan` of `data` sources only (`aws/definitions/existing-postgres-lookup.ts`), judged in `aws/plan-reader/existing-postgres.ts`. Built for a `bucket` on AWS: the place is the bucket row's `existing` flag beside its Cloud account and region, the lookup `aws/definitions/existing-bucket-lookup.ts` (the account's buckets in the region, then the bucket's tags), judged in `aws/plan-reader/existing-bucket.ts`; a task role's permissions boundary covers the objects of any bucket in the Cloud account's own AWS account (`s3:ResourceAccount`), so a linking Service reaches one with any name, and never another account's.

An Environment may use a database the operator already has, for example an RDS instance `acme-prod` made by hand in the AWS console, without changing the Project config. **We make it a Database Service whose place is "an existing database", and Cloudgate only reads it.** The operator gives its identifier, the login the apps use, its database name (or, for a cache, its token and whether TLS is on). Cloudgate looks up its address through an OpenTofu `data` source at every plan, hands out the usual Outputs (ADR-0031), and never changes it: it makes no database or user inside it, never opens its security groups, and its Delete removes only Cloudgate's own records, with no snapshot and no "also delete its data". One that carries Cloudgate's own tags, so one another Environment's Cloudgate made, is refused.

## Considered options

- **A setting on the Environment, keyed by Config name**, beside the Services. Rejected: a Service row is already what a plan matches, what hands out Outputs and what has a page and a Delete; a side setting would need all of that again. A Service's place is already fixed at creation, so this is one more kind of place.
- **Cloudgate logs in as admin and makes its own database and user** from the config's `database` and `user`. Rejected: the runner is on the platform host and a cloud database is never public, so it would need a task inside the cloud just to run SQL, an admin password, and a cleanup on Delete that can fail halfway.
- **Only inside the Environment network.** Rejected: the Environment network is always Cloudgate's own, so a database made before it would almost never qualify, and that is the case this exists for. One in another network needs the operator's "I made it reachable" tick instead, which Cloudgate cannot check.
- **Point at another Environment's Cloudgate-made database.** Rejected: it would bring back shared database servers (dropped 2026-10-16) without the owner/user guard, and a Delete of the owner would break the user silently.

## Consequences

- The config's `database`, `user`, `size` and `version` are not applied in an Environment that uses an existing database; the plan says so, and a different major version is a note, not a refusal.
- A switch between a Cloudgate-made and an existing database is asked for on the Service's page and kept as a `database_switch` row by Environment and Config name until an Apply makes it. It is a pending choice, not the place the first option above rejects. No data is copied either way: a Cloudgate-made instance keeps its destroy guard and final snapshot, and an existing one is left untouched. From an existing database to a Cloudgate-made one is one plan and one Apply: the destroy only drops Cloudgate's records, so the create runs in the same Apply. From a Cloudgate-made database to an existing one takes two Applies. The first plan shows both the destroy and the add, but the instance's Delete is a Cloud run that ends after the Apply, and while it runs the name is still taken. So that Apply runs the Delete and marks the add failed, keeping the switch, and the plan after the Delete has finished adds the existing database. **Amended: this said a switch either way was one plan. The operator accepted two Applies for a switch to an existing database, rather than let two rows share a Config name or rename the departing one.**
- A lookup that finds the database at a new host or port does not save it: the plan shows the Output change and redeploys what links to it (ADR-0031), and its Apply saves the address before those redeploys. One that finds nothing marks the Service, whose page says "AWS cannot find" it, until a lookup finds it.
- On AWS only node-based ElastiCache with cluster mode off is accepted, so the `redis` Outputs stay one form.
- A Server Environment and a bucket (slice 5) take the same shape: a Server's address is typed with no lookup and always needs the reachability tick.

## Amendment: on Google Cloud the Service owns its private address, and reach is checked, not ticked

An Environment network on Google Cloud is peered with nothing (ADR-0042), so a hand-made instance is reached only through a **Private Service Connect endpoint in the Environment network** that points at the instance's service attachment. **Cloudgate makes that endpoint, keeps it in the Service's own state, shows it in the plan with its cost (about $7.30/month each) and deletes it with the Service.** It is Cloudgate's own piece on its own side, so "never changes it" still holds: the instance's settings are untouched. Google's automatic connections (`psc_auto_connections`) were rejected because they are set on the instance.

- **Kinds:** a Cloud SQL `postgres` (one endpoint) and a Memorystore for Valkey `redis` with cluster mode off (two endpoints). Memorystore for Redis has no Private Service Connect and Redis Cluster is cluster mode, so both are refused; reaching them would need a peering and reopen ADR-0042.
- **What the operator gives:** the instance's connection name (`project:region:instance`; `project/region/instance` for Valkey), in the Environment's region, plus a `postgres`'s login as on AWS. The instance may sit in another project; the operator then grants Cloudgate's service account read on it (`roles/cloudsql.viewer` or `roles/memorystore.viewer`), and the form shows the command.
- **No reachability tick on Google Cloud:** Cloudgate can check. The plan refuses while the Environment's project is not on a Cloud SQL instance's allowed consumer projects (the command shown keeps the projects already listed, since Google's replaces the list); after the Apply the page says so when the endpoint is not accepted. A Valkey instance needs the operator to register the two endpoints on it, which Cloudgate cannot do without changing it: the page shows the exact `--add-endpoints` command and "waiting for registration" until a read finds both registered. Linked Services deploy without waiting.
- **Outputs:** a `postgres`'s host is the instance's own `<id>.<hash>.<region>.sql.goog.` name (the one its certificate carries), **exactly as Google reports it, trailing dot included**, with `?sslmode=require`, and its `ca` the server certificate the instance reports; no certificate rotation is asked for. The certificate names no IP, so Cloudgate makes a private DNS zone for exactly that name, bound to the Environment network, whose record points at the endpoint; it sits in the Service's state with the endpoint, is shown in the plan with its cost and goes with the Service's Delete. The name is read each plan (a change is a change of address), and an instance reporting none is refused. Amended: this replaced the endpoint's IP after a live walk showed node-postgres fails on it, and a live check confirmed it. The certificate's name carries the same trailing dot, and libpq's `verify-full` compares names letter for letter, so it fails without the dot and connects with it (Node ignores it either way); the amendment keeps the dot rather than strip it. The same rule, the name exactly as Google reports it, holds for a Cloudgate-made instance's `….sql-psc.goog` host; libpq there is checked separately. A Valkey's TLS and login mode are read, not typed: only `AUTH_DISABLED` is accepted (token and IAM login refused, ADR-0042), so it hands out no `password`, and `rediss://` with the instance's own `ca` when TLS is on.
- **Refused, each naming the fix:** not found or not readable; not the Service's kind; another region; Private Service Connect off (Google's patch command, about 8 minutes and 45 s of downtime; a public-IP-only instance needs a private IP first); the Environment's project not allowed; client certificates required; a Valkey below maintenance version `MEMORYSTORE_20251210_02_00`; Cloudgate's own labels. A different major version stays a note.

## Amendment: on Google Cloud an existing bucket's access is one line the operator adds and Cloudgate checks

On AWS a linking Service reaches an existing bucket through its task role, which never touches the bucket. On Google Cloud a bucket's access is held only on the bucket or its project, and a Cloud Storage bucket is reached by its own HMAC key (ADR-0032), so the key's service account needs a grant **on the bucket**. **The operator adds that grant; Cloudgate shows the command and checks it, and never changes the bucket.** Cloudgate adding and removing the grant itself was rejected: it would break "never changes it" and work only in the Environment's own project. Refusing an existing bucket on Google was rejected as needless.

- **What Cloudgate makes:** the bucket Service's own service account and one HMAC key, in its own state, shared by every linking Service and rotated from the console, exactly as for a Cloudgate-made bucket on Google. The plan shows them at $0/month and the line that the bucket is used as given.
- **The grant:** after the Apply, the page shows `gcloud storage buckets add-iam-policy-binding gs://<bucket> --member=serviceAccount:<its account> --role=roles/storage.objectUser` and "waiting for access" until a list of one file with the key succeeds. Linked Services deploy without waiting. Whenever the page reads the bucket and the test fails again, it shows "no access" with the same command; a plan is never refused for it.
- **Which buckets:** any project and any location. In another project the operator also grants Cloudgate's service account `roles/storage.legacyBucketReader` on the bucket so every plan can look it up, and the form shows the command. A location that does not hold the Environment's region is a plan note (slower, and charged between regions), not a refusal. Refused, each naming the fix: not found or not readable; requester pays (the S3 SDK cannot name a paying project); Cloudgate's own labels.
- **Delete** leaves the bucket and its files as they were, with no "also delete its files", and always destroys the service account and key. The grant the operator added is left, now naming a deleted account that gives nobody access; the Delete report names it with the exact `remove-iam-policy-binding` command.
- **A switch** between a Cloudgate-made and an existing bucket copies AWS: chosen on the Service's page, kept until an Apply, no files copied, a Cloudgate-made bucket that holds files kept and named in the report.
