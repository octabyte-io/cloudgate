# Session revocation is addressed by session id, not by session token

better-auth keys revocation by token: `revokeSession` takes `{ token }`, looks the row up by it, and deletes it. Its `listSessions` answers with the `session` rows verbatim, token column included, and Cloudgate exposed both shapes as they came, so `GET /users/me/sessions` handed the caller a live bearer credential for every other machine the same user was signed in on, and the account screen pulled all of them into the browser. The token *is* the session; there is no weaker sense in which it identifies one. It was on the wire for exactly one reason: revocation needed it back, so the client had to be given it first.

Cloudgate instead **addresses revocation by `session.id`**. `POST /users/me/sessions/revoke` takes `{ sessionId }`; the service resolves that id to its token with a single query scoped to the caller's `userId`, and hands the token to better-auth's `revokeSession`. The token never leaves the server. This inverts the same way ADR-0007 inverted the deployment log's `logPath`: a credential on the wire can only ever be protected negatively — every future reader of the listing inherits an obligation not to log it, cache it, or put it in a URL — whereas an id carries no authority at all, and the one place that needs the token is the one place that already has the database.

Consequences, all deliberate departures from the auth library's own shapes, which a future change should not "correct" back:

- **This is a knowing divergence from ADR-0001.** That decision commits to reusing better-auth rather than rewriting auth, and it still holds everywhere it matters here: better-auth still decides which sessions a caller may see, still owns the session table, still performs the delete, and its `databaseHooks.session.delete.after` still writes the logout entry to the audit trail — which is why the revoke goes through `auth.api.revokeSession` and not a `db.delete`. What is *not* reused is the wire shape of two endpoints. "Reuse the library" was never "publish whatever the library returns"; ADR-0001's own wording is about session semantics and schema compatibility, and both survive untouched — the `session` table still has its `token` column, and a client that talks to better-auth directly is unaffected. Restoring `{ token }` to be closer to better-auth's shape would re-open the hole, not fix a drift.
- **The listing is an allowlist, not a subtraction.** `SessionSummary` names its six fields — `id`, `userId`, `userAgent`, `ipAddress`, `createdAt`, `expiresAt` — and a mapper builds each one. Deleting `token` from a passthrough, or typing it as `Omit<Session, 'token'>`, would be correct only about the fields that existed the day it was written: better-auth renaming the column, or any plugin adding one to `session`, puts a field nobody chose back on the wire and no type error says so. `updatedAt`, `activeOrganizationId`, `activeTeamId` and `impersonatedBy` are dropped for the weaker reason that no client reads them. The e2e test asserts the **exact key set** rather than the absence of one name, for the same reason.
- **Not-owned and not-found are one refusal, and it is a refusal.** Both are `404 Session not found`, byte-identical but for the timestamp, so the route is not an oracle for whether a session id exists. This is ADR-0007's single close code and ADR-0008's one-close-code-per-denial restated on HTTP, where §2.2 already reads a row outside the caller's scope as a 404 rather than a 403. It falls out of the implementation rather than being layered on it: one `where(id AND userId)` cannot tell the two cases apart, which is the shape to keep — a later "helpful" distinction would have to be added on purpose, and would be visible as such.
- **That the two cases are indistinguishable is better-auth's behaviour too, but better-auth reaches it by lying.** better-auth 1.6.23's `revokeSession` guards its delete with `if (findSession(token)?.session.userId === ctx.context.session.user.id)` and then returns `{ status: true }` regardless — a token that does not exist and a token belonging to somebody else both get a success answer for a revocation that did not happen. Uniform, and useless: the console would show a session it had just been told it revoked. The 404 keeps the indistinguishability and drops the falsehood, which is the half worth having.
- **better-auth's ownership check survives as defense in depth, not as the boundary.** Its condition can now only ever be true, because the token handed to it was selected by `userId` in the first place. It stays because a redundant check that can only ever agree costs nothing, and because a future upstream that turns that silent branch into a distinguishable error would find the case already unreachable from here.
- **The wire contract broke once, on purpose.** `{ token }` is no longer accepted, and the listing's `token`, `updatedAt` and `activeOrganizationId` are gone. Nothing was lost: the console's Revoke button sat in a table row that already held the session's `id`, and it was passing the token only because the endpoint asked for one.
- **The route stays `POST .../sessions/revoke` rather than becoming `DELETE .../sessions/:id`.** The id is in a body, not a path, which is the one thing here that reads slightly against §2.2's shape for a nested resource. Changing the method and path would be a second, unrelated break of the same contract in the same release, and revocation is a named action on a session rather than a delete of a row the caller may address — the row is better-auth's, and the endpoint's answer is `{ status: true }`, not the deleted entity. Worth revisiting only if the sessions surface is reshaped for its own reasons.
- **The API-key listing is a separate credential and a separate issue**. `@better-auth/api-key`'s `listApiKeys` already answers with `start` and never the key — the shape this decision brings sessions into line with, and the reason the fix here is a projection rather than an argument about whether a listing may carry secrets.
