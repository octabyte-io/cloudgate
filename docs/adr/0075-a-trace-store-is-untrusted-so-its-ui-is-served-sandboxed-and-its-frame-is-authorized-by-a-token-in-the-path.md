# A Trace store is untrusted, so its UI is served sandboxed and its frame is authorized by a token in the path

Status: accepted. Amends [ADR-0028](0028-a-traced-service-gets-its-own-trace-store-on-its-own-server-read-only-through-the-backend.md)'s consequence on the store's Content-Security-Policy. Builds on [ADR-0012](0012-sockets-hold-an-authorization-lease.md) and [ADR-0023](0023-an-agent-is-a-member-authorized-by-the-one-check.md).

ADR-0028 framed a Service's Trace store same-origin with the console, with no `sandbox`, and held off XSS with a policy of `script-src 'self'` plus the hashes of the inline scripts in the head of the page it forwarded. That treats the store as trusted: the hashes were computed from whatever the store sent, and any non-page answer (a script, whatever its content) was served from the console's origin and so counted as `'self'`. The store runs on the Service's own Server. On the **Hosted instance** that Server is the customer's, root included, so a customer can replace the store with any HTTP server and run any script on the console's origin, with the session of whoever opens the Traces tab. That viewer can be Octabyte staff the customer invited, whose session carries instance authority in the Instance organization (host shell, Traefik settings, every Organization through the Operator page). On a self-hosted instance the same holds for any Member who has root on a Server but not the instance's authority.

## Decision

**The Trace store is untrusted. What it serves runs in an opaque origin, so it can never act with the viewer's session, and the frame's requests are authorized by a short-lived frame token in their path instead of the cookie.**

- **Every answer the proxy forwards from the store is served under `sandbox allow-scripts allow-forms allow-popups`**, a directive of the one policy (`traceStoreContentSecurityPolicy`), a page or anything else, an error included. No `allow-same-origin`, so the document is in an opaque origin and cannot read the console or use its cookie; no `allow-top-navigation`, so it cannot take over the console. It is a response header, so a store page opened outside the console's frame is sandboxed too. The console's `<iframe>` carries the same flags. The inline-script hashes stay, because Jaeger's head scripts need them to run, and the rest of the policy stays as defence in depth against an XSS through span data, but nothing relies on the hashes for safety: the store chose the page they are computed from.
- **A frame token authorizes the frame.** The sandboxed document is cross-site, and the session cookie is `SameSite=Lax`, so none of its requests carry the session. `GET /traces/:serviceId/frame` mints a token under exactly the check the proxy used to make with the session (`service: ['read']` on the route, then the entitlement to that Service, ADR-0023's one check) and answers the UI's base path under it, `/backend/traces/<serviceId>/ui/t/<token>`. The token is HMAC-SHA256-signed under a key derived from `BETTER_AUTH_SECRET` with a label of its own, so no new secret is configured. It names the Service, the Member, the Organization they were acting in, and the credential they were recognised by (a session or a Personal key, by id), and it expires 15 minutes after it is minted.
- **Every framed request re-runs the authorization.** The proxy route is `@Public()`, since there is no session to find, and before anything reaches the store it checks the token (this Service's, signed here, unexpired), re-reads the credential by id (`AuthService.assertCredentialAlive`: revoked, expired, banned or acting in another Organization is refused, ADR-0012's rule) and re-runs the one check as that Member. A withdrawn entitlement, a removed Member or a sign-out ends the frame at its next request, not at the token's expiry. Only reads are forwarded, as before.
- **The token stays on every URL the UI builds.** Jaeger writes its configured `base_path` into its page's `<base href>`, and builds every asset and API URL from that `<base>`. The store keeps that base path; the proxy rewrites every whole use of it in a page, and in a `Location`, to the token's base path, and strips the token on the way to the store. A page is therefore decoded, rewritten and sent uncompressed, with `cache-control: no-store` since it names one viewer's token.
- **The frame's requests are answered to any origin and never with credentials.** Its module scripts, fonts and fetches arrive with `Origin: null`. Forwarded answers carry `access-control-allow-origin: *` and no `allow-credentials`, and the global CORS policy answers a frame path's preflight the same way (`TRACE_STORE_FRAME_CORS`) and keeps its allowlist everywhere else. The store's own CORS, `referrer-policy`, `clear-site-data` and `service-worker-allowed` headers are dropped, and every answer is `referrer-policy: no-referrer`, so the token is not sent onwards.

**Considered options.**

- **Keep the frame same-origin and tighten the hashes.** Rejected: the store writes the page and every script it loads, so no policy computed from what it sends can tell its scripts from an attacker's, and pinning hashes ties every store image to a backend release.
- **A separate origin for the store's UI.** Still rejected, as in ADR-0028: a self-hosted install has one host and one certificate. The sandbox gets an opaque origin without a second host.
- **A cookie scoped to the proxy path.** Rejected: a sandboxed document's requests are cross-site, so a `Lax` or `Strict` cookie is not sent, and a `SameSite=None` one would be sent on every cross-site request to that path, which is what CSRF defences exist to stop.
- **A longer-lived token.** Rejected: the re-check on each request bounds what a token can do, but the token is in a URL, which ends up in history. The console asks for a new one a minute before it expires, which reopens the frame on its search page.

## Consequences

- **The token is readable by whatever the store serves**, since it is in the frame's own URL, and so are the ids it names (Member, Organization, session or key). It grants only reads of that Service's own store, which whoever controls the store already has. An id is not a credential (ADR-0009).
- **A popup the store opens is still sandboxed**, since the flags have no `allow-popups-to-escape-sandbox` and the header is on every answer. A popup that navigates to another console path is a top-level `GET`, which a `Lax` cookie does go with, but its document is in an opaque origin and cannot read what comes back. A `GET` that changes something would be its own defect.
- **The UI runs without storage of its own.** An opaque origin has no `localStorage` or cookies. Whether every part of the store's UI copes with that is checked in a browser against a real store, not by a unit test: a part that does not fails inside the frame and nowhere else.
- **The route-permission census lists the proxy** as an undecorated `@All` whose gate is `TracesService.proxy`'s, and the audit census still names it as a read it does not record.
