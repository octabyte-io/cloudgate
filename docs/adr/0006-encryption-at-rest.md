# AES-256-GCM at-rest encryption keyed from APP_ENCRYPTION_SECRET

Sensitive columns (SSH keys, tokens, database passwords) are encrypted at rest with AES-256-GCM. The key is derived as `HMAC-SHA256(APP_ENCRYPTION_SECRET, "cloudgate:db-encryption:v1")` — a single dedicated secret (≥32 chars, enforced by env validation), not derived from `BETTER_AUTH_SECRET`, and with no fallback key chain, because Cloudgate has no legacy ciphertext that an older key would have to decrypt. The wire format is `enc:v1:` + base64(iv(12) ‖ authTag(16) ‖ ciphertext); the prefix makes values self-describing and versions the scheme for future rotation. Schema code never encrypts by hand — use the `encryptedText` column type from `backend/src/db/columns.ts` (services can use `EncryptionService` for non-column values). Decryption failure throws (no fail-open passthrough of ciphertext); plaintext values without the prefix are passed through on read, so legacy/imported rows are re-encrypted on their next write.

**Extended: an encrypted column cannot be looked up by value, and that is part of this decision rather than a detail of it.** AES-256-GCM under a random IV encrypts the same plaintext to different bytes every time, and drizzle applies a column's `toDriver` to the bound parameter as well as to the stored value — so `where col = $1` compares one ciphertext against a freshly minted one and matches nothing, whatever the value. Classifying something as a secret and giving it `encryptedText` or `encryptedJson` is therefore also a decision to move every equality lookup on it out of SQL and into the process. The rule has now cut both ways in this tree: better-auth's `session.token`, `apikey.key` and `verification.value` are exempt from encryption *because* looking them up by value is the only thing anything does with them (`test/coding-standards/secret-bearing-columns.spec.ts`), while `MetricsConfig.server.token` was encrypted and its lookup moved into `NotificationsService.receiveServerThreshold`, which had been asking SQL `metrics_config -> 'server' ->> 'token' = $1`. A value that must be found by its own contents and cannot be moved wants a hash, not this scheme.

**A `jsonb` blob whose secret is one member is converted whole, not split apart.** `encryptedJson` takes the structure and makes it one opaque text value; the alternative is to lift the secret field into an `encryptedText` column of its own and leave the rest as `jsonb`. The metrics-config change weighed both for `metricsConfig` and chose the blob — `src/servers/server.schema.ts`' `MetricsConfig` docblock carries the argument in full, and it is not "encrypt less is better": splitting changes a shape the console and two DTOs mirror, and it leaves two columns that must agree about a value an authentication check reads. The narrow change is right only when something still needs the non-secret fields in SQL, which is the question to ask first — and the answer decides the column type, not the other way round.

**The mechanics of that conversion, because `drizzle-kit` gets one of them wrong.** `jsonb` → `text` is real DDL, and the *type change* is the half `drizzle-kit` emits correctly: a bare `ALTER TABLE … ALTER COLUMN "col" SET DATA TYPE text` **succeeds** on a `jsonb` column. Postgres has no `jsonb` → `text` entry in `pg_cast` at all and reaches a string-category target through the source type's output function instead (coercion via I/O, allowed in assignment context) — which is the same path `::text` takes, so the two produce byte-identical text, and a `NULL` row stays `NULL` either way. **Amended: this paragraph said the opposite, and the opposite does not reproduce.** Measured directly on PostgreSQL 17.11 — with a `jsonb` default present and absent, over a populated row and a `NULL` row, and byte-compared against the `USING` form — so `0065`'s `USING "metrics_config"::text` is belt-and-braces rather than the cast Postgres demanded, and `0066` carries no `USING` clause. The error the old sentence was quoting is real but belongs to the *other* direction: `text` → `jsonb` bare answers *cannot be cast automatically … You might need to specify "USING c::jsonb"*, because coercion via I/O into a non-string type is only allowed as an explicit cast. Two obstacles a `USING` clause would not have fixed either, both absent from the two converted columns: an index over the `jsonb` column fails the change outright (*data type text has no default operator class for access method "gin"*) and has to be dropped, and leaving the old default in place lets the `ALTER` carry it across but re-renders it as `jsonb`'s canonical text — `{"a": 1}` where the migration wrote `{"a":1}` — which is the reason to `DROP DEFAULT` first rather than distrust. The real `drizzle-kit` defect is that default: a `customType` with an object `.default()` is outside what it serializes, so it writes `SET DEFAULT [object Object]` — hand-correct the emitted file (`drizzle/0065_encrypt-metrics-config.sql` is the worked example) and leave the snapshot as generated. **The default stays plaintext, and must**: a ciphertext baked into DDL is tied to whichever `APP_ENCRYPTION_SECRET` generated the migration and is undecryptable on every other instance, so a default may only ever hold a value that is not a secret. **No data migration re-encrypts in place, and none can.** The key is derived in the Node process; `db:migrate` is `drizzle-kit migrate`, which replays `.sql` and nothing else, and no install has `pgcrypto` — AES-256-GCM is not expressible in a migration file. The pass-through in the paragraph above is what makes that safe rather than a gap: a converted column reads a legacy plaintext row as the object it always was, every write afterwards goes through `toDriver` so no path produces new cleartext, and the residue closes on the next save. A secret that was already in a `pg_dump` wants rotating rather than re-encrypting, and rotation is a write.
