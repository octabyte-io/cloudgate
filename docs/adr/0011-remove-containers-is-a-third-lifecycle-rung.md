# A compose stack gains a third lifecycle rung rather than Stop changing meaning

A volume cannot be restored while any container still references it — Docker's volume refcount counts exited containers, and `docker volume rm` refuses regardless of `--force`. Of the five stop paths in this codebase only one leaves a container behind: an Application scales its swarm service to zero, a Database does the same, a Compose stack of the `stack` type runs `docker stack rm`, and all three leave nothing holding the volume. A Compose project of the `docker-compose` type runs `docker compose stop`, which leaves its containers `Exited` and still attached. So its volume restore refused, its own printed instructions said to press Stop, Stop did not clear the refusal, and the only control that removed the containers — Delete — destroyed the Cloudgate row with them. The feature was unreachable for that one service type, and completing a restore required a shell on the host.

Cloudgate answers this with a **third lifecycle action, "Remove containers"**, sitting between Stop and Delete: it removes a project's containers and nothing else, leaving the network, the project directory, the volumes and the row intact, so the round trip is Remove containers → restore → Start.

The alternative was to make `docker-compose` Stop remove containers too, which would make Stop mean one thing across all types and needs no new vocabulary. It is rejected, and a future change should not "correct" it back: `docker compose stop` followed by `start` preserves container identity and the writable layer, while removing and recreating does not. Changing Stop would silently degrade an existing, legitimate behaviour — pausing a stack overnight, freeing a port — for every user, to fix a papercut on one flow. Stop is not wrong; it was merely missing a stronger neighbour.

Consequences, all deliberate:

- **The control exists only for the `docker-compose` type.** For the other four stop paths it would duplicate Stop exactly. This follows the console's existing rule that a control which would do nothing for a type is absent rather than present and misleading — the same reason Start is hidden for a Swarm stack.
- **It runs `docker compose rm --stop --force`, not `docker compose down`.** `down` also removes the project network, which Traefik is attached to, which is why the delete path disconnects Traefik first; something would then have to reconnect it on restart or the stack returns unrouted. The job is to free a volume, and networks do not hold volumes. `-v` is deliberately absent: it would destroy anonymous volumes. That absence buys less than the sentence implies, and a later measurement showed the difference: a **named** volume round-trips exactly, while an **anonymous** one survives the removal with its contents and is then never re-attached — `docker compose up -d` carries an anonymous mount across a recreate by copying it off the previous container, and `rm --stop --force` destroyed that container, so `start` mints a fresh empty volume and the old one is left dangling, one per anonymous mount per cycle. `-v` stays absent regardless, because destroying the data outright is worse than orphaning it; re-attachment is rejected too, since the only way to point `up` at the preserved volume is to write its 64-hex id into the operator's own compose file, converting their unnamed mount into a named one without their say. What this rung promises is therefore the volume's *survival*, not its return: the console says so in as many words, and the orphan is swept from Settings → Maintenance → "Remove unused volumes" rather than from the removal path, which must never prune (it would take a stopped database's named volume elsewhere on the host).
- **It does not reuse `teardownCommand`.** That command ends in `rm -rf` on the project directory, which `start` needs in order to bring the project back.
- **It is gated by the lifecycle statement (`deployment:['create']`), not by `service:['delete']`.** The restore is gated on `volumeBackup:['restore']`; gating its prerequisite behind delete rights would rebuild the same dead end for any custom role holding restore but not delete. A row-level service-access check applies on top: `checkServiceAccess(…, 'read')`, which the compose service reaches through `findOwned`. This was drafted as *stronger* than Stop's gate, on the belief that Stop omitted the row-level check — it does not, because Stop takes the same `findOwned` path, so the two gates are in fact identical. The half of the decision that bites is unaffected and is the half to keep: the statement is `deployment:['create']`, never `service:['delete']`.
- **Its confirmation is a plain dialog, not the typed-name modal.** Typing the stack's name is this console's signal for irreversible destruction of a record; this action is reversible by pressing Start and destroys no durable state. Reusing the ritual here would dilute what it means on Delete.
- **The restore's refusal message names this control** instead of saying "stop all containers/services", which is the sentence that sent one reporter to a host shell.
- **Locking was untouched by this decision, and was closed by a later fix.** As drafted, a turn-off volume backup held an `flock` keyed by *service* while it stopped, acted and restarted, and neither the restore nor this action took it — so a scheduled turn-off backup could race either. That fix re-keyed that lock by **volume**, which is the resource actually contended, and made all three operations take it: the backup on both its turn-off and its non-turn-off path, the restore, and this action for every volume named by a volume-backup row of **this compose stack** that has `turnOff` set. Those rows are the ones whose backup stops the containers and tars underneath them, so they are the ones a removal can pull a volume out from under; a row's `enabled` column is deliberately not part of that query, because a disabled row's schedule does not fire but its run can still be triggered by hand. What this action does is still exactly `docker compose rm --stop --force` and nothing else; the lock decides only *when* it may run. A scheduled backup waits for the lock; every synchronous HTTP caller — this action included — is refused with **409 Conflict** naming the busy volume rather than holding a response open for the length of somebody's tar. This rung is unmoved: the fix changed what interlocks with a running backup, not what Remove containers, Stop or Delete do.
