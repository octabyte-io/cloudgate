# A socket holds an authorization lease rather than authorizing once at connect

Every gateway under the realtime module authorizes in its connection handler and never again. `WsAuthGuard.authenticate` runs once, the entitlement check runs once, and for the rest of the socket's life nothing re-reads the caller: no revalidation, no close on session expiry, no subscription to revocation. Nothing *could* re-read them — `handleConnection` keeps the resolved `WsAuthContext` and lets the upgrade request go, so there is no credential and no handle left to ask with. The consequence is that a Member whose service entitlement is withdrawn, or who is removed from the Organization outright, keeps receiving frames on every stream they had already opened; `removeMember` deletes the member row and does not touch the session, so their session expiring would not close them either, and an attacker who anticipates losing access can open sockets across many services first and keep them. This is not a bounded exposure. `container-logs` sends a keep-alive ping every 45 seconds for the express purpose of holding sockets open past proxy idle timeouts, and `tail -n +1 -f` against a finished deployment's log follows a file that will never get another line, so a socket can stay open indefinitely with no natural end. It is distinct from the earlier defect of authorization *missing* on one gateway; this is authorization *stale* across all six.

Cloudgate gives each authorized socket an **authorization lease** (CONTEXT.md). The lease is renewed every 30 seconds by re-running the same authorization the connection handler ran, and it is valid for 2 minutes past the last renewal that actually succeeded; when it ends, the socket closes with `4010 No longer authorized`. A renewal that is *refused* ends the lease immediately. A renewal that merely *fails* — the database is unreachable, a query times out — leaves the lease standing until it expires on its own. The guarantee this makes is a property rather than a tick rate: **no socket sends a frame more than the lease duration after the last time its authorization actually succeeded.**

Three alternatives were weighed and rejected, and a future contributor should not "correct" them back. **Capping socket lifetime** and forcing a redial is cheaper and needs no re-check, but it drops operators mid-command on a schedule and still leaves a full cap's worth of window for the attacker above. **Publishing revocation events** from the mutation sites is the only option with no latency at all, and it fails on maintenance: it is a list of revocation vectors distributed across `organizations.service.ts`, `custom-roles.service.ts`, `license-lapse.service.ts` and better-auth's own session delete, where a site that forgets to publish is silent and nothing type-checks it — and a license lapsing is not a mutation anyone performs, it is a timestamp passing, so the vector that most needs covering has no publisher to attach to. **Closing on session expiry alone** does not cover the case in the issue's own title, because `removeMember` leaves the session alive.

Consequences, all deliberate:

- **A socket is a standing subscription, not a long-lived request.** The invariant is that a frame may only be sent to a caller entitled at the moment it is sent, not at the moment the socket opened. This is the whole decision and everything below follows from it. It is the right model here because the frames are *live*: a container terminal executes what is typed into it and the stats socket samples fresh data every 1300ms, so these are new reads and new writes happening now rather than the replay of a decision made at connect. It also keeps ADR-0008 honest — that decision made containers reachable only through the Service that owns them, and entitlement to a Service is a mutable, row-level thing, so snapshotting it at connect would make `accessedServices` un-revokable through the one transport that streams.
- **Renewal re-runs the authorization; it does not consult a list of revocation vectors.** A session revoked, a session expired, a Member removed, a role changed, an `accessedServices` array edited, a custom role's grants edited, a lapsed license, a banned user, a Service deleted or moved, an `activeOrganizationId` changed — all ten are inputs to the one computation the connection handler already performs, and re-running it covers them by construction. An enumerated list would be correct only about the vectors that existed the day it was written; two of those ten (custom roles, license lapse) arrived after the gateways did, and nothing would have failed loudly. This is the same reasoning ADR-0009 applies to the session listing being an allowlist rather than a subtraction.
- **One step is captured at connect rather than re-run: the resolution of a container to its owning Service.** Of everything the six gateways do to authorize, exactly one is expensive — `ContainerAccessService.ownerNamesOf`, which shells out to `docker inspect`, over the remote-execution layer for a remote Server. Every other input is an indexed read. The expensive one is also the one that provably cannot change: a container's labels are fixed for its life and Docker does not reuse container ids, so re-inspecting can only ever return what it returned at connect. `resolveLogSource`, `findAuthorizedServer` and the permission checks are re-run whole, because they are the parts that go stale and they are all database-only. **The exception is a swarm-addressed target**, where the parameter is a service name rather than an id and names *can* be reused: `docker service rm foo` followed by another Organization creating its own `foo` would leave the captured resolution pointing at the wrong Service. Removing the service kills the stream the socket is following, so the reuse has no window in practice, but it is unmitigated in principle and is the one place this decision trades correctness for cost.
- **The credential is re-read by id, never by a retained header.** At connect the socket keeps a handle — `session.id` for a cookie caller, `apikey.id` for a key caller — and renewal reads that row: its absence is revocation, its `expiresAt` is expiry, and for a session its `activeOrganizationId` is the tenth vector above, while for a key its `enabled` column is a third. Retaining the upgrade request's headers would be simpler and would re-run `validateRequest` exactly, but it is the shape ADR-0009 already refused one layer up: a credential can only ever be protected negatively, and holding a live cookie in a gateway's closure for the life of a socket creates that obligation on an object that now outlives its request by hours, sits in a heap dump, and would be interpolated into a log line by the first person to debug a renewal failure. This codebase has had precisely that leak once. The cost of the inversion is real and should be named: "is this credential still alive" now has a second implementation living beside `validateRequest`, able to drift from it if better-auth adds a condition to session validity. It is kept in `AuthService` next to its sibling for that reason, rather than invented inside the realtime module.
- **Uniform across all six gateways, terminals included.** The intuition that an interactive shell dropped mid-command costs an operator more than a log tail dropped mid-stream is true, and it argues for renewing terminals *more* often rather than less: the terminal is the sharpest capability in the set — `docker exec` inside a container holding application secrets, or a root SSH shell on a Server — and a policy gentler with `container-terminal` than with `deployment-logs` would grant the longest survival to the thing most worth revoking. ADR-0007 and ADR-0008 both chose uniformity for connect-time authorization; a second, differently-shaped table for mid-stream authorization is what a seventh gateway gets wrong.
- **30 seconds because the keep-alive ping is 45.** `container-logs` arms a 45-second ping specifically to defeat proxy idle timeouts — the mechanism that makes an otherwise-dead socket immortal, and the reason this exposure is indefinite rather than theoretical. A renewal interval below it means the check that ends a stale socket always runs at least once between the pings that keep it alive, so the two are ordered rather than racing. Cost is not the constraint: at 50 concurrent sockets this is under one indexed read per second, against a stats gateway that already spawns a `docker stats` subprocess every 1300ms per socket. **Neither number is operator configuration.** They are constants, exported so tests can import them; an environment variable here would be a knob whose only interesting setting is "longer", and an operator who set it to an hour would have silently reverted this decision on a live install. The renewal interval is injected through a DI token that defaults to the constant, overridden only by the test module — nothing reads `process.env`, and weakening it on a real install still requires editing source and rebuilding.
- **A mid-stream refusal is `4010 No longer authorized`, and it is deliberately not ADR-0008's `4003`.** The uniformity of the connect-time frame exists so a caller cannot tell "no such deployment" from "not yours" and walk another Organization's id space. That reasoning does not bind here: the caller already connected, already passed, already received frames, so the id in question is one they were legitimately handed and there is nothing left to enumerate — the same carve-out ADR-0010 made for `local`. Reusing 4003 would also lie about the tense, showing "Not found or not permitted" to someone who watched a stream work for an hour, which reads as an application bug rather than a change in their access. The code sits outside both existing bands: not `400x`, which are connect-time, and not `server-terminal`'s `44xx` HTTP-offset band, because no HTTP status means this — 401 and 403 both describe a request being judged, and this is a grant withdrawn from something already running. Being in the 4xxx range is what makes the console stop retrying (`socket-stream-store.ts`), which is correct, since a redial would only be refused at connect.
- **One reason on the wire, the specific cause to the journal, and no extra frame.** Renewal observes pass or fail; because it re-runs the authorization rather than enumerating vectors, it does not *know* which of the ten fired, and producing a per-vector close reason would mean reintroducing the enumeration solely to write a string. It would also turn a held-open socket into a live probe for organizational state, telling a Member the exact second and cause of a role change that the HTTP surface never volunteers. The journal keeps the detail, through the `denyConnection` shape that already logs the caller, their Organization and the specific failure — prefixed so an operator can grep an expired lease apart from a refusal at connect. Nothing is written into the stream before the close: the precedent for writing frames covers content a close code cannot carry, such as a multi-line remediation command, and one sentence fits the 123-byte reason field. Writing it into a log stream instead would put a server-authored line into the log buffer, indistinguishable from something `tail` printed and carried along by anyone who copies a deployment log into a bug report. The console already renders it: `terminal-status.tsx` and the log views surface `closeReason` on a refusal, and the terminal stops accepting input.
- **A refused renewal ends the lease; a failed renewal does not.** An `HttpException` is the system answering "no" and closes the socket at once. Anything else is the system failing to *answer*, and is logged while the lease keeps running — the split ADR-0005 already draws, where domain code throws `HttpException` subclasses and anything unrecognized is a logged failure rather than a verdict. Failing closed on infrastructure errors is the tempting security-maximalist reading and it is wrong on its own terms: it cannot distinguish the attacker's socket from the operator's, so it closes both, and it does not even hold the line, because the attacker redials into a `handleConnection` whose `authorizedOrDeny` fails closed against the same broken database. A two-second Postgres hiccup would drop every terminal and log stream in the instance, mid-command, and buy nothing. **The lease duration is what closes the hole this opens**: without it, a database down for an hour would leave every socket streaming unauthorized for that hour, which is this issue again with an outage as the trigger instead of time. Two minutes is four consecutive failed renewals — long enough to ride out a pool blip or a failover, short enough that a real outage does not leave sockets running unverified into a second coffee break.
- **Terminals accept input for the life of the lease, and that is accepted rather than overlooked.** `bridgeTerminalInput` forwards every keystroke, so a Member whose access was withdrawn has up to a renewal interval of shell that executes what they type, and up to a full lease duration when renewals are failing. Tightening it would put a database read on the keystroke path of an interactive shell — the one interaction in this product where latency is felt keypress by keypress — to defend a window that does not matter: whoever holds a root shell at the instant of revocation has already had unbounded time with it, and everything they wanted was available before the clock started. The exposure this decision closes is the one in the issue, sockets held open deliberately across revocation for hours or days, against which 30 seconds of residue is rounding error.
- **Nothing is written to the audit log.** That log records acts by actors — someone removed a Member, someone changed a role — and a socket closing 30 seconds later has no actor; it is a timer noticing a consequence. Recording it would attribute the event to nobody, or worse to the revoked user, who did nothing, and revoking one busy Member with eight open sockets would write eight entries describing the single act `removeMember` already recorded once with its actor and IP. Enriching that existing entry with the count instead would require the revocation path to know about sockets, which is the coupling rejected above when polling was chosen over events.
- **Each gateway arms its own lease, and a test is what stops a seventh forgetting.** One helper in `socket-access.ts` takes the credential handle and the same authorization thunk the connection handler used, and each gateway calls it once after its own connect-time check passes. Connect-time denial contracts are untouched: ADR-0010's `4403` for the host shell and `server-setup`'s own `SETUP_CLOSE` stay exactly as they are, because connect-time and mid-stream refusals are separate concerns with separate frames. Folding the arming into `authorizedOrDeny` would have given three gateways a lease with a zero-line diff, but buying the other three would have meant overwriting close-code decisions that have their own ADR. A type cannot express "call this function", so the invariant is pinned by a test that enumerates `src/realtime/gateways/`, drives each handler with an authorized double, deletes the credential row and asserts a `4010` close — the same move ADR-0009 makes in asserting an exact key set rather than the absence of one field, because the invariant is about what a future edit might add and only an enumerating test notices. Note that this helper deliberately does *not* inherit `authorizedOrDeny`'s catch-everything behaviour; the two treat the same thrown error differently, on purpose.
- **The lease is per-process.** ADR-0003 folds everything into one NestJS application, so every socket and every lease live together and there is nothing to coordinate. A future split of the realtime module behind its own bootstrap would need each process to run leases for the sockets it holds, which falls out naturally from the per-socket timer but should be decided rather than discovered.
