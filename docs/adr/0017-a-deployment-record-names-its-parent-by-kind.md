# A deployment record names its parent by kind, and one precedence ranks the five

A `deployment` row hangs off one of five parents — an Application, a Compose stack, a Backup, a VolumeBackup or a Schedule — or off none at all, which is a real row shape that no reader can name an owner for. The columns are five nullable foreign keys, and until this ADR the *writers* said which one they meant by leaving four of them null. `CreateDeploymentInput`, the engine-facing port, declared `applicationId?: string | null` and `composeId?: string | null` as independent optionals with "exactly one of these" in a comment, and `DeploymentsService.create` coalesced both through to the insert (`applicationId: input.applicationId ?? null, composeId: input.composeId ?? null`). Exactly one was ever non-null because the engine's two call sites branched before calling — not because anything said so. Migration 0064 constrained the table (`deployment_at_most_one_parent`, `num_nonnulls(…) <= 1`), which turned a two-parented row from storable into a 500 naming the constraint, and its own docblock recorded that a database `CHECK` was the wrong surface for a rule the type should be stating.

Cloudgate's answer: **the parent is a discriminated union, one arm per kind, and the port takes the arms it can honour.** `DeploymentParent` (`deployment-engine/ports/deployment-recorder.ts`) has six arms — the five parents plus `none` — each carrying exactly one id and pinning the other four parent columns to `never`; `CreateDeploymentInput` is `Extract`ed down to the two arms that record a *build*; `create` branches on the discriminant; and `parentColumns` is the one place an arm becomes columns. A caller passing two parents does not compile, so the failure never reaches Postgres.

The alternative was to leave the type alone and let the constraint be the rule, which is where migration 0064 left it. It is rejected because the surfaces are not equivalent: a `CHECK` answers a caller with a 500 and a constraint name, at the end of a request that has already initialized a log file on a build server, and it says nothing at the call site where the mistake is made. The type answers at compile time and names the fix. The two are not alternatives in the other direction either — see the consequences.

The five columns also had **two precedence orders** over them, which the union is what let us delete rather than reconcile. `DeploymentsService.create` ranked compose before application (`input.composeId ? … : input.applicationId ? …`); every reader ranked application first. Application-first is the one with readers behind it, and one of those readers has shipped:

- `ownerOf` (`deployments/service-scope.ts`) titles every row in both deployment feeds, in the order application, compose, schedule, volumeBackup, backup;
- `ownedServiceId()` coalesces in the same order, so both feeds also *list* rows by it;
- `resolveCancelScope`, `resolveLogServer` and `scheduleRunServer` all test `applicationId` before `composeId`;
- **migration 0064 normalized by it.** Its data fix resolved the two-parented rows an install could already hold down to `application_id` — "the owner its feeds already titled it by" (`test/db/parent-consistency.e2e-spec.ts`). Reversing the order now would relabel rows a shipped migration has already decided about, with nothing left in the database to appeal to.

So application-first is the precedence, `create` no longer spells one at all, and the order is written in exactly two places that are asserted to agree.

Consequences, all deliberate:

- **The `CHECK` stays, and is now a backstop rather than the statement of the rule.** The type is in front of one writer; the constraint is in front of a migration, a fixture, a hand-run `UPDATE` and any writer added later — which is exactly the half `test/coding-standards/parent-id-writes.spec.ts` cannot see, and the half migration 0064 added it for. A future reader should not read "the type makes it unrepresentable" as licence to drop it.
- **The union covers all five parents and the parentless row, not the two the port accepts.** Migration 0064 established the count: `deployment` is not a third copy of `patch`'s `applicationId`/`composeId` pair, and the sweep reports only two of its five parents because `backup`, `volume_backup` and `schedule` are not service tables. The three run-record arms describe what `BackupRunRecorderService.start` writes, and `none` is deliberate rather than an orphan — `ownerOf` answers `NotFoundException` for it, `readLogs` answers 404 through it, and `run-history.e2e-spec.ts` inserts one by hand to pin that, which is why the constraint counts `<= 1` instead of stating an XOR. A union covering only the buildable two would have left the other four shapes nameless, which is how a second spelling gets invented.
- **`BackupRunRecorderService.start` was left on its own untagged `options.fk`.** It was `{ backupId } | { volumeBackupId } | { scheduleId }` — already exclusive, already internal, and outside this ADR's blast radius. Adopting `DeploymentParent` there would make the vocabulary universal and is worth doing; it is a `backups/` change rather than a `deployments/` one and was deliberately not bundled.
  **Amended: done, and the vocabulary is now universal.** The field is `parent: RunRecordParent` — `Extract<DeploymentParent, { kind: 'backup' | 'volumeBackup' | 'schedule' }>`, declared in `backups/run-recorder.service.ts` beside the writer that takes it — and the insert spreads `parentColumns(options.parent)` rather than the shape itself, so both writers of a `deployment` row now go through the one function that turns a parent into columns. `Extract` rather than the whole union is what makes this an adoption and not a widening: `create` takes the two *buildable* arms because it names a log directory after a service's `appName`, this writer takes the complementary three, and `none` is refused here because recording a run of something is the whole job. The pairing is the property worth having, so it is asserted rather than described — `test/backups/run-recorder-parent.spec.ts` pins that the two writers partition every parent foreign key on `deployment` with none left over and none contended, deriving the column list from the table's own `foreignKeys` so that a sixth parent fails there before anybody teaches the union about it, and that the recorder actually goes *through* `parentColumns` (adopting the type and then spreading the tagged object would have put `kind` in the insert, which drizzle drops without a word, leaving every existing suite green with the shared function bypassed). The import points no dependency backwards, which is the one thing that could have made this the wrong move: `deployment-recorder.ts` imports nothing at all, deliberately, and `backups/run-recorder.service.ts` already imported `deployment-engine/deployment-engine.paths` for `logsDirectoryOn`.
  **Amended by [ADR-0034](0034-a-cron-service-is-its-own-service-with-a-fresh-container-per-run-not-a-schedule.md): a run of a Cron service is a Run record whose parent is `application`** — the Cron service itself, stored like an Application — marked as a run rather than a build. The `application` arm is therefore no longer only a build, and the run recorder now also writes rows with a buildable parent; the partition test must state that split rather than the clean two-and-three one above. Done: the mark is the nullable `cron_run` column (the run's Swarm job, its image and who started it), held to an `application`-parented row by `deployment_cron_run_has_an_application`; `BackupRunStartOptions` requires it on that arm and refuses it on the other three, `CreateDeploymentInput` has no field for it, and the partition test now states that `application_id` is the one column the two writers share, the recorder's rows on it always marked and the engine's never.
  **Amended: a seventh tag, `environmentNetwork`,** for an Environment network's own Cloud run — its create by the Apply that makes it, and later its removal by the Environment's Delete. Its column, `environment_network_id`, is counted by `deployment_at_most_one_parent` like the other five, which now reads six columns. It is written by a third writer, `DeploymentsService.recordEnvironmentNetworkRun`, through `parentColumns`, so the partition test names three writers that between them claim every parent column. The read side ranks it **last**, after backup: a network's run owns no Service, so `ownedServiceId()` is unchanged and lists it under none, and `ownerOf` only titles it, `Environment network (<region>)`. Its log is on the platform host, under `environment-network-<id>` in place of an `appName`, and it is read with `environment: read` on the network's Environment.
  **Amended: an eighth tag, `postgres`,** for a postgres on RDS's own Cloud run — its create by the Apply that makes it, and later its changes and Delete. A database builds nothing, so this is the only row it has. Its column, `postgres_id`, is counted by `deployment_at_most_one_parent`, now seven columns, and written by a fourth writer, `DeploymentsService.recordPostgresCloudRun`, through `parentColumns`. Unlike the network's, its run is about a Service: `ownedServiceId()` coalesces `postgres_id` last, after the backups, and `ownerOf` ranks it after backup and before the network, titled with the Service's name. Its log is on the platform host under the database's `appName`, and it is read with `service: read` on the postgres.
  **Amended: a ninth tag, `bucket`,** for a bucket on AWS's own Cloud run — its create by the Apply that makes the S3 bucket, and the Apply of its CORS change or of a Drift put back. It is the postgres arm's twin: column `bucket_id`, counted by `deployment_at_most_one_parent` (now eight columns), written by a fifth writer, `DeploymentsService.recordBucketCloudRun`, through `parentColumns`; `ownedServiceId()` coalesces it after `postgres_id`, `ownerOf` ranks it after postgres and before the network, titled with the Service's name; its log is on the platform host under the bucket's `appName`, read with `service: read` on the bucket. The spec's "no new Deployment parent" meant no parent *beside the Service*: a bucket's Cloud run is a Deployment of the bucket itself.
  **Amended: a tenth tag, `redis`,** for a redis on ElastiCache's own Cloud run, exactly as the postgres's: its column `redis_id` is counted by `deployment_at_most_one_parent`, now nine columns; it is written by `DeploymentsService.recordRedisCloudRun`, which shares `recordDatabaseCloudRun` with the postgres's writer; `ownedServiceId()` coalesces it after `bucket_id`, and `ownerOf` ranks it after the bucket and before the network, titled with the Service's name.
  **Amended: an eleventh tag, `mysql`,** for a mysql on RDS's own Cloud run, exactly as the postgres's: its column `mysql_id` is counted by `deployment_at_most_one_parent`, now ten columns; it is written by `DeploymentsService.recordMysqlCloudRun`, which shares `recordDatabaseCloudRun` with the postgres's and the redis's writers; `ownedServiceId()` coalesces it after `postgres_id`, and `ownerOf` ranks it after the postgres and before the bucket, titled with the Service's name.
  **Amended: no new tag, but a "for Service" column.** On Google Cloud every Domain is a host rule in the Environment network's one URL map, with its certificate in the network's state, so adding, editing or removing a Domain is a Cloud run **of the network**: its parent is `environmentNetwork`, written by `recordEnvironmentNetworkRun`, and nothing above changes for it. The nullable `for_service_id` names the Service whose Domain the run is about, so that the run is listed on that Service too (`DeploymentsService.findAllByApplicationId` lists a Service's own rows and the network runs for it). It is **not a parent**: `deployment_at_most_one_parent` still counts nine columns, `ownedServiceId()` and `ownerOf` are unchanged, so the feeds title and list the run as the network's; `deployment_for_service_on_a_network_run` holds it to a network-parented row; it is `set null` with the Service; and the partition test sets it aside by name as a reference to `application`, as it does `held_by_plan_id` to `plan`.
- **The vocabulary lives in the port, not beside the table.** `deployments/` implements the port, so a type owned there would point the dependency backwards and put the engine behind the module it was separated from. `deployment-recorder.ts` imports nothing at all, which is what makes it reachable from every writer.
- **The read side's `DeploymentOwnerType` is now derived from the write side's kinds** rather than spelled a second time. Two hand-written copies of one enumeration is what `service-scope.ts` already exists to remove one level down (two copies of `ownerOf`), and a write side and a read side naming the same five owners differently is how the precedence disagreement started.
- **A compile-time guarantee is asserted by a compiler.** `test/deployments/deployment-parent.spec.ts` type-checks each refused shape as source against the real port and makes the diagnostic the assertion, because "this does not compile" written in a comment is true when written and unfalsifiable afterwards. The fixture is compiled in memory: a fixture file on disk would carry deliberate type errors into `tsc --noEmit`, which has no `exclude` and so type-checks `test/` too.
- **The tag is `kind`, and every call site says it.** The two engine call sites gained `kind: 'application'` / `kind: 'compose'` and so did fifteen test calls. An untagged union keyed on which id is present would have cost no call-site churn, and is rejected because it cannot express the parentless arm at all — `{}` is assignable from everything — and because "which key is present" is a discriminant a reader has to reconstruct.
