# A preserved rollback image is reclaimed by the delete that destroys the row naming it, not by a maintenance screen afterwards

`DeploymentEngineService.captureRollback` preserves a released image by tagging it `${appName}:v${version}` on the Server that built the Deployment, and the `rollback` row is the only thing in the database that records that tag. Nothing else names it, and a `docker images` listing on the host cannot tell a preserved snapshot from anything else. `rollback.deploymentId` and `deployment.applicationId` are both `onDelete: 'cascade'`, so deleting an Application — or its Environment, or its Project — destroys every row that names one of its preserved images. Until this ADR, none of those three paths reclaimed the images first: `ApplicationsService.remove` and `common/service-cascade.ts` each run exactly three teardown steps, the swarm service, the Traefik dynamic config and the source directory, and neither issues any `docker image rm`. So one unreclaimable image per Deployment was left on disk with nothing an operator could use to identify it.

The ticket offered two directions and asked for an argument rather than a coin toss. The first was to reclaim ahead of the cascade, hooked at the Server delete. The second — the ticket's own lean — was a maintenance surface listing preserved images on a Server that no `rollback` row names, offering to remove them: cheaper, coupling no two Server lifecycles, and putting a human in front of a destructive act on a machine.

**Cloudgate reclaims at the delete**, in `rollbacks/preserved-images.ts`'s `reclaimPreservedImages`, called by all three roots after their refusal has been decided and before the parent row is dropped.

The maintenance surface is rejected because **it cannot be both safe and effective, and the reason is structural rather than a matter of effort**. Its predicate is *"a preserved image on this Server that no `rollback` row names"*, and the cascade that creates the orphan is the same one that destroys every row the predicate would consult. The Application is gone, so the Server no longer holds an `app_name` to match tags against either. What is left to recognise an orphan by is the shape `<word>:v<digits>` — which is not this platform's to claim. An operator's own `myapp:v3` matches it. Worse, `captureRollback`'s docblock already records that two `server` rows may point at one machine and read as different Servers, so on a shared host a tag matching the shape may be another organization's live rollback point, whose naming row this caller cannot see and whose deletion this caller must never be offered. Narrow the listing to tags whose repository matches an Application this organization still has on this Server, and it becomes safe and blind: it can no longer see a single one of the orphans this ADR is about. A screen that finds them cannot be safe; a safe one cannot find them.

At the delete, the three facts the reclamation needs exist simultaneously and exactly once: the tag, off `rollback.image`; the machine, off `preservedImageServerId` over the snapshot's own Server pair merged onto the live Application's, which is the build-server rule; and whether that machine is still this organization's, off `checkServerAccess`. After the row goes, all three are unrecoverable. That is the whole argument: **the information required to reclaim exists only before the rows are destroyed, so the reclamation belongs there.**

The ticket's framing of direction 1 was nonetheless wrong in a way worth recording, because the schema invites the same mistake again. It described the cascade as firing when a **run** Server is retired, and proposed a hook ahead of that cascade. That hook would be dead code: `ServersService.remove` has refused to delete a Server while any Application names it, later widened to thirteen cascades, so `application.serverId`'s cascade is not reachable through the HTTP surface at all. It fires only when the whole organization is deleted, which destroys the build Server in the same statement. The ticket's own objection to direction 1 — that it would make retiring one Server depend on a different Server being reachable — therefore never arises, because the hook does not belong at the Server delete. It belongs at the delete of the thing that actually goes away, whose own contract already answers for an unreachable machine.

Consequences, all deliberate:

- **The defect is larger than the asymmetry the ticket named, and the fix is aimed at the larger one.** The ticket framed this as `application.serverId` being `cascade` while `buildServerId` is `set null`, scoped to snapshots captured before the build-server rule — "a cleanup question for existing installs rather than a hole in the current write path". That scoping is wrong. The two FKs decide only *which machine* the orphan lands on; the leak itself is that no delete path reclaimed a preserved image at all, which is live on the **default single-Server install**, where `captureRollback` writes these tags on every successful deploy with `rollbackActive` on and the run Server is the one that keeps them. The build-Server arm is the legacy one; the run-Server arm is the common one, and it was never guarded.
- **It runs after the refusal and before the row, and neither half is a preference.** All three roots can still answer 409 — a workload they could not confirm gone keeps the tree intact — and reclaiming ahead of that refusal would leave a live Application whose console still offers Rollback on snapshots whose images have been deleted, converting a recoverable refusal into silently unrestorable rollback points. Reclaiming after the row is not late but impossible.
- **It never blocks a delete, and it says what it left behind.** This is the opposite of `RollbacksService.remove`, which refuses on a failed removal — and the two are consistent because there the row survives to keep recording the tag, while here the row is a child of the thing being destroyed and cannot survive. The choice is between naming the leak and making *forget this Application* impossible on a machine that is down, which was already settled: "a dead server must not make deletion impossible", answered with a truthful response rather than a bare 200. So the delete's answer carries `unreclaimedImages: [{ serverId, images }]` when something was left, and omits the field entirely when nothing was — `cascadeDelete`'s existing rule for `orphaned`, for its stated reason. A leftover image is disk, not ADR-0008's unmanaged container, which is the property `?force=true` exists to guard.
- **A Server this organization no longer has is skipped silently, and a Server in another organization is never touched.** `full_context` is a plain `json` column no foreign key constrains, and the rollback-context fix proved that ids in it can name another organization's rows — so without the organization predicate this would run a `docker image rm` on somebody else's machine off an id no caller had to be entitled to. `checkServerAccess` rather than an existence probe, because it answers *still ours* in the same select. Neither case is reported: there is no image this instance can reach and nothing an operator of it could act on.
- **One `docker image rm` per tag, and the first real failure stops asking that Server.** A batched `docker image rm a b` exits 1 with both complaints in one message, so a batch where one tag was already gone and another is genuinely held by a container would read as wholly reclaimed — `imageAlreadyGone` would answer for the pair. The N round trips are `tearDownCascadeChildren`'s accepted cost for its stated reason, bounded by stopping at the first error that is not "no such image": an unreachable Server must not multiply an SSH connect timeout by the tag count of an Application with a hundred Deployments.
- **`reclaimPreserved` is a required parameter of `cascadeDelete`, not an optional one.** This is `teardownStepsFor`'s exhaustive switch one resource along: a third cascade root that forgot to pass it would destroy `rollback` rows with no reclamation and nothing would say so, which is the failure the module exists to close.
- **`preservedImageServerId` and `imageAlreadyGone` moved out of `RollbacksService` rather than being copied.** Three call sites now ask the same question — `rollback` refuses when the answer is not the Server it would converge on, `remove` addresses the answer, and this reclaims it in bulk — and the build-server rule's own lesson is that two copies of a rule that has been wrong once is how it goes wrong again. They are plain exported functions rather than a provider because `RollbacksService` injects `ApplicationsService`, so a provider would make `applications`, `projects` and `environments` reach `RollbacksModule` through a `forwardRef` knot for what is a select and a shell word — `common/service-cascade.ts`'s precedent and its stated reason.
- **What this does not reclaim, and does not pretend to.** Only the preserved snapshot tag. The `${appName}:latest` image every build leaves on the build Server, the buildkit cache beside it, the source tree under `applicationsDirectory()` when the build ran on a different machine from the removal, the patch-repo clone, and every deployment log file are all left where they are; each is its own ticket, and `docker image prune`/`docker builder prune` from Settings → Maintenance remains the machine-wide sweep for the images among them. The claim here is narrow on purpose: the preserved tag is the one artifact whose *only* record was the row being destroyed, which is what made it unidentifiable rather than merely uncollected. **Amended: the source tree is no longer on that list.** It was named here as its own ticket and that ticket landed — both Delete paths ran their `rm -rf` on `serverId` while `DeploymentEngineService` clones on `buildServerId || serverId`, so on a dedicated-build-Server install the removal was issued to a machine that had never held the directory, exited non-zero, and was swallowed by the best-effort `catch`. The build-host rule is now stated once, in `deployment-engine/build-host.ts`'s `buildHostServerId`, and every Delete asks each artifact which machine it is on rather than assuming the Service's own; ADR-0018 carries the decision. Nothing else on this list moved then: the `${appName}:latest` image, the buildkit cache, the patch-repo clone and the deployment logs were all still left where they were. **Amended again: the patch-repo clone comes off the list for an Application**, reclaimed on the build host that made it and named in the delete's report when it could not be — it stays on the list for a Compose stack, whose clone no delete path reaches. **Amended a third time, which empties the list of everything it can: the `${appName}:latest` image comes off it** — reclaimed on the build host by all three deletes (`applications/built-image.ts`'s `reclaimBuiltImages`) and named in `unreclaimedImages` beside the preserved tags when it could not be, because a leftover `${appName}:latest` and a leftover `${appName}:v3` are the same claim and take the same follow-up. The docker-source arm reclaims nothing at all, deliberately: `builtImageName` answers the operator's own `dockerImage` column there, an image the platform pulled rather than produced. **The deployment logs come off it too, by a different mechanism**, because they were never the cascade's to reclaim — ADR-0020 keeps them for a fixed window and reaps them with a nightly sweep of the tree. **What is left on this list is the buildkit cache, and the third amendment establishes that it is not a ticket but a refusal**: a BuildKit cache record carries no image, tag or repository field, measured on Docker 29.3.1 — `docker buildx du --verbose` prints a record's whole field set with no name of any output on it, and `--filter` (the same parsing `docker builder prune` takes) selects on `id`, `parents`, `description`, `type`, `until`, `unused-for` and three booleans while `ref=`, `image=`, `repository=` and `label=` match nothing. So one Application's delete cannot scope a prune to its own build, and firing a machine-wide one would be a worse defect than the leak; `docker builder prune` from Settings → Maintenance stays the honest surface. `railpack` leaks no *cache* in the first place, creating and `docker buildx rm`-ing a per-build container builder without `--keep-state` — **true of every build that reaches one of its branches, and disproved for the kill path by two later fixes: see the amendment at the end of this bullet.** **Amended again, which adds an artifact rather than removing one: a Compose stack's own built images.** They were never on this list because nothing had established what they are called, and the answer is not `${appName}:latest`: `docker compose build` names an image `${project}-${service}`, and the project is `appName` (`createComposeCommand` passes `-p ${appName}`; `getCreateComposeEnvFileCommand` writes `COMPOSE_PROJECT_NAME=${appName}`). Measured on Docker 29.3.1 / Compose v5.1.1 — a `build:` service with no `image:` tags `${project}-${service}:latest`, a `build:` service *with* `image: my-own-name:7` tags the operator's own reference, and a service with only `image:` builds nothing. So `ComposeService.remove` reclaims the first class on `compose.serverId` (`compose/compose-images.ts`' `reclaimComposeBuiltImages`) and names what it could not in `unreclaimedImages`, sharing the field with the Application's tags for the third amendment's reason; and it refuses the second on that amendment's own docker-source reasoning, since `docker image rm` on a name the operator chose could untag a reference every other stack on the host is running. Two whole stack shapes name nothing and are refusals with the measurement rather than tickets: a `stack`-type stack, because `docker stack deploy` has no build phase, and a stack carrying `compose.command`, because that column replaces the whole `docker` subcommand so neither the project name nor whether a build happens is Cloudgate's to know. **The cascade still leaves them**, exactly as it still leaves a stack's patch-repo clone and for the same reason: `listCascadeChildren` would need each compose child's `composeType`, `command`, `sourceType` and `composePath` — the per-cascade `select` H-87 dropped — plus one `cat` per git-sourced stack ahead of the teardown's `rm -rf`. So a Project delete leaves a stack's images behind and a stack's own delete does not, which is where this rule holds and where it drifts. Two things this bullet did **not** name were also wrong and are closed by the same change — a preview deployment's Swarm service and source tree, which no delete path named at all, and a failed directory removal, which was reported nowhere; the second is why ADR-0018 widens this ADR's claim from *when* an artifact is reclaimed to *and what was left when it was not*. **Amended, which add an artifact this bullet never named — what a *killed* build leaves — and correct the railpack sentence above.** The correction first, because it is what hid the artifact. Railpack leaks no *cache*, and that claim is true of every build that reaches one of its branches: `railpackStrategy` removes its per-build `docker-container` builder on both failure branches and at the end, and `nixpacksStrategy`'s `publishDirectory` branch removes its copy-out container the same way. So the one path where nothing removes either is the path where **no branch runs** — a `SIGKILL`, a dropped SSH channel, a cancelled Deployment — and a buildkit builder plus its state volume, or a `Created` container holding a writable layer, then sits on the build host under a name no row records. One fix answered that in the *next* build of the same Application, which the queue makes exact (`getGroup` returns `application:<id>` and `InMemoryQueue` admits one job per group at a time), and the other did the same for nixpacks — which **bounds** each leak at one leftover per Application rather than closing it, since an Application that never builds again keeps its leftover for ever. **It comes off this list by reclamation, in this ADR's own slot:** `applications/build-leftovers.ts`' `reclaimBuildLeftovers` sends `builders/build-leftovers.ts`' one composed program per build host, after the presence refusal and before the rows, from `ApplicationsService.remove` and from the cascade alike. **Both halves of that slot are load-bearing here, one weaker than the third amendment's and one sharper.** The rows half is this ADR at its plainest: `appName` is the only thing that names either artifact, and one statement later it does not exist. The refusal half is *not* the sharp version `reclaimBuiltImages` has — nothing is running these — but it is not merely conventional either, because what the sweeps match is a **pattern**: a build genuinely in flight would have its live builder and its live copy-out container removed underneath it, and running after the refusal keeps that impossible for a **kept** Application, which is the one outcome where a live build still matters. For a delete that proceeds it is moot and deliberately so — the same delete has already `rm -rf`'d the source tree the build is reading and `docker image rm --force`'d the tag it is writing — which is why the queue premise the first fix leans on is not needed at a delete and is not claimed. **And it reports nothing, which is the question the second fix asked and the third amendment answered the other way.** `UnreclaimedArtifact` states two criteria about itself, *is it a path* and *does something break differently from the entries already there*: a buildx builder name and a container name are neither paths nor image references, so a fourth `kind` would put that type's `path` field back in the state the second amendment renamed it out of — the third amendment's first reason for keeping `${appName}:latest` in `unreclaimedImages`, verbatim. The decisive half is new, and it is a difference in **mechanism** rather than a judgement about severity: every entry in both existing fields names an artifact the delete knows exists, because `rm -rf` exits 0 for a path that is not there (so a non-zero exit already means *this exists and I could not remove it*) and `removeImagesOn` reads the daemon's own *no such image* one tag at a time — while a **sweep** exits 0 whether it matched nothing or everything, so a failed exec means *the sweep did not run*, which is not the same claim. An entry carrying no artifact name is the field-named-for-nothing the second amendment refused to write. That is not a hole because the failure modes are correlated by construction: this sweep goes to the build host, and the source-tree `rm -rf` (`kind: 'source-tree'`), the patch-repo clone (`kind: 'patch-repo'`) and `${appName}:latest` (`unreclaimedImages`) all already report on that same machine when it is the machine that cannot be reached. **A later fix found the same artifact in the lane the second fix could not see: a preview's.** `deployPreview` spreads the parent Application's row over `{ appName: preview.appName }`, so a killed preview build leaves `railpack-{preview.appName}-{nonce}` — and no delete named it. Not because the cascade filters `reclaimBuildLeftovers` to `serviceType === 'application'`, which is where the ticket looked: **a preview is not a `CascadeChild` at all** (ADR-0018 — no `service_type`, no row in the eight service tables, no `checkServiceAccess` of its own), so every sweep any delete sent carried the *parent's* appName, which the length-not-prefix pattern can never match against a preview's builder. Widening that filter would have reached nothing. The sweep is a third step of `preview-deployments/preview-teardown.ts`' `previewTeardownSteps` instead, the only place all four preview delete paths meet — `tearDownApplicationPreviews` for the Application delete and both cascades, and `PreviewDeploymentsService.teardown` for the closed-pull-request webhook and `DELETE /preview-deployments/:id`, the two commonest ways a preview goes away and the two no cascade sees. **What is left on this list is still the buildkit cache**, on the third amendment's measurement, and the correction above narrows that refusal rather than reopening it: a killed build's leftover is reclaimable precisely because it is *named*, which is the property the daemon's shared cache does not have.
