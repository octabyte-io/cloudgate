# A tool result carries nothing we would not accept being public for good

A tool result is a response, and ADR-0019 governs it unchanged. What differs is where it comes to rest. An HTTP response lands in a console the operator runs. A tool result lands in a model's context, on the model host, in its logs and in summaries carried into later turns. That copy neither Cloudgate nor the operator can recall, and revoking the Agent key does nothing about a value that has already left. So the question a tool result must pass is not ADR-0019's "is this caller entitled to it?" (its last consequence already says entitlement to a resource is not entitlement to its key). It is **"would we accept it public, permanently?"**

**The rule.** Every byte `POST /mcp` returns comes from exactly one of three sources:

1. **a declared projection field.** A tool never returns its service method's return value. It returns fields it declares, censused as an allow-list and fail-closed at boot. A field enters the allow-list because a named step of the agent loop needs it, not because it is harmless. Where a secret was, the projection carries its presence at the field's own depth, per ADR-0019 (`hasEnv`, `hasDatabasePassword`), with **no key list and no count**.
2. **a declared error message.** Each tool maps exception classes to fixed text. **Amended: the key is the class plus the response's `code`**, because the row-level `*_ACCESS_NOT_GRANTED` refusals are plain `ForbiddenException`s carrying a code — the same class as a role refusal — and CODING_STANDARDS §2.5 rules out a class of their own. A 403 entry without a code would swallow every refusal there is, and the census refuses one. A thrown message never passes through verbatim. An unmapped failure answers "the call failed" plus the audit row id, and the detail is read in the console.
3. **a deployment-log window of an application or compose Deployment.** Any other owner (schedule, volume backup, database backup) answers the same 404 as an unknown id.

The dispatcher runs all three through **one mask of every stored secret value reachable from the target**. That set is derived from the schema (every encrypted-at-rest column reachable from the owner), so a new secret column joins the mask with no hand-kept list. **As built, "reachable" is read off the foreign keys:** the target row, everything its foreign keys reach transitively (a Service's Environment, Project, registry, git provider, Server and that Server's SSH key), and, when the target is a Service, its child rows and what their foreign keys reach (mounts, patches, basic-auth credentials, schedules, backups and a backup's Destination). `KEY=VALUE` blobs contribute each value, `encryptedJson` every string inside it. The encrypted columns no Service reaches that way (Notification channels, identity providers, the AI key, the license key, a Server's certificates) are listed with their reasons in the census, so a new one is argued rather than silently unmasked.

**No tool ever runs a command in a Managed container or on a Server.** This is a standing prohibition, not an absence. A shell ends every other rule in this ADR, and relying on an absence is how a later `exec_in_container` gets through review. It is pinned by the agent roles never holding a `docker` statement, which the unlicensed-install spec (`test/rbac/agent-roles.e2e-spec.ts`) asserts.

**Amended: one encrypted column leaves on purpose, a Cloudgate-kept Project config's text.** `projectConfigLocation.text` is `encryptedText` by ADR-0015's argument (YAML comments carry anything), and the boot check refuses a projection that copies an encrypted column. But reading the config is the named step of the loop an Agent takes: it explains a plan against the config, and the config names Services and variable *names*, never a value. So `get_project_config` answers the text, as `configText`, and nothing else in the tree may: the call renames it on the way out, the frozen allow-list names the one path, and `tool-secret-mask.spec.ts`'s reason for the column says so. The mask still runs over it from the Project, so a Project secret pasted into a comment comes back masked; the column is not a root of its own, because masking it by itself masks the whole text. What an operator writes into a comment that Cloudgate never stored is this ADR's stated limit, as a build's own output is for `read_deployment_log`, and `docs/connecting-an-agent.md` tells the operator to keep credentials out of the config. A repository-kept config is never copied into Cloudgate, so it answers its location and commits, not a text.

**Consequences.**

- **The projection is the defence, and not a formality.** The read path is sanitized and the write path is not. `BaseDatabaseService.start`/`stop` return the raw row with `databasePassword`, so "a tool returns what its method returns" would leak a database password through a `stop` call with no rule visibly broken.
- **The mask is the second line of defence, and its limit is stated rather than discovered.** It cannot catch what a build prints that Cloudgate never stored: a token fetched by the Dockerfile, an encoded value, a value under 6 characters. That limit is written where an operator grants an Agent: *"An Agent can read deployment logs. Values Cloudgate stores are masked; anything else your build prints is not."* The log tool was kept anyway, because without it the deploy → poll → read-log loop the surface exists for breaks.
- **No env key list, although it looks harmless.** An Agent cannot write env, so a key list lets it report a gap but never fix one. The Deployment log already names a missing variable. And a list of keys is a map of vendors and credentials to hunt for.
- **Each part is censused and fails closed:** the projection allow-list, the error tables, the mask's schema derivation and the log-owner narrowing. What they share is that a twelfth tool is masked, projected and error-mapped without anyone remembering to.

**Pinned by** the docker assertion above, `test/coding-standards/tool-projections.spec.ts` (every tool's allow-list, frozen), `tool-error-tables.spec.ts` (404 and each `*_ACCESS_NOT_GRANTED` fold into `grant`), `tool-secret-mask.spec.ts` (the reach, against an unpruned walk of the schema) and `test/mcp/mcp-endpoint.e2e-spec.ts` (a stored secret echoed into a returned field comes back masked; three-way byte identity). The log-owner narrowing lands with `read_deployment_log`.
