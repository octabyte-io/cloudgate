# A file body an operator authors and Cloudgate materializes on a host is `encryptedText`, unless something looks it up by value

ADR 0006 says _how_ a column is encrypted and names the kind of thing that gets encrypted — "SSH keys, tokens, database passwords". Every column it covered when it was written was a **credential**: a value minted or pasted for the sole purpose of authenticating, whose name says so, and which `secret-bearing-columns.spec.ts` can therefore find by reading the schema. Five columns in this tree are not that and are encrypted anyway — `mount.content`, `patch.content`, `schedule.script`, `compose.composeFile` and `schedule.command` — and until this ADR there was no written rule they were instances of, only three separate arguments that happened to agree. So the fourth candidate got decided twice, differently, by two issues that were looking at the same page.

**The rule.** A column is `encryptedText` when both halves hold: it stores a **file body an operator authors**, which Cloudgate takes verbatim and materializes on a machine it manages; and **nothing looks the value up by value**. The first half is the argument — a file body is where an operator puts a credential, and the platform has no way to know which lines of it are the secret, so the whole body is treated as one. `mount.content` is an env file or a config file, `patch.content` is a file headed for the build tree, and `schedule.script` is a shell script that Cloudgate writes to `script.sh` on a Server and runs there on a cron: it is the likeliest of the three, not the least, because `curl -H "Authorization: …"` and `PGPASSWORD=…` are what a cron script is _for_. The second half is the constraint, and it is the reason better-auth's `session.token`, `apikey.key` and `verification.value` are exempt from the secret-columns sweep as a set: AES-256-GCM under a random IV encrypts the same plaintext to different bytes every time, so `where token = $1` matches nothing, and a column something searches cannot be given this type at all. Establishing that nothing queries a candidate — no `where`, no `like`, no ordering, no index — is therefore the first work of any change under this rule, and it is most of the work: `encryptedText` `dataType()`s to `'text'`, so there is no DDL diff, no migration and no backfill, and a value already stored without the `enc:v1:` prefix is passed through on read (ADR 0006) and becomes ciphertext on the next write of that column.

**What this rule is not.** It is not a claim that the value is secret in transit or at the far end. All three columns are shipped to a host base64-encoded inside a shell command and land there as a world-readable file that a process runs — that is the _point_ of the column, and no column type can change it. What ADR 0006 defends is the database: a `pg_dump`, a read replica, a backup tarball or a stolen disk. So "the script is written to `script.sh` in clear anyway" is not an argument against encrypting it, and neither was the fact that a failed materialization logged the command it could not run: that path was identical for `mount.content`, which has been `encryptedText` since it was written, and closing it was one change for the exec layer rather than three arguments about three columns. **That change has since landed** — `ExecError`'s constructor elides the encoded payload out of every string a failed exec carries (`common/logging/error-payloads.ts`), so the journal echo is closed for all three columns and for the ten other builders that emit the same wire shape. The sentence this paragraph opens with is unaffected and still holds: the body still travels to the host in clear inside the command, and still lands as a world-readable file. Nothing about a column type could change that, and nothing here claims to.

**`compose.composeFile` satisfied this rule, and it is `encryptedText`.** This paragraph used to record the question as _open and qualifying_, because the scheduling change owned it and the column's readers were in four other modules. The secret-columns sweep had looked at it before that, left it, and recorded the reason as: it is _edited in a code editor, diffed and templated_. **That sentence is retired, and it is not inherited anywhere** — the bullet in `secret-bearing-columns.spec.ts` that carried it now points here instead. None of the three was a reason. `encryptedText` converts at the driver boundary, and the change that encrypted it checked every reader rather than asserting that: the DTO's `composeFileSchema` refinement, `ComposeService.update`'s `data.composeFile ?? row.composeFile` merge, `readComposeFile`, `findDeployable`, the label injector, `DomainsService.findComposeDefinition`'s projection, `DeploymentEngineService.readComposeContent`, the template writer and the AI writer — and, on the relational-query side, `ComposeService.findOne` and `TraefikSetupService`. **Not one of them needed an edit.** That is the finding worth carrying forward: the nine reader sites were the reason to schedule the work and turned out not to be work at all, because a `customType` is transparent to anything that goes through drizzle, and nothing here does not. The console's editor and converted-file diff work on JSON the API had already decrypted, before and after.

The gate was the same as every other column under this rule and it held: nothing queries `compose_file`. No index in the 0066 snapshot, no `where`, `like`, `orderBy`, `groupBy` or `distinct` anywhere in `src/`, no `sql` template or `db.execute` naming the column, no view and no `.mapWith`. The `notNull` `default('')` stays plaintext in the DDL and must — a ciphertext in a migration is tied to the `APP_ENCRYPTION_SECRET` that generated it and is undecryptable on every other instance (ADR 0006) — and reads back as `''` through the same pass-through that carries every existing row until its next write. On the merits it was the strongest of the four rather than the weakest: it routinely carries literal `environment:` values even though the `encryptedText` `compose.env` sits beside it on the same table for exactly those, and the blast radius of one file is every service in a stack.

**What that change found by doing the echo check, which is the part that was not bookkeeping.** Four builders ship the file to a host in the covered base64 shape — `writeComposeFileCommand`, `getBuildComposeCommand`, `composeStartCommand` and `raw.strategy.ts`' clone — so the journal path was already closed. One echo was neither that shape nor an author reading their own file back: `parseComposeFile` called `yaml`'s `parse` with no `logLevel`, the library defaults it to `'warn'`, and `parseDocument` runs `prettifyError(source, lineCounter)` over **warnings** as well as errors — so a `YAMLWarning` carried up to 80 characters of the operator's own document plus a caret into `process.emitWarning`, which with no `process.on('warning')` handler anywhere in `src/` Node formats onto process **stderr**. Measured: a `!!tag` on an `environment:` entry puts the warning's position on the credential's line and prints `MARIADB_ROOT_PASSWORD=…` verbatim. The document still _parses_, which is why nothing had noticed: no exception exists at any point, so `ExecError`, `elideEncodedPayloads`, `capMessage` and `AllExceptionsFilter` are all downstream of a path that never reaches them, and six warning classes are reachable from an operator-authored file on the read-only routes as much as on a deploy. `parseComposeFile` now passes `logLevel: 'error'`; `'silent'` is rejected on measurement rather than on documentation, because it makes `parse` _return_ a half-read document instead of throwing and would take `composeFileParseRefusal`'s whole contract with it. **The general lesson is the one this ADR's third consequence already asks for and had not been asked of a third-party parser: a library's own diagnostic channel is an echo site.**

**Amended: the rule is about operator-authored program text, not about the file. `schedule.command` is now `encryptedText` too.**

The rule above says _file body_, and `schedule.command` is not one: it is a shell program an operator writes for a container schedule, which Cloudgate hands `docker exec` on a cron and never materializes anywhere. The scheduling change left it plain deliberately, and the reason was the right one — encrypting a column the code then prints is exactly the docblock lie the third consequence below warns about, and `buildScheduleCommandScript` wrote the command verbatim into the deployment log.

**So the rule now reads: a column is `encryptedText` when it stores program text an operator authors, which Cloudgate takes verbatim and hands to a machine it manages; and nothing looks the value up by value.** The file was never the load-bearing half. What made `mount.content`, `patch.content`, `schedule.script` and `compose.composeFile` qualify is that an operator writes them, that Cloudgate cannot know which of their words are the secret, and that they are executed or read by a host — and every one of those is true of a `command` word for word. `script` and `command` are the same thing about the same schedule, differing only in **delivery**: `script` becomes `script.sh` and travels base64 through the shape `error-payloads.ts` elides, `command` travels as an argument of the program and had no shape at all. Treating delivery as the classification is how the container-side sibling of an encrypted column stayed plain.

**The echo went first, and that ordering is part of the decision rather than a courtesy to it.** The command had two echoes with two different audiences, and only one of them was a widening:

- **The deployment log keeps it verbatim, and that is correct under this ADR's own second paragraph.** `DeploymentsService.resolveLogServer` reaches a schedule run's log through `scheduleRunServer`, which calls `SchedulesService.findOne` — `checkRowAccess(ctx, row, 'read')`, the identical predicate that answers `GET /schedules/:id` with the column in clear. The log reader _is_ the column reader, and the file sits on the host that is about to run the command. That is the far end ADR 0006 does not claim to defend, the same far end that makes "the script lands as a world-readable `script.sh`" no argument against encrypting `script`. The echo is also load-bearing: it is how an operator sees what a run that failed _last night_ ran, which the row stops being able to answer the moment the command is edited. It is preserved byte-for-byte, by expanding the holder below.
- **Cloudgate's own journal was the widening, and it is closed structurally.** The command was a word of the program handed to `RemoteExecService`, so `ExecError` captured it and pino wrote it six times over — on _every_ failed run, because the run script turns the operator's own non-zero exit into a failed exec, and because none of the mask's four patterns recognises a bare container command. It now travels in `RemoteExecOptions.env` under `CG_SCHEDULE_COMMAND`, and the program references the holder for the remote shell to expand: this ADR's _a mask is the second-choice answer_ bullet asked for never-carry rather than a fifth pattern, and `carryBuildEnv` is the shape it asked for. `SchedulesService.exec` grew an `env` parameter; an empty one passes no options at all, so materialization, removal and script runs stay on exactly the transport they had.

**The ticket's alternative was a shape-preserving elision, and it is not implementable here — which is a fact about the value, not about the effort.** The mask's model works because Cloudgate authors the wire shape it recognises. A container-exec command has no Cloudgate-authored _internal_ grammar: it is arbitrary shell, and every candidate token class demonstrably can itself be the secret — the first word (`PGPASSWORD=… pg_dump`), a flag's value (`curl -H "Authorization: …"`), and the flag token itself (`mysql -phunter2`, the documented form, which any keep-the-verbs-and-flags rule leaks outright). The only implementable elisions are all-or-nothing, and never-carry beats all of them. Two residuals are recorded rather than claimed away: the host shell expands the holder into `docker`'s argv, so the value is in the host's process table for the life of the exec — exactly as `--env KEY"=$CG_BUILD_ENV_0"` puts a build variable into nixpacks' argv, unavoidable for a program `docker exec` must receive as an argument, and no worse than before; and setting an environment moves the program onto the remote shell's stdin, so the `docker exec` carries `< /dev/null` for the reason `RemoteExecService`'s `buildEnvScript` gives.

**The title of this ADR and its filename now understate the rule.** They are left alone on purpose, the way ADR 0006's and ADR 0017's amendments were: the number is what every docblock cites, and a renamed file is a broken citation in exchange for a heading nobody reads twice. The rule is the paragraph above, not the title.

**Consequences.**

- The property lives in `backend/test/coding-standards/secret-bearing-columns.spec.ts`, in two halves. `NOT_SECRETS` holds a plain column with a credential _name_ to a written reason; `ENCRYPTED_BY_ARGUMENT` holds an encrypted column with an innocent name to one, and asserts that the vocabulary genuinely cannot reach it. The second half exists because this rule's columns are invisible to a name match by construction — adding `script`, `file`, `content` or `command` to the vocabulary would match `dockerfile`, `composePath` and `description` and be widened straight back into silence — and because a `text`/`encryptedText` swap is invisible to the compiler and to `drizzle-kit`, so a revert of one of these would otherwise ship green. **It holds five columns now**: the three first named, plus `compose.composeFile` and `schedule.command`, which is the one entry that is not a file body.
- A new column that stores an operator's program text is `encryptedText` by default, and the change is a one-line schema edit plus the two assertions shipped for `schedule.script`: the author gets the exact bytes back over an HTTP round trip, and the host receives plaintext. Both are needed — a column that encrypts correctly and ships `enc:v1:…` to `base64 -d` is a silently broken feature, because every other assertion in a scheduling or mount suite matches on the path and not the payload. **The `schedule.command` change is the proof that neither is decoration**: run against the unconverted column, the ciphertext half fails and the plaintext half passes, and against a conversion that forgot to decrypt it would be the other way round. For a value that never becomes a file the second assertion is about the _environment_ rather than a base64 payload (`schedule.command`), and it comes with a third: that the program string carries nothing to elide.
- Classifying a column under this rule obliges a check for where the value is _echoed_, because a docblock calling a column a secret while a log prints it is worse than the plain column was. **The two conversions since have both earned that obligation its keep, and in ways the bullet did not anticipate**: one found a _third-party parser's_ diagnostic channel printing a line of the document to stderr on a path with no exception in it, and another found the echo deciding the ordering of the whole change — the command's journal echo had to be closed before the column could honestly be called a secret, and the deployment-log echo had to be shown to be inside the entitlement that already reads the column rather than outside it. **Ask both questions of an echo: who can see it, and is that the audience the column already has.** **The compose-label change is the first where that second question had two answers for *one* refusal, and it is the shape to reuse.** Two compose refusals — `composeFileParseRefusal`'s and `ComposeLabelRefusal` — quote the operator's own file back, which is right for the audience `compose.composeFile` already has (a 400 to whoever sent the bytes or owns the stack they sit on) and wrong for the audience `DeploymentEngineService.deployCompose` adds: its `catch` hands **one string** to `appendErrorToLog`, whose reader is behind the same `checkRowAccess` predicate as the column, *and* to `notifier.buildError` — email, mattermost, telegram, pushover and a **customer-supplied webhook**. So the refusal takes an audience (`ComposeRefusalEcho`, `'verbatim' | 'summary'`) rather than the sink taking a mask, and it **defaults to `summary`**, so a call site in another module that passes nothing gets the safe answer — the direction-of-forgetting rule. `ComposeLabelRefusal`'s byte-free form is a *required* constructor argument for the same reason: a default is how the next refusal added to that guard would leak, and the compiler is the only thing that makes the author of a new one answer this bullet's question. **Three things that change found that the ticket had not, and the third is the general lesson.** First, the leak was worse than filed: an earlier fix moved the raw injection *in front of* the clone, so for a `raw` stack `writeDomainsToCompose` sees the file before the guard does and threw `yaml`'s error **raw** — first line, caret diagram and all, with neither the trim nor the 500-unit cap — so fixing the guard alone would have left the ticket's own example untouched. Second, `composeFileParseRefusal`'s docblock claimed the `YAMLParseError` arm was *"bounded by the library's own vocabulary"*, and measurement on the installed yaml 2.9.0 refutes it: `Block scalar header includes extra characters: ${source}`, `Could not resolve tag: ${source}` and `The ${source} tag has no suffix` each put an unbounded slice of the document before the first newline (977, 954 and 952 code units from a 907-byte token), while two of the ticket's three named examples do not survive — `Not a valid tag:` is unreachable because a `tag` token always starts with `!`, and `Unexpected ${token.source} in …` reads an indicator token, so it is one of `-`, `?`, `:`. Third: **an echo check has to be run against the seam that throws first, not against the guard that is documented as owning the refusal.** The cost of doing this at the refusal rather than at the sink is recorded rather than hidden — the log is summarized along with the notification, because one string serves both — and the one line that would restore the log's verbatim words is in that `catch`, splitting the two sinks with `composeContentRefusalSummary`. For `schedule.script` the echoes are: back to its own author, through `GET /schedules` and the create/update responses, which is the one echo the classification permits; and, on a failed host write, into the journal as the base64 payload of the command that failed — which was the pre-existing exec-layer path this rule did not claim to close, and which is now closed at `ExecError`'s constructor rather than at any of the thirteen builders. The check this bullet asks for therefore has one fewer standing answer, and the reason to keep making it is unchanged: the elision recognises _this_ wire shape, `echo <base64> | base64 -d`, and a future builder that ships a body some other way would need its own pass. What a redacted error still shows is on `elideEncodedPayloads` — every verb, every path, the exit code, the `serverId` and the body's decoded size; only the bytes are gone.
- **That obligation immediately found two secrets the wire-shape elision did not cover, and the reason is worth keeping.** Both are `encryptedText`, both reached the journal in clear, and neither was a file body: `registry.password`, which travels as `printf %s '<the password>' | docker login … --password-stdin`, and `sshKey.privateKey`, which `git-providers/strategies/git.strategy.ts` wrote as `echo '<the PEM>' > /tmp/cloudgate/id_rsa` — the `echo` anchor with no `| base64 -d` after it. The docblock listing what the elision covered named "certificate keys", which was true of traefik's (they go through `getCreateFileCommand`) and false of this one, and nothing in the code distinguished them. So the rule this ADR states is necessary and not sufficient: **a column being a file body is what makes the wire shape predictable, and a secret that is not a file body has its own shape or none at all.** The SSH key now ships in the same base64 shape as every other body, which is the answer that scales; the registry password keeps its command shape and is elided on it, because it is `docker`'s wire format rather than Cloudgate's. Both fixes are recorded with their reasoning at `common/logging/error-payloads.ts`, which now also records in prose the shapes that would defeat the pattern and are unreachable from `src/` today — a chunked payload, `echo -n`, `base64 --decode`, a heredoc, `set -x`, and `https://<token>@host`.
- **A mask is the second-choice answer, and this is where the first choice lives.** A secret that never enters a command string cannot be journalled, mis-elided, or leaked by the next tool that reads the string; a mask has to keep being right. `RemoteExecService`'s `RemoteExecOptions.env` is that first choice — assignments travel as a script on the SSH channel, `ExecError` records only the command, and neither the process table nor a shell history sees them. It was not used for the registry login because it is not reachable from a _composed_ program without changing how every deployment command is delivered to a host, and the reasons are on `safeDockerLoginCommand`. Anything new that must hand a host a credential should take the environment and not the command string, and should not read this bullet as permission to add a fourth pattern instead.

- **The build-env change took the first choice, and the sentence above needs one correction rather than a repeal.** Every builder but `drop` put the operator's resolved `application.env` / `project.env` / `environment.env` — and `buildArgs` and `buildSecrets` — on a build tool's command line, and all of it is now in `RemoteExecOptions.env` (`backend/src/builders/build-env.ts`). What made that reachable is **where the values originate**, which is the distinction the paragraph above did not draw: a build's environment is resolved inside `DeploymentEngineService` itself, so nothing had to be threaded back out of `SourceCloneService.cloneCommand`'s string return — the obstacle that really did block the login sites. The other three obstacles the mask recorded turned out to be smaller than they read, and each is now measured rather than asserted: the composed `( … ) >> logPath 2>&1` needed no change at all, because an environment is _prepended_ to a program rather than woven into it; the local branch's `ExecOptions.env` replacing rather than extending is one `{ ...process.env, ...env }` at the call site, which `destinations/rclone-exec.ts` had already been doing for the same reason; and the `sh -s` substitution costs nothing here because these programs are POSIX — no `pipefail`, no `[[`, and the one bash they want they invoke explicitly. An empty environment passes no options at all, so a build with nothing to protect stays on the transport it has always used.

  Two things came out of doing it that are worth carrying forward. The value does not have to travel under the operator's own name, and it should not: a _holder_ (`CG_BUILD_ENV_0`) keeps operator-chosen names out of the build shell's environment, where `PATH` and `LD_PRELOAD` are live, and it sidesteps the fact that `RemoteExecService`'s `ENV_NAME` is stricter than the `[\w.-]+` dotenv allows as a key. And a command can _reference_ a value it does not carry — `--env KEY"=$CG_BUILD_ENV_0"`, expanded by the remote shell — which is what lets never-carry work without depending on any build tool's own env-var flag form. The same two ideas are what would close the registry password: `safeDockerLoginCommand`'s obstacle is the string return type of a clone command, not the environment.

  The mask does not go away, and one place in the builders still needs it: with `createEnvFile` set, the operator's environment _is_ a file body, so it travels base64 through `getCreateFileCommand` like a mount's content and is removed by the elision this ADR already records. That is the honest division — never-carry where the value is an argument, the covered wire shape where the value is a file.

- **A later change took the fourth site, and the last sentence of the paragraph above is now history rather than state.** It said _"`safeDockerLoginCommand`'s obstacle is the string return type of a clone command, not the environment"_, and that obstacle is gone: `GitProviderStrategy.clone` became `cloneProgram` and `SourceCloneService.cloneCommand` became `cloneProgram`, both returning `{ command, env }` — `BuildProgram`'s shape, for `BuildProgram`'s reason. The blast radius was measured rather than feared: **three production callers and no `src/` file outside `git-providers/`, `registries/` and `deployment-engine/`**, against 42 mechanical call sites in twelve specs. So both registry logins are never-carry — `printf %s "$CG_REGISTRY_PASSWORD_0" | docker login …` for a push, `CG_SOURCE_REGISTRY_PASSWORD` for a private image's pull — and `STDIN_CREDENTIAL` matches nothing this tree emits. **It stays anyway, and its status changed rather than its code:** it recognises `docker`'s own wire format, so the next caller holding a password is covered before review. One correction it did need is worth carrying forward: a holder _reference_ is a perfectly good match for a credential pattern's shell-word class, so the mask's first act on a never-carry login was to rewrite `"$CG_REGISTRY_PASSWORD_0"` as `'[credential elided]'` — deleting the diagnosis the new shape adds and asserting a secret had been in a string that never held one. A pattern that recognises shapes has to be taught to recognise _references_ as not-secrets when never-carry lands beside it.

  **And one credential is deliberately still on a command line: the git providers' tokens.** `github`, `gitlab`, `gitea` and `bitbucket` put theirs in the _userinfo of a URL_ `git` must receive as one word, so an environment reference cannot replace it without a credential helper or `GIT_ASKPASS`. Those four remain `URL_CREDENTIAL`'s, which is the honest division: never-carry where the value is an argument, a mask where the value is inside a word a tool's own grammar requires.

  **A Docker API service spec is a third case this ADR had not named, and the answer there is not never-carry.** That change's other half was `redis-server --requirepass <password>` in a swarm `ContainerSpec.Args`. Measured on Docker 29.3.1: `docker service inspect` returns `Args` and `Env` side by side in clear in the same document, so moving a value between them buys nothing, and neither reaches an `ExecError` or the deployment log at all — the spec goes over the socket, not through a shell. What `Args` _did_ have that `Env` does not is an audience needing no Docker socket: it becomes the argv of a live wrapper process whose `/proc/<pid>/cmdline` is world-readable, where `/proc/<pid>/environ` is `0600`. The password is in that spec's `Env` regardless — it is the connection credential the operator's own applications read — so the fix was to reference it (`--requirepass "$CG_REDIS_REQUIREPASS"`) rather than to add a Docker secret that would remove one copy and keep the other. **The rule to carry: for a service spec, ask which audience reads which field, not which field looks safer.**

- **A later change re-ran the echo check on the four `yaml.parse` sites the first sweep did not reach, and it sharpens two things written above.** The first is the mechanism. The third consequence's sentence compresses `parseDocument`'s prettify and `log.warn`'s emit into one clause, and it reads as though `parseDocument` logs. Measured on the installed yaml 2.9.0, it does not: it prettifies `doc.warnings` and hands them back _on the document_, and **only `parse` iterates them into `log.warn`** — `parseAllDocuments` does not either. So the echo site is exactly `parse`, which is what makes the property pinnable and what bounds the sweep; `TraefikFilesService.toggleRequests` uses `parseDocument` and needed nothing, and giving it the option would have asserted a property the library does not have. `backend/test/coding-standards/yaml-parse-log-level.spec.ts` holds the property — no `parse` in `src/` may inherit the default `logLevel` — and its last `describe` runs the detector over synthetic sources, because an empty offender list is also what a broken walk produces.

  The second is that **this ADR's two echo questions had their first _narrower_ answer, and the change was made anyway.** All four Traefik sites' sink is this process's own stderr: its reader operates the Cloudgate host, can already `cat` every file involved and holds `APP_ENCRYPTION_SECRET` and every Server's SSH key, and the product serves that stream to nobody at all — `isPlatformContainerName` refuses the platform's own containers on every container-addressed route. Traefik configuration also has no at-rest classification to defeat: it is plaintext on a disk because Traefik has to read it, which is not the shape the first sweep closed, where the bytes' authoritative home was an `encryptedText` column and the echo put them in a store the column type exists to keep them out of. So the general test is worth stating in the words the check now has: **an echo whose audience is strictly inside the source's own is not a disclosure, and the reason to close it has to be a different one or there is no reason.** Here there were two, and both are per-site rather than about the library: the **trigger**, because `GET /settings/traefik/requests` is ADR-0013's named any-authenticated-user carve-out and its only gate returns for an absent `serverId`, so any signed-in member of any organization drives the echo on demand; and the **content**, because `dynamic/{appName}.yml` is a file Cloudgate itself writes bcrypt `basicAuth.users` entries into while `TraefikVerifyInput.secrets` cuts those same bytes out of every message that file's own verifier stores or serves. `TRAEFIK_YAML_PARSE_OPTIONS` carries the per-site record and the rejection of `'silent'`, which stands on the first sweep's measurement.
