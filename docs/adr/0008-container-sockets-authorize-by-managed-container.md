# Container-addressed sockets authorize by managed container, not by machine

Cloudgate's container security model asked one question — *which machine?* — and never *which workload?*. The Docker routes gated every container procedure on `docker:read` plus an organization check that ran only `if (serverId)`; the three container-addressed sockets (`docker-container-logs`, `docker-container-terminal`, `docker-stats`) dropped even the permission half and authenticated only. `checkServiceAccess` appeared in the mount and database services, and in none of the container code on any transport. The local branch — no `serverId`, meaning the platform's own machine — was wide open. Together with `memberRole`'s `docker: []`, that produced an asymmetry: a base member was refused `GET /docker/containers` and handed an interactive shell inside any container on the host over `/docker-container-terminal`.

Cloudgate instead authorizes a container-addressed socket against the **Service that owns the container**. On connect the gateway resolves the target to its owning Service — by reading `com.docker.swarm.service.name` / `com.docker.compose.project` off the container on whichever machine is being addressed, or directly from `appName` for the stats socket — and gates on `checkServiceAccess`. A container that resolves to no Service is *unmanaged*, and is reached through machine-level Docker access instead — `docker:read` for the read-only routes, and `docker:write` for the writing ones — the five destructive verbs and the file upload. **Amended: on the platform host that is not the whole gate.** Machine-level Docker access is an *organization* capability and the platform host belongs to no organization, so an unmanaged container there additionally takes `PermissionService.checkInstanceAuthority`. A named Server is unchanged. ADR-0013 carries the decision, the rejected alternatives and the cost; the check sits in `ContainerAccessService.authorizeAppNames` rather than in `authorizeContainer` because a socket's lease renews the former and never the latter. The entitlement model was already enforced this way everywhere a service is addressed by its own id; containers were the one address the gateways could reach it by without asking whether the caller was entitled to the workload behind it.

Consequences, all deliberate, which a future change should not "correct" back:

- **Entitlement, not machine access, governs a managed container.** `docker:read` is *not* additionally required. Requiring both would deny every base member the logs of their own services, because `memberRole` has `docker: []` and container logs exist on no other transport — a feature removal delivered inside a security fix. Machine access governs unmanaged containers only, where there is no Service to ask about. **And machine access alone governs them only on a named Server** — on the platform host it is machine access *plus* instance authority. The half of this bullet that matters is unchanged: a **managed** container is still entitlement and nothing else, on every machine, so no base member loses the logs of their own services.
  **Amended: machine access is no longer one action.** `docker` gained a `write` statement, and `containerOp` — `stop`, `kill`, `start`, `restart` and `docker rm -f` — asks for that rather than `read`, because a *read* statement authorising five destructive verbs made the destructive path more permissive than the benign one (a custom role holding `docker: ['read']` could `docker rm -f` a container while being refused `POST /settings/traefik/reload`). The bullet above is unchanged in substance: entitlement still governs a *managed* container and `docker:write` is still not additionally required for one. What changed is only which machine-level action an *unmanaged* container's destructive routes ask for. Existing custom roles holding `docker: ['read']` lose those five verbs and must be re-granted `docker: ['read', 'write']`; owner and admin hold the new action outright and the built-in member role held no `docker` action to begin with.
  **Extended: the verb list is six, not five.** `uploadFileToContainer` — `docker cp` of a caller-supplied file to a caller-supplied path — was the one route the earlier move to `docker:write` scoped out by name while leaving a note that it had been considered, and it was the same defect one route over: a *read* statement let a licensed custom role write arbitrary bytes into any managed container it could address. It asks for `docker:write` too. Two things were decided rather than fallen into. **`write` now means more than it did**: not only "change this container's lifecycle" but also "put a file inside it" — a third `docker` action whose only holder would be one route was rejected in favour of keeping the statement table small. And it landed **immediately rather than batched** with any further `docker` narrowing, so operators re-grant twice; the alternative was leaving a known hole of the class this ADR closes standing to save one re-grant, which is the trade that move had already refused. Same migration story as above, one route wider: a custom role using `docker: ['read']` to upload must be re-granted `docker: ['read', 'write']`. `getConfig`, which shared the old gate, is a genuine read and stays on `docker:read` — it is now the only *container-addressed* route that asks for `read` alone.
- **The `if (serverId)` conditional stays.** It is not the defect it looks like: `checkServerAccess`'s own first line returns undefined for an absent `serverId`, so "no server row to check" is the deliberate contract for the platform host across the whole HTTP surface. What the gateways were missing was never an unconditional lookup — it was any authorization at all for the host branch.
- **`IS_CLOUD` is not restored as the local branch's gate.** Per-managed-container entitlement is strictly stronger and more precise than refusing local container access wholesale, and `IS_CLOUD` stays a billing flag here rather than a feature gate — the same reasoning as ADR-0007.
- **A swarm-addressed target is resolved as a service, not as a container.** With `runType=swarm` the socket's parameter is a swarm *service* name rather than a container id — `docker service logs` takes one, and the console sends it for every database and for a compose stack's services. A `swarm.Service` object has no `.Config`, so inspecting it with the container template does not come back unlabelled, it errors; treating that as "unknown container" would close 4003 on every database's own owner. Swarm targets are inspected `--type service` and resolve through `.Spec.Name` (an Application's swarm service is called its `appName` outright) or `com.docker.stack.namespace` (a stack's is `${appName}_${serviceName}`, which matches no row). That third label is therefore an owner label alongside the two named above: a compose row with `composeType: 'stack'` deploys as a Swarm stack whose containers carry the namespace and not a compose project, and without it every stack container would read as unmanaged and be denied to the people who own it. **`runType` travels with the id** from any gateway that accepts one, because it is what decides which question the daemon can even answer about that name. Only the logs socket does: a terminal is `docker exec`, which takes a container and nothing else, and the stats socket names its workload directly.
- **Labels are read on the machine being addressed, not locally.** A remote target's labels come back over the remote-execution layer. Reading them locally would authorize one machine's socket against another machine's containers.
- **One close code and one reason for every denial.** Not-entitled, unknown container, and an ambiguous resolution are byte-identical on the wire, so the socket is not a container-enumeration oracle across organizations; the distinction goes to the journal. **The decision was not upheld on `/listen-docker-stats-monitoring` until later** — verified on a host, 18/18 reproducible: a name owned by nobody fell through `authorizeAppNames`' `owners.length === 0` branch to machine `docker:read` and answered `4000 Container not running`, while a name owned by a Service in another organization threw first and answered `4003 Not found or not permitted`, so the two were distinguishable by close code to any caller holding any valid key. The REST refusal had the same shape one layer up (`403 No such container` against `403 Container belongs to a service in another organization`). The decision itself was right and the implementation was what deviated, so it was recorded here rather than rewritten, and a later fix brought the implementation to it: every container-addressed refusal now says `CONTAINER_DENIAL_MESSAGE` and the cause goes to the journal, and the stats socket resolves an `appName` naming no Service to the container it actually names and authorizes *that* by its owner labels — the same rule this bullet states, applied to the one socket that was exempt from it. The runtime state that used to reuse `4000` has its own code, `4011 No running container to sample`, which is only reachable by a caller already authorized against that container. This follows ADR-0007's denial precedent rather than the silent codeless `ws.close()` that `realtime/server-access.ts` uses for an organization mismatch — a shape filed as a defect in its own right.
  **Amended: the rule covers the check standing *in front* of a branch, not only the branches themselves.** The enumeration fix brought the three refusals inside `ContainerAccessService.authorizeAppNames` to one sentence and left the `docker: ['read']` check ahead of its machine branch answering better-auth's own *"unauthorized to access resource \"docker\""* — a sentence that names the resource, where every branch behind it said `CONTAINER_DENIAL_MESSAGE`. So one caller got two answers: one for a container no Service owns and the other for a container somebody else's Service owns, a fifth distinguishable answer of the class the enumeration fix closed four of, arriving from in front of the branch rather than from inside it. **Which caller, measured rather than assumed, because the obvious answer is wrong.** Not a base member: `memberRole` grants `docker: []`, but all three container-addressed routes on `DockerOpsService` ask for a `docker` statement of their own before the gate, so a base member is refused identically for every id and never arrives. Not a socket either: `socket-access.ts`'s `denyConnection`, `authorizedOrDeny` and `armAuthorizationLease`'s `end` each send a fixed reason and put the cause in the journal. What arrives is a caller who clears the *route's* statement and fails *this* one — and those stopped being the same statement when two changes moved the five destructive verbs and the upload to `docker: ['write']` while this branch kept asking `docker: ['read']`. `CustomRolesService`'s `validatePermissions` accepts `docker: ['write']` with no `read`, so a licensed custom role granted exactly that read the two sentences apart from `POST /docker/containers/:id/stop`, on the platform host and on its own Server alike. That is an HTTP hole rather than a seam-only invariant, and it is the correction this amendment makes to its own first draft. Every judgement this gate makes now goes through one private `deny` — the one sentence and the one journal line in one place, which is what stops a sixth site; `resolveTarget`'s `Could not inspect` stays outside it, because that line records a target the daemon would not answer about rather than a decision, and `container-sockets.e2e-spec.ts` reads the two prefixes apart on purpose. **`PermissionService`'s message is deliberately untouched**: `docker: ['read']` is an organization capability whose own refusal is the right answer on `GET /docker/containers` and the swarm routes, where there is no container id to leak, so making `checkPermission` quieter for everybody to close a leak in one branch was rejected. Two pins, because the hole and the invariant are not the same claim: `docker-ops.e2e-spec.ts` asserts the write-only role's two refusals byte-identical over HTTP, and `container-access.e2e-spec.ts`'s *"every refusal says the same thing"* is widened to a caller holding `docker: []` at the seam — it had only ever used callers who **held** `docker: ['read']`, so it never reached the statement check at all, which is how this survived the enumeration fix.

  **Amended: the rule governs the outcome of a resolution that ran, and a machine that was never reached is answered before the resolution.** The rule as written above covered every failure, so a Server that could not be reached *at all* was refused `403 Container not found or not permitted` on `GET /docker/containers/:id/config`, the five lifecycle verbs and the upload, and `4003 Not found or not permitted` on the three container sockets — an *authorization* claim about a machine nothing spoke to, on every container-addressed surface on both transports. That is the species the enumeration fix closed one turn worse: that oracle lied about which containers exist, and this lied about who the reader is. A transport failure is now taken out of the swallow ahead of the resolution — `503 HOST_UNREACHABLE` with *"This Server could not be reached"* on HTTP (`docker-ops/host-reachability.ts`'s `rethrowIfHostUnreachable`, the split made for `runtime-info` and X11-4 made for the Docker readers) — or, `503 PLATFORM_HOST_UNREACHABLE` with *"The platform host could not be reached"* where there is no `serverId`, since a claim about a Server is as wrong on the platform's own machine as an authorization claim was about an unreached one — and close code `4012` carrying whichever of those two sentences applies on a socket (`socket-access.ts`'s `UNREACHABLE_CLOSE_CODE`, the next free code after `4010` and `4011` and in that band for the same reason: it is not a judgement of the request — one code for both arms, because a close frame has no `code` field and the sentence is already on the wire). **The enumeration fix's guarantee is untouched, and the argument is why this is an amendment rather than a reversal:** the enumeration oracle is about *the outcome of a resolution that actually happened*, and a transport failure happens before one — no id was looked up, no label was read, no owner row was queried — so the frame discloses nothing about whether the container exists or who owns it, for the same reason `GET /settings/runtime-info` answering `observed: null` discloses nothing about the probe's subject. On a Server that answers, not-entitled, unknown-id, ambiguous-resolution and the platform's own are still byte-identical on both transports, and the paired e2e assertions in `test/docker-ops/docker-ops.e2e-spec.ts` are where that pairing is pinned rather than assumed. The two arms are told apart by `ExecError.exitCode` and never by a message match, so `docker inspect` having run and answered *no such container* is still a denial — `isTransportFailure` reads a rejection that is not an `ExecError` as "not a transport failure" on purpose, and the direction of that guess is what keeps the fix from widening into "any exec rejection is a transport failure".
  **Amended: the branch beside the machine one had the same shape, and the audit that found it says where the rule does *not* reach.** An earlier fix wrapped the statement check standing in front of `authorizeAppNames`' machine branch and left the branch next to it — `checkServiceAccess`, the entitlement question a **managed** container takes — `await`ed bare, so *that* method's two sentences travelled out of the gate verbatim: better-auth's *"You are not allowed to access resource: service"* for a role holding no `service` action, and *"You don't have access to this service"* for a member row that does not name the Service. **So *not-entitled*, the first of the three refusals the bullet above says are byte-identical, was the one that never was** — on HTTP, where the sockets' normalization does not reach. Measured, not inferred, and the population is that fix's one statement over: a licensed custom role granted `docker: ['read', 'write']` and no `service` statement clears every route on `DockerOpsService`, clears the machine branch, and is refused by this one — so it could partition every container id on a shared machine into *owned by a Service in my organization* and *owned by somebody else's, or by nobody, or not a container at all*, a distinction drawn by an authorization refusal rather than by a listing. The refusal is now translated through the same private `deny`, cause to the journal, and the wire pin is in `docker-ops.e2e-spec.ts` beside that fix's while `container-access.e2e-spec.ts`'s *"every refusal says the same thing"* gains the entitlement branch it had never exercised. **The lesson that fix's "one place to throw from" missed: the leak was a *delegated* refusal, not a second `throw`** — nothing in this class threw the wrong sentence, it let another class's out — so what is funnelled now is every call out of the gate that can refuse, and that is the shape to look for next.

  **The audit itself, because "we checked" is worth as little as "it is not reachable" was.** The audit asked whether any other id-bearing route has the pattern *a statement check in front of an object lookup whose refusal is indistinguishable from "not found"*. It does not, and the reason is structural rather than lucky: a refusal can only be an oracle across ids when the check is reached for some ids and not others, and every other statement check in `backend/src` is reached **before** anything is resolved — either as the route's own `@RequirePermission`, which the global `PermissionsGuard` runs uniformly for every id by construction, or on a branch chosen by a caller-supplied `serverId` rather than by a resolved row (`ClusterService`/`SwarmService.instanceOrServerScoped`, `CertificatesService.create`/`update`, `ForwardAuthService.assertTargetAuthority`, `PatchRepoService.cleanRepos`, `MonitoringService.findReadableTarget`, `AiService.assertDestinationAllowed`, `ServerTerminalGateway.assertMayShellIntoTheHost`). The three that *are* chosen by a resolved row were each measured and each stays as it is: `SchedulesService.checkRowAccess` forks on `row.scheduleType` and answers a `cloudgate-server` row outside the caller's organization as an outright `404 Schedule not found` before any authority is asked, so the instance-authority refusal behind it can only ever describe a row the caller's *own* organization holds; `CertificatesService.update` forks on `current.serverId` behind an organization-scoped `findRow`, with the same consequence; and `TemplatesService.assertEnvironmentTarget` already catches its `ForbiddenException` and answers `ENVIRONMENT_DENIAL_MESSAGE`. **And `PermissionService` is still untouched**, for the reason that earlier fix gave: `docker: ['read']`'s own refusal names the capability an operator has to grant, which is the right answer on `GET /docker/containers` and the swarm routes, where there is no id in front of it to leak.

- **An ambiguous resolution fails closed.** `appName` is `.unique()` per service table but not across them, so a resolution matching more than one Service is a denial, not a first-match win.
- **Preview deployments resolve through their parent Application.** A preview's `appName` is unique and lives in its own table, not among the eight; entitlement is the parent Application's. Without this, the service gate would silently break every preview's logs and terminal.
- **Extended: HTTP reads keyed on an `appName` take the same gate.** `GET /docker/containers/search`, `/by-label`, `/stack` and `/service` answer by a Service's name rather than by a container id, and asked only for an organization statement and `ownedServerId`, so a base member of any organization listed every organization's containers on the platform host by name prefix. They now call `ContainerAccessService.authorizeAppName` before any exec: the name is resolved to its Service exactly, a foreign, not-entitled or ambiguous one is refused, an unresolved one takes the machine branch, and on that branch the platform's own names are refused as `authorizeContainer` refuses them. Every refusal is the one `CONTAINER_DENIAL_MESSAGE`. The listings then filter on the owner label the gate resolved by (`com.docker.swarm.service.name`, `com.docker.stack.namespace`, `com.docker.compose.project`, or an anchored `name=^<appName>$`), because authorizing one name and listing by prefix would still list a neighbour. **`GET /monitoring/metrics/containers` filters instead of refusing**: it keeps collection's substring lookup and answers from the best-ranked stored series the caller may read (`firstReadable`), so an unreadable series is indistinguishable from an absent one and the existing 400 is not a probe. The candidate names of every ranked series are resolved in one read and the verdict is asked once per distinct owner set, because the caller's substring chooses how many series there are. The platform's own series are deliberately not refused on this read, unlike on the four Docker reads: they resolve to no Service, and the machine branch's instance authority governs them, which this extension left in place. An instance admin no longer reads another organization's managed series on the platform host, which matches the logs socket. **The swarm routes stay outside this.** `GET /swarm/apps/info` is a machine-level read behind `instanceOrServerScoped`, and its sibling lists every Swarm service on the machine anyway (CONTEXT.md, *Managed container*). `container-route-statements.spec.ts` holds the rule: every `@Get` whose `@Query()` DTO has an `appName` key must reach one of these gates.
- **Amended: a shell into a managed container takes `service:update`, not `service:read`.** A shell writes inside the workload, and `service: ['read']` means read only, so the entitlement branch now asks for an action its caller names (`ContainerAccessService`'s `ServiceAction`, a required parameter on `authorizeContainer` and `authorizeAppNames`): `/docker-container-terminal` asks for `update` at connect **and at every lease renewal**, so taking the action off a role closes an open shell at the next renewal (ADR-0012); the log and stats sockets, the container routes and the `appName` reads keep `read`. This reaches the Servers → Docker shell too, since it is the same socket. **The cost lands on licensed custom roles alone:** owner, admin and the built-in member hold `service:update` and see no change, and a custom role holding `service: ['read']` and no `update` keeps the logs of the Services it is entitled to and loses their shell; to restore it, add `update` to its `service` actions. Nothing is migrated on its behalf, on the reasoning the service and project narrowings gave for their own. **Unmanaged containers are untouched**: they keep the machine gate above, whatever the action. **The Service-scoped listing is the same gate in HTTP form.** The Shell tab finds a Service's running containers through `GET /docker/services/:serviceType/:serviceId/containers`, addressed by the Service's own id, gated by `ContainerAccessService.authorizeService` on that same `service:update` and on no `docker` statement — so a built-in member entitled to the Service can find its container, which no machine-level listing let them do, and whatever the listing offers the socket accepts. It carries no `@RequirePermission` on purpose: the route guard would refuse a role lacking the action in better-auth's own sentence, and every refusal here — no such action, not entitled, another organization's Service, an id naming nothing — is `CONTAINER_DENIAL_MESSAGE`, pinned in `service-containers.e2e-spec.ts`, and on the socket the fixed `4003`, pinned in `container-sockets.e2e-spec.ts` for a read-only custom role's own, foreign and missing container ids alike. It lists with `docker ps` on the Service's own machine, so a replica on another Swarm node, which `docker exec` there could not reach, is never offered.
- **Amended: on the platform host a label is only the Service's when the Service runs there.** The resolution read a label and never asked where the Service it named runs, and a customer picks their own `appName`, so any container on the shared machine carrying a label that matched a customer's Service on their own Server was that customer's to shell into, stop, `rm -f` and `docker cp` into. `authorizeAppNames` now sends a Service whose place is a Server or a Cloud account to the machine branch when the machine is the platform host, which there takes instance authority; `unownedAppNames` reads the listing the same way. A named Server is deliberately not held to it: a Service's swarm tasks may run on a worker that is a Server of its own, and that Server is already the caller's Organization's. The stats socket, which only ever samples the platform host, also stopped asking Docker's substring `name` filter: a Service is sampled by its exact owner label and a container name by an exact match, so a Compose called `traefik` no longer streams `cloudgate-traefik`.
