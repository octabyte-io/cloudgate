# An instance-wide resource takes instance-level authority, and there now is one

ADR-0010 asked the right question and could not answer it. Its fourth consequence is explicit: *"There is no instance-level authority in this codebase to gate on, and this decision does not invent one … an owner or admin of **any** organization on the instance passes … If an instance-level role is ever introduced, this is one of the call sites that should move to it."* That ceiling was named for the host shell and applied by inheritance to everything else that reaches the platform host through `SettingsService.requireOwnerOrAdmin`. On one of those surfaces it is not a ceiling, it is a bypass. The forward-auth settings are instance-wide by construction — one Traefik, one `dynamic/forward-auth-domain.yml`, one oauth2-proxy that **every** organization's gated Domain dials — so an owner of any licensed organization could point that single proxy at their own `sso_provider` by sending `serverId: null`, and `OAUTH2_PROXY_EMAIL_DOMAINS=*` then admits whatever identity that issuer mints. That is a cross-organization authentication bypass rather than an over-broad admin role (H-51). `dynamic/cloudgate.yml`, the console's own router file, has the same shape through three writers (H-52): `POST /settings/assign-domain`, `POST /settings/traefik/web-server-config`, and `POST /settings/traefik/file` with no `serverId` — the last behind `traefikFiles:write`, which a licensed custom role can hold.

The hole is not a missing lookup. `checkServerAccess` returning `undefined` for an absent `serverId` is deliberate and documented as such — ADR-0008's second consequence, restated in `common/owned-server.ts` as *"The absent-id branch is not a bug — do not 'fix' it"* — because the platform host has no `server` row to find. What was missing is the second question, the one ADR-0010 named: **not "may you reach this row" but "do you administer this instance"**, asked of the host branch rather than assumed from the caller's organization role.

**The authority is the instance organization's owners and admins**, in `PermissionService.checkInstanceAuthority`: the Organization `bootstrapDefaultOrganization` created for the instance's first user, found as the earliest `member` row whose role is `owner`. It exists on every install that anyone can sign into, because `hasInstanceOwner` — the same row — is the predicate that *closes* sign-up, and it cannot be taken away through the API: `updateMemberRole` refuses to set or clear `owner` ("The owner role is nontransferable") and `OrganizationsService.delete` refuses to take the last organization a user owns. It is a **no-op on the single-organization install** `deploy/install.sh` produces, where the one Organization is the instance organization and its owner and admins are exactly who `requireOwnerOrAdmin` already admitted.

Two alternatives were weighed and should not be "corrected" back. **The admin plugin's global `user.role`** is what ADR-0010 was looking at when it concluded no such authority exists — correctly, because `admin({ adminRoles: [] })` plus `input: false` means every row is `'user'` and no request can change it (H-10), so gating on it refuses *everybody*. Using it would have locked operators out of their own instance, which is the failure mode this decision most had to avoid. **The first *user* rather than the first Organization** is the narrower boundary and was rejected on cost: it would strip a single-organization install's admins of routes they hold today while buying nothing at all against a second organization, which is the entire threat.

Consequences, all deliberate:

- **Reads move with writes, on this surface.** These routes answer with the platform's own Traefik configuration — entrypoints, certificate resolvers, the console's router, the ACME email — so a boundary that admits the read hands another organization's owner the reconnaissance half of the same attack and confirms the resource is there. The white-labeling split (public read, licensed write) is not a precedent for it: that read is branding, deliberately reached with no session at all. `GET /settings/traefik/requests` is deliberately left alone — it answers one boolean, discloses no configuration, and is a documented any-authenticated-user quirk.
- **`requireOwnerOrAdmin` keeps its name and its meaning.** It is still the right question for a route that names a Server: an organization's owner administers its own fleet, and `serverId != null` behaves exactly as before, `checkServerAccess` included. ADR-0010 cites the symbol; renaming it on the way past would strand a decision on a symbol that no longer exists, which is the trap `common/owned-server.ts` documents about `checkServerAccess` itself.
- **This is not a new statement in the entitlement vocabulary.** ADR-0010's first consequence rejected gating host-level power on anything from `statements`, because a licensed custom role can be granted it and "Deploy engineer" would then quietly carry the platform host. The same reasoning holds here, so the check reads the static role and nothing else — which is also why `POST /settings/traefik/file` needed the host branch: `traefikFiles:write` *is* grantable, and it was the weakest gate on `dynamic/cloudgate.yml`.
- **ADR-0010's own subject has not moved, and that is now a known gap rather than a ceiling.** *(Discharged by H-63 below.)* The host shell at `serverId=local` still authorizes on the caller's organization role. Its last consequence asked for exactly this move once an instance-level authority existed; one now does, and a root shell on the platform host is strictly more than any Traefik file it has been placed above. Until that gateway moves, the instance answers the same question two ways.
- **The rest of `settings.controller.ts` has not moved either.** *(Discharged by H-63 below.)* `update-server`, `reload-server`, `infrastructure-health`, `clean-deployment-queue`, `docker-disk-usage`, the `cleanup/*` family, `gpu`, `runtime-info`, `ip`, `ssh-private-key` and `builds-concurrency` are all instance-wide and all still organization-gated. They are the same question and they should get the same answer; they were left out of the change that closed H-51/H-52 to keep that change reviewable, not because they differ.
- **Fail closed with no owner member at all.** Unreachable through sign-up, and a refusal is the only safe answer to "who administers this?". The two ways of failing the check share one sentence, so an unauthorized caller cannot learn whether the instance has an owner.

**Extended by H-64: the same decision, applied to four routes that asked nothing at all.** H-51 and H-52 were the *wrong* question asked of the platform host. H-64 is no question: `POST /settings/traefik/requests` gated on `checkServerAccess` alone, which returns for an absent `serverId` by design, so its host branch had no gate; `POST /settings/log-cleanup` took no `@CurrentUser` at all; `POST /monitoring/requests/logs` took none either; and `MonitoringService.findReadableTarget` answered an absent `serverId` with the web-server target before asking anything, behind a `monitoring:read` that the **base member role holds**. So the decisive caller on all four was a plain member of any organization, not a second organization's owner — verified over HTTP: a member switched the platform host's access log off, stopped its rotation, read every tenant's request hostnames and paths out of one access log, and read the host's own CPU and memory. All four now take `checkInstanceAuthority`, and the third bullet above is why: the access log names other organizations' hosts, URLs and services, so it is the case where "a read is cheaper than a write" is plainly false — the disclosure *is* the attack.

Two things this extension settles that the bullets above left ambiguous:

- **The `traefik/requests` carve-out is the read, and only the read.** The third bullet named `GET /settings/traefik/requests` and gave the reason — one boolean, no configuration disclosed — and that reason still holds and the route is still open to any authenticated user. The `POST` beside it is a write into the static `traefik.yml` and was never covered by it; reading the carve-out as covering "the pair" is what left it open.
- **`POST /monitoring/requests/stats` moved too, and the pair now takes one boundary.** It was the *gated* half — owner or admin in the caller's own organization — over the same one access log, so a second organization's owner was answered with the instance's hourly request volume: H-51's shape, quieter. Gating the rows at instance authority and leaving the chart above them at organization authority would have put two answers to one question on one screen.

`POST /admin/setup-monitoring` is the same question still answered the old way *(closed by H-63 below)*: it writes the platform host's `metricsConfig` behind `SettingsService.requireOwnerOrAdmin`, so any organization's owner sets the thresholds and collection interval for the machine every organization runs on. It belongs on the list in the second-to-last bullet above, which names `settings.controller.ts` only.

**Extended by H-63: the two bullets above that promised a later move, and the machine itself.** H-51/H-52 fixed the platform host's *Traefik*. H-63 is the rest of the host, and the ordering was backwards — a root shell and a cron job on the machine are strictly more than any file it serves.

- **The host shell has moved, and ADR-0010's last consequence is discharged.** `serverId=local` on `/terminal` now takes `checkInstanceAuthority`. The gateway keeps its own sentence and its `4403`, because the wire contract is a console-rendering concern and not an authority one; the refusal deliberately still says "an owner or admin" without naming *which* organization, so a refused caller learns nothing about the instance's shape. The check sits where it already sat — before the parameters are read — which is §2.10's rule and the reason this gateway was the one of six that had it right; a `4403` therefore strictly precedes the `4400`s, so a caller who is both unauthorized and malformed is told only the first. Nothing in the close contract changed.
- **`cloudgate-server` schedules have moved, and they were the sharpest hole in the batch.** `scheduleType: 'cloudgate-server'` hard-codes `serverId: null`, materializes a `script.sh` under `schedulesDirectory()` and cron-runs it as the backend process user: **persistent arbitrary code execution on the platform host**, reached by an owner of any second Organization. Every verb takes the boundary, not only the writing ones — `list`/`findOne` are already `organizationId`-scoped and disclose nothing, but the *target* does not change with the verb.
- **The platform host's swarm has moved.** `cluster.service.ts`'s four routes fork on the same absent `serverId`. `GET /cluster/add-manager` is why the read takes the write's boundary here and the argument is sharper than the first bullet's: a **manager** join token is not a disclosure, it is an invitation — whoever holds it joins a node to this swarm as a manager, which is the raft quorum, every service spec and every secret in it. There is no second request to gate; the read *is* the compromise.
- **The list in the second-to-last bullet above is done**, plus `cleanup/monitoring`, `docker-cleanup`'s host branch, and `POST /admin/setup-monitoring` from H-64's closing paragraph. The sharpest is `POST /settings/cleanup/volumes` — `docker volume prune --all --force` on the platform host takes every volume no running container holds, which is **other tenants' data**, destroyed by a caller who was never a member of their organization.
- **`GET /settings/log-cleanup` moved with the `POST` H-64 gated, and it is where the `traefik/requests` carve-out stops.** That carve-out is one boolean; `LogCleanupService.getStatus` answers `{ enabled, cronExpression }`, which is the schedule the host rotates its access log on — configuration, and the operational half of the write beside it.
- **The delegation an operator really makes is why this primitive fits the destructive routes, rather than a narrower "instance owner".** Docker hygiene on the platform host is a job an operator hands to an admin, and `checkInstanceAuthority` admits the instance organization's owners *and* its admins — the same set `requireOwnerOrAdmin` admitted on a single-organization install. The only caller it newly refuses is a *different* organization's admin, who has no host here to keep tidy. No route in this batch was better served by a different boundary.
- **One premise in the brief was wrong and is corrected here.** The instance's `sshPrivateKey` is *not* "the credential the platform dials every organization's Servers with" — that is `ssh_key.private_key`, resolved per Server through `SERVER_KEY_PROVIDER`. Nothing outside `settings.service.ts` reads `webServerSettings.sshPrivateKey` at all. The route still moves, because it writes an instance-wide secret column on the singleton, but what it closes is a cross-organization write and not a fleet takeover. *(Later: the column and both `ssh-private-key` routes were removed — a key nothing reads is a credential at rest with no benefit, and it had leaked through three responses.)*
- **Extended: two surfaces this enumeration does not name, and the second is a decision rather than a fix.** `PatchRepoService.cleanRepos` gated on the caller's role in their *own* organization and then globbed `{patchReposDirectory()}/*` on the platform host, so an owner of any second Organization deleted every organization's patch-repo clones in one call — ADR-0010's fourth consequence verbatim, on a destructive route. It takes `checkInstanceAuthority` on the host branch now; the named-Server branch keeps `requireOwnerOrAdmin`, per the second bullet above. Scoping the glob to a per-organization subtree was preferred in the abstract and rejected on three counts: it orphans every existing install's clones, since the two-segment tree is what is on disk and this route is the only thing that removes from it; no query can name the *deleted* service's clone, which is precisely the residue this route exists to clear, so a row-derived delete would leave the garbage while appearing to have run; and H-63 already answered the same question the same way for `cleanup/volumes`, which destroys data rather than a re-clonable cache. `CertificatesService.create`/`update` write PEM material into the platform host's certs directory behind `certificate: ['create']`, which every organization's owner and admin holds outright and a licensed custom role can be granted — the third consequence's case exactly. Traefik merges every certificate's fragment (`dynamic/certificate+<certificatePath>.yml`) into one `tls.certificates` and selects on the SANs *inside* caller-supplied material, so this is not an exception: the host branch of both writes takes instance authority. Two splits are deliberate — `remove` and a rename keep organization authority, because `certificatePath` is server-minted and unique per row, so nothing shared is reachable and an organization can always withdraw a host certificate it created. **The cost, unlike every earlier surface in this ADR, is a refusal of something legitimate:** a tenant whose Domain terminates on the platform host must now use the resolver or ask the instance operator. Validating the material's SANs against the organization's own Domains is the structural answer and is open. Finally, an enumeration in this ADR **cannot** be made self-checking by a tree-wide test, and the certificate fix measured why: a per-tenant write to the platform host is the *default* in this codebase — eighteen `src` files fork on an absent `serverId` and nearly all legitimately — so the trigger does not discriminate and would need a twenty-row semantic excuse list, which is this prose relocated; and it has false negatives covering the certificate fix's own second surface, since what makes the certificate store instance-wide lives in Traefik's selection rules rather than in the code that writes one entry. What is testable is per-module: each service's method key set asserted against a map naming the boundary each method takes, so a new method goes red by name until someone writes its boundary down.

  **Amended: a certificate's fragment sits at the top of `dynamic/`, not in its own directory.** It was `dynamic/certificates/<certificatePath>/certificate.yml`, and a new certificate, or new material over an existing one, was not served until an unrelated top-level file changed: `traefik:v3.6.7`'s file provider reads subdirectories at each reload but watches only `dynamic/` itself (measured). The PEM pair stays in `dynamic/certificates/<certificatePath>/`, `0700`; only the fragment moved, renamed into place from a file created `0600` (`replaceOwnerOnlyFile*`), since `dynamic/` stays open. `+` is outside `APP_NAME_REGEX`, so no Application's file can take the name. A save removes an earlier version's `certificate.yml` after the new fragment is in place, and a Delete removes the fragment, then the directory; when that directory held a legacy `certificate.yml`, the Delete then creates and removes a `0600` file beside the fragment, so the removal raises the reload a subdirectory cannot. None of this moves the boundary above: every fragment is still merged into the one store.

**Extended: the third surface, and the one where the boundary had to be placed so a *socket* could re-ask it.** `ContainerAccessService.authorizeAppNames`' machine branch is where an **unmanaged container** lands — anything no Service owns, per CONTEXT.md — and ADR-0008 sent it to machine-level Docker access, correctly for the question ADR-0008 was answering (*who governs a container no Service owns*) and without asking this ADR's (*which machine is it on*). On the platform host the two checks in front of it were both organization-level: the `docker` statement is a capability `ownerRole` and `adminRole` hold as `['read', 'write']` and a licensed custom role can be granted — the third consequence exactly — and `DockerOpsService.ownedServerId` resolves an absent `serverId` to `undefined` by design. So an owner or admin of **any** organization could `stop`, `kill`, `restart`, `rm -f` or `docker cp` into an operator's own sidecar on the machine every organization's services share, read its logs, and open an interactive `docker exec` shell in it. `memberRole` holds `docker: []`, so a base member was never in scope. The `isPlatformContainerName` carve-out already refuses Cloudgate's *own* containers on both of its call sites — the listing filter in `DockerOpsService.getContainers` and `authorizeContainer` itself — which is why what was left is everything an operator runs *beside* Cloudgate, `cloudgate-monitoring` included by construction since the predicate deliberately excludes it. The machine branch now takes `checkInstanceAuthority` when there is no `serverId`; a named Server keeps the `docker` statement and `checkServerAccess`, per the second bullet above.

Four things this extension settles that the certificate fix's two surfaces did not have to:

- **The check lives where a lease can renew it, and that is not an implementation detail.** Three sockets reach this branch, and ADR-0012's lease re-runs *`authorizeAppNames`* — never `authorizeContainer`, whose `docker inspect` is the one step a socket captures at connect. The natural reading of the recommendation was to put the check beside the platform-container carve-out in `authorizeContainer`; that would have been asked once and never again, so a refused caller kept streaming an operator's sidecar for as long as they held the socket, which is the connect-only-authorization defect reintroduced one gate below the six gateways it was filed against. So `authorizeAppNames` takes the target's `serverId` as a **required** parameter and the three gateways pass it in their renewal thunks. Required rather than defaulted deliberately: a default would silently pick a machine, and the renewal is the call site nobody remembers.
- **The refusal is translated to `CONTAINER_DENIAL_MESSAGE`, not passed through.** `checkInstanceAuthority`'s own sentence names the platform host, so letting it out here would tell a caller *"that id resolved to no Service"* apart from *"that id belongs to a Service you may not reach"* — the enumeration oracle ADR-0008 closed and its one-close-code bullet forbids, reopened by its own fix. The cause goes to the journal like every other cause on this surface. This is the one place where ADR-0008's wire vocabulary outranks this ADR's refusal sentence; contrast the host shell, which H-63 let keep its own `4403` sentence because no enumeration hangs off it.
- **"The platform host" is the absence of a `serverId` and not a machine identity.** `!serverId` is the contract (ADR-0008's second consequence), so a `server` row an operator registers *pointing at the platform host* is still that organization's own Server, reached over SSH through its row and governed by `checkServerAccess`. Nothing in this codebase recognises the platform host by address, and this decision does not start: an operator who registers the host as a Server hands that organization's owners and admins the old boundary back, on this surface and on every earlier one in this ADR. Recorded as a known residue rather than closed here, because closing it means deciding what identifies a machine.
- **The stats socket's host branch moved with the containers.** `appName=cloudgate` on `/listen-docker-stats-monitoring` samples the machine itself through `HostStatsService`, names no Service, and so took the same machine branch — which means H-64's *"a member read the host's own CPU and memory"* was closed on `MonitoringService.findReadableTarget` and left open one transport over, on `docker:read` rather than `monitoring:read`. It takes the same boundary now. That socket has no `serverId` parameter at all, so its target is the platform host by construction.

**What legitimately loses access, checked rather than asserted.** Not a base member (`docker: []`). Not the single-organization install's owner or admins, who *are* the instance organization's. Not any container a Service owns, on any machine — entitlement answers those and this branch is never reached. Not Cloudgate's own surfaces for its own containers: `/settings/traefik/*` and the runtime probes never went through the container routes, and the platform-container carve-out already refused those containers here. What loses access is an owner or admin of a **second** organization, and a licensed custom role granted `docker` — including one in the instance organization, since `checkInstanceAuthority` reads the static role and nothing else, which is the third consequence's price and the same one the certificate fix paid on `certificate: ['create']`. Unlike that certificate surface there is no legitimate tenant use behind it: an unmanaged container on the platform host is by definition not any tenant's Service. **That consequence is pinned rather than hidden**, on the same precedent set in `certificates.e2e-spec.ts`: `docker-ops.e2e-spec.ts`'s destructive-verb and upload blocks proved their claim about the `docker` statement against an unmanaged container on the platform host, so their unmanaged target moved to a Server in the role's own organization — where the statement really is the whole gate — and the refusal they used to assert as an allowance is now its own test beside them. `containerOp` and `uploadFileToContainer` carry the operator-facing half, and it is the one note in this ADR that no re-grant answers.

**Extended: the listing follows the operation path, and that is the second decision the amendment above deliberately did not take.** That amendment put the boundary on `ContainerAccessService.authorizeAppNames`' machine branch, which is what every container-*addressed* surface reaches — three HTTP routes and three sockets — and left `DockerOpsService.getContainers` alone. So on the platform host the listing kept offering rows the routes then refused: an unmanaged container came back to any holder of `docker: ['read']`, filtered only by `isPlatformContainerName`, carrying its image, its published ports, its state and the **container id** the container routes act on. That is the disagreement the listing rule exists to prevent — its stated purpose is that *"the same definition of 'managed' decides which rows a listing may show and which containers a socket may reach"* — reopened one layer up by the amendment's own fix, and `isPlatformContainerName`'s docblock records what it cost the first time.

The narrowing is this ADR's **first consequence** applied unchanged: a boundary that admits the read hands another organization's owner the reconnaissance half of the same attack and confirms the resource is there. It is not that reasoning stretched to a weaker case either, because the listing's own justification for keeping the row had stopped being true: `getContainers`' docblock kept unmanaged rows on the ground that they *"are reached through machine-level Docker access per CONTEXT.md"*, and on the platform host the amendment is what made that sentence false. The listing asks `ContainerAccessService.hasMachineAuthority` once for the whole response and drops every row resolving to no Service when the answer is no.

Four things worth writing down:

- **The listing rule's decision is applied rather than reversed.** Unmanaged rows still stay visible — on a named Server, and on the platform host to the instance organization's owners and admins, which is everybody who can act on them. What changed is not which rows count as unmanaged but who administers the machine they sit on, and the listing now asks that through the same method the routes ask it through.
- **Two questions, each asked in the shape its own answer has.** *Which machine, and does this caller administer it* cannot differ between rows of one listing — `ownedServerId` resolves `serverId` once — so `ContainerAccessService.hasMachineAuthority` is asked once for the whole response, and the alternative of batching it per name would have been a query for a constant. *Is this row unmanaged* genuinely does differ per row, so it is asked in `foreignAppNames`' shape, as `unownedAppNames`, over the same set of names and beside it. **Asking it of the parsed owner labels instead was the first draft of this narrowing, and it was wrong**: the listing's `owners` array is what `docker ps` printed and the acting path's *unmanaged* is what the Service relation answers, and the two part company for a container an operator started with `docker compose -p my-monitoring up`. That row carries `com.docker.compose.project`, so a label filter keeps it — while `authorizeAppNames` resolves the name, finds no Service, takes the machine branch and refuses the id. The label version would have closed the disagreement for every `docker run --name` sidecar, which is the platform's own containers and `cloudgate-monitoring`, and left it open for exactly the rows nobody would think to check. Measured: with the label filter in place, `docker-ops.e2e-spec.ts` hands a second organization's owner `my-monitoring-grafana-1` and refuses her `POST /docker/containers/ddd444/stop` in the same run. The cost of the resolution version is one more `ownersNamed` — two indexed `IN` queries — and it is paid **only** on a listing the narrowing can actually change, since `getContainers` asks it only when `hasMachineAuthority` said no.
- **The amendment's third ground for leaving this — that the disagreement is not visible in the product — was wrong, and the screen it is visible on is the one that makes the case.** The claim rested on `ContainersCard`, which renders with `serverId={server.serverId}` and whose query is disabled for an empty id, so the Server tab genuinely never asks about the platform host. But that card is one of three callers. `monitoring/live-card.tsx` calls `dockerApi.containers(null)` — the platform host, by construction — and feeds every **running** row into the live-stats `Picker` through `targetOptions`, and the amendment had *already* refused those unmanaged targets on `/listen-docker-stats-monitoring` (its fourth point above: that socket's machine branch takes this boundary and has no `serverId` parameter at all). So a second organization's owner was offered picker options whose socket then closed `4003` on selection — the disagreement, on screen, in the shape a user meets it. This narrowing makes the picker agree with the socket, so the visible change is an option list that no longer offers what it cannot sample. The third caller, `compose/containers/use-stack-containers.ts`, also passes `compose.serverId` and so reaches the platform host for a stack deployed there — and is untouched, because every row it joins on is **managed**: a compose project's containers carry `com.docker.compose.project`, a Swarm stack's carry `com.docker.stack.namespace`, and both are owner labels. The Image and Ports columns it reads this route for keep their source.
- **The cost is the set the amendment already named, and no larger.** A second organization's owner or admin, and a licensed custom role granted `docker`, including one in the instance organization since `checkInstanceAuthority` reads the static role and nothing else. They lose the *rows* for exactly the containers they already could not touch, so no listing now hides something its reader could still act on. A base member was never in scope: `memberRole` holds `docker: []` and `getContainers`' own statement gate answers first.

**And the dead singular spelling went with it.** `ContainerAccessService.authorizeAppName` had no caller in `src` from the moment the stats socket moved onto `resolveAndAuthorize`, and the amendment noted that in its docblock rather than deleting it. It is gone, its e2e cases re-pointed at `authorizeAppNames`: the decision above is about which entry points reach the machine branch, and taking it against a method nothing calls would have been taking it against a list that was already wrong.

**Extended: the two writes to the `web_server_settings` singleton that were still organization-level, and the question this ADR had left silent — *whose licence* gates an instance-wide feature.** Neither write appeared in any enumeration above, which is how they survived H-51, H-63 and the certificate fix: those batches walked the routes that fork on an absent `serverId`, and these two never mention a Server at all. The singleton is the platform host by construction — one row, no `serverId`, no organization column — so "instance-wide" here is a property of the *table*, and the trigger every earlier batch searched on does not fire.

- **`SettingsService.updateEnforceSso` is the sharper of the two and is why the pair moved together.** `enforceSSO` is one boolean on that row and `SsoService.enforceSso` reads it with no organization in the query, while the gate was `requireOwnerOrAdmin` — the caller's role in the organization they are *currently acting in*. So an owner or admin of any second Organization could take password sign-in away from every Organization on the instance, or hand it back after an operator had deliberately removed it. This is ADR-0010's fourth consequence verbatim on the **login path** rather than on a Traefik file, and the console says so in its own voice: `EnforceCard` calls it *"the most dangerous control in the console and it is not close"*, because F06's sign-in screen renders no password form at all while it is on. The licence is still deliberately not asked here and that is not an oversight left standing — the *off* direction is the recovery path, so a gate that can lapse is a gate that can strand an instance in SSO-only mode with no screen left to leave it from.
- **`SettingsService.updateWhitelabelingConfig` is the H-51 shape with the enterprise gate mistaken for a boundary.** `whitelabelingConfig` is one `jsonb` column on the same row, so an owner or admin of any second, licensed Organization wrote the app name, logo, favicon, colours, CSS and error-page copy that every *other* Organization's members and every anonymous visitor to the sign-in page render. Its gate was a private `ensureEnterprise` asking two questions of the caller's own active Organization, and the bundling is why the defect survived review: the method *looked* like a licence check, and it was one, so the missing authority half read as present.
- **The white-labeling disclaimer in the first consequence above was about the read, and the write is now argued rather than disclaimed.** *"The white-labeling split (public read, licensed write) is not a precedent"* stands exactly as written — `GET /settings/whitelabeling` is still `@Public()`, still selects the branding column and nothing else, and still refuses to create the singleton for an anonymous reader. What that sentence never said is which callers the *write* admits, and it was read as though it had.

**The decision this extension exists for: an instance-wide feature's licence is the instance organization's.** ADR-0010's ceiling shaped the alternative already in the tree, and reading it as a precedent would have been reading a workaround as a decision. `LicenseService.hasAnyValidLicense` — *"whether **any** organization on this instance holds a valid license"* — was written for `SsoService.showSignInWithSso` when this codebase had no instance-level authority to name, as an approximation of a subject that is really the **instance owner's** licence row. So it is this decision's subject with no vocabulary to express it. Now there is one, and "any Organization's licence unlocks a switch that reaches every Organization" is the same cross-tenant defect, one level up: a second Organization that buys one seat would license the instance's branding for everybody. `SettingsService.requireInstanceLicense` therefore asks `LicenseService.hasValidLicense` of the Organization this ADR already made the owner of the instance-level surface.

- **This narrows nothing for the enterprise modules, and their gate is still right.** `SsoService.ensureEnterprise` and `CustomRolesService.ensureEnterprise` ask the licence of `ctx.session.activeOrganizationId` and keep doing so: an `sso_provider` and a custom role are `organizationId`-scoped rows, so the Organization that pays is the Organization that gets the feature, and the licence there is answering a commercial question about a tenant. The subject follows the *column*, not the module, which is the only rule that separates those two call sites from this one.
- **Entitlement and licensing are two questions and stay two methods.** `requireInstanceAuthority` then `requireInstanceLicense`, at the call site, in that order. Folding them back into one `ensureInstanceEnterprise` was the shorter diff and was rejected: a caller refused for authority ("this is not yours to configure") and one refused for licence ("this instance has not bought the feature") are different answers, and an operator debugging the second must not meet the first's sentence. `requireInstanceLicense` takes **no** `PermissionCtx` for the same reason — the subject of that question is the instance, and a signature that accepted a caller is the shape that produced the cross-tenant defect.
- **The order is load-bearing, on this ADR's own last consequence.** Whether this instance holds an enterprise licence is not a fact a second Organization's owner is owed, and `checkInstanceAuthority`'s refusal is written once so a refused caller learns nothing about the instance's shape. Asking the licence first would answer "is this instance licensed" to exactly the caller that boundary exists to refuse.
- **The resolution of "which Organization is the instance organization" is not copied.** `PermissionService.instanceOrganizationId` is the earliest-owner query extracted out of `checkInstanceAuthority` and made public for this one caller. Re-deriving it inside `LicenseService` was the obvious alternative and was rejected twice over: that service reads `member` directly *because* `PermissionService` injects it to resolve custom roles, so a dependency the other way closes a cycle — and a second copy of this ADR's own definition is a second decision waiting to disagree, which is the drift the exported `staticRoles` map exists to refuse. `SettingsService` already holds both services, so the composition sits there.
- **What legitimately loses access, checked rather than asserted.** Nobody on the install `deploy/install.sh` produces: the one Organization *is* the instance organization, and `whitelabeling.e2e-spec.ts` and `settings.e2e-spec.ts` now pin both its owner and an admin they invite writing both columns. Not a plain member, who was refused before and is refused now — with a different sentence, which is the one visible change to an existing caller. What loses access is an owner or admin of a **second** Organization, and, newly, a caller who holds instance authority while acting in another Organization that happens to be the licensed one: authority passes, the licence question is asked of the instance organization, and it answers no. That last case is the one the decision above is really about, and it is pinned as its own test rather than argued.
- **Two residues, recorded rather than closed.** `hasAnyValidLicense`'s two remaining callers are `SsoService.showSignInWithSso` and the deployment queue's builds-concurrency resolver; both are a public read and a capability resolver rather than an authorization gate, and neither was widened or narrowed here — but by the rule above their subject is now nameable and "any Organization's" is no longer the only thing they could say. And `SettingsService.getSanitizedWebServerSettings` still hands the whole branding blob to any authenticated user while `GET /settings/whitelabeling` hands the same blob to anybody at all, which is this ADR's first consequence pointed at a read whose two gates disagree; it was filed separately and deliberately, and it is not made worse by this change — the blob is now written by strictly fewer callers than could read it before.

**Narrowed by ADR-0023: instance authority is a person's.** `checkInstanceAuthority` refuses any Agent whatever its `member.role`, and every `member.role` write goes through one writer that keeps Agents on agent roles. The instance organization's owners and admins are its owners and admins *who are people*.

**Not a precedent against "reads move with writes": the counts-only GPU read.** `GET /settings/gpu/counts` answers a machine's cards and free count to anyone who may create a Service there, because choosing a GPU reservation needs them and a refused save says as much; the driver, runtime and CUDA inventory beside it stays on `maintenanceTargetAuthority` with the setup it targets.

**Narrowed by ADR-0061: the platform host's access log rows.** H-64 moved `POST /monitoring/requests/logs` and `/stats` to instance authority because the one file names every organization's hosts, paths and Services. On a self-hosted instance that left an Organization running Services on the platform host with no view of its own requests. The log is now read as its Services, the way a Server's is (ADR-0055), with matching that fails closed: a line goes to an Organization only when its host is held there by that Organization alone. Unmatched lines, lines whose host is shared, and the Request logging switch keep instance authority.

**Narrowed by ADR-0067: a managed container's stored metrics.** H-64 put `findReadableTarget`'s platform-host branch behind instance authority before any series was resolved, which also refused a non-instance Organization its own Services' container metrics. Container series are now decided per series: a managed container by entitlement to its Service, as CONTEXT.md's **Managed container** says; an unmanaged or `cloudgate-*` one, and the host's own metrics, keep instance authority.

**Amended by ADR-0077: the instance organization is pinned, not found.** "The earliest `member` row whose role is `owner`" above is no longer how it is found. That row moved whenever the one it named was deleted, and handed this authority to the next-earliest owner. The Organization is now recorded once in `instance_organization`, and a pin naming an Organization that no longer exists names nobody. The claim above that the Organization "cannot be taken away through the API" now also covers deleting it: every app path refuses, and the database refuses through any other path.
