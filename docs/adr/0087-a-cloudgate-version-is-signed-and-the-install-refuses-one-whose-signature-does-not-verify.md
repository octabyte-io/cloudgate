# A Cloudgate version is signed, and the install refuses one whose signature does not verify

Status: accepted. Built in #52: `deploy/version-sign.sh` signs both CPUs' `.sha256` in publish-version.yml, and root `install.sh` carries the public key as its `VERSION_SIGNERS` line.

The `.sha256` beside a version's tarball comes from the same GitHub Release, so it proves the download arrived whole, not that we published it: anyone who can write a release can replace both. **The publish workflow signs the checksum with an SSH key held as a GitHub Actions secret, and `install.sh` carries the public key and verifies the signature with `ssh-keygen -Y verify` before anything is unpacked.** A version without a valid signature is refused, with nothing changed. `ssh-keygen` comes with `openssh-client`, which a stock Ubuntu Server has; on a minimal image without it, the install adds `openssh-client` with `apt-get` before it downloads anything, as it does `curl`.

Chosen over Sigstore keyless signing, which needs no key to look after but makes every box download `cosign` before it can verify anything, and over GitHub artifact attestations alone, which only someone with `gh` checks: the box would still trust the checksum. The cost is one secret to keep and rotate; a rotation ships the new public key in `install.sh` before the first version signed with it. `VERSION_SIGNERS` is an allowed-signers file of one line per key, so during a rotation it holds the old key and the new, the install accepts a signature by either, and `deploy/version-sign.sh` checks what it signed against all of them; the old line is dropped once no version signed with it needs installing.
