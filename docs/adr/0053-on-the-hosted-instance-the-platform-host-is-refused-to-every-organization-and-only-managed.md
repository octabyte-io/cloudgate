# On the Hosted instance the platform host is refused to every Organization and only managed

On a Self-hosted instance an absent `serverId` means the platform host, and `checkServerAccess(null)` admits it on purpose (ADR-0008, ADR-0010). On the Hosted instance that box is shared by every customer, so it runs no Organization's Services, Octabyte's included, and no customer-triggered commands. With hosted mode on, every request that would create a Service there or run a command there is refused with `PLATFORM_HOST_REFUSED` (400). Services and Environments get *"This Cloudgate doesn't run Services on its own host. Choose one of your Servers or Cloud accounts."* Connection tests (the rclone destination and restore probes, the registry `docker login` probe) get *"This Cloudgate doesn't run checks on its own host. Choose one of your Servers to run it from."* The Instance organization keeps all of its authority to manage the box (Traefik, settings, Docker cleanup, host certificates and monitoring, the host shell, swarm and unmanaged containers). It just has no Services there, like everyone else.

**Amended 2026-11-10 (ADR-0070, #1372): a console Compose stack in a cloud Environment is never asked for a Server.** It runs on its own Stack VM in the Environment's Cloud account and region, so it does not reach the `runServerFor` seam below and never lands on the platform host on either instance. A body that leaves `serverId` out gets the stack on its Stack VM, not *"Choose one of your Servers, or this Cloudgate host on purpose"*. A body that names the platform host (`serverId: null`) is refused: on the Hosted instance with this ADR's sentence and code, on a Self-hosted instance with *"Leave the Server out"*, as a named Server is on both. So the Consequences' Self-hosted platform-host landing in a cloud Environment no longer holds for a Compose stack; it still holds for an Application and the other kinds a cloud Environment's console create asks a Server for. A stack created on the platform host before this keeps its place.

- **Where it is refused.** One refusal function, owned by the instance-mode module (ADR-0049), is called at the four seams the census found: the Deploy target (`resolveOnHost` no longer picks or accepts the platform host), `runServerFor` (a console create in a cloud Environment with no Server named), `checkServerAccess(null)` on every Service-creating and probing caller, and `compose.createByTemplate`, which templates and AI deploy reach without that check. Off hosted mode, nothing changes.
- **The console** removes "This Cloudgate host" from the Deploy target and every create form. It does not show it greyed out.
- **An Environment needs somewhere to point.** With no Server and no Cloud account, making an Environment is refused, and the console sends the person to add a Server or connect a Cloud account. So every Environment still has exactly one Deploy target. A Project with no Environment is fine.
- **A Server cannot be the box itself.** On the Hosted instance a Server address on loopback, link-local or a private range, or one of the box's own addresses, is refused when saved and again at every SSH connect, so a hostname that changes later cannot reopen the host.
- **Turning hosted mode on** with the hand-run mode command refuses while any Service is still on the platform host, and lists them.
- **The census gate.** One test lists every caller of `checkServerAccess` and every place a Service row is inserted. Each is marked either "host management (instance authority)" or "refuses the platform host in hosted mode". A new one fails the test until its author picks. Work that follows a Service's own place (builds, Trace stores, previews, backups, schedules, rollbacks) needs no refusal of its own on a Server-hosted Service: with no Service on the host, it has nowhere to land. **A Service in a Cloud account is the exception**: its `serverId` is `null`, which every exec dispatcher reads as the platform host, so work that follows its place through `serverId` lands on the box. Volume backups, file and volume mounts and command schedules need its own container or volume, so they are refused for it with `CLOUD_SERVICE_HAS_NO_CONTAINER` (409), in every mode, at create, update and every run. A second census (`cloud-service-exec-census.spec.ts`) lists every function that calls an exec dispatcher and marks each cloud-staging (clone, patch apply, source zip, static publish copy and image push, ADR-0047), refusing a cloud Service, a machine's own, Cloudgate's own records, only a Service on a Server, or open; a new one fails until its author picks.

## Considered Options

- **Quietly choose a Server instead.** Rejected: an Organization's work would land somewhere it never named, and one with no Server would still need an answer.
- **Show the platform host greyed out with a reason.** Rejected: a choice that never works is noise. The refusal sentence covers API callers.
- **Refuse only inside `checkServerAccess(null)`.** Rejected: host-management routes call it too, and templates and AI deploy reach `createByTemplate` without it.
- **Let connection tests keep running on the host, since they leave nothing behind.** Rejected: they run customer-supplied credentials and endpoints on the shared box. The customer's backups run on their own Servers anyway.
- **A database trigger refusing host rows.** Rejected: Service rows live in many tables. The code census is cheaper and fails at review time.

## Consequences

- Uptime probes, request-metric collection, the deployment queue and timers, OpenTofu Cloud runs, SSH forwards, cloud-build source zips (ADR-0047) and the AI Gateway still run on the box. They are the "only manages" part.
- A Self-hosted instance keeps every behaviour it has today, including a console Application in a cloud Environment landing on its platform host.
- The console hides the platform host's pages from every customer on the Hosted instance, for the reason the Deploy target leaves it out rather than greying it: Settings → Traefik, Instance, Maintenance and Branding are listed only for an Operator, and their addresses say in one sentence who they are for. Requests was hidden the same way until it read each Server's own access log; it is offered to every customer again.
