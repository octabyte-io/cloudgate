# A Delete reclaims each artifact on the machine that made it, and every row it destroys is asked what it left behind

ADR-0016 settled *when* a machine-side artifact is reclaimed: by the delete that destroys the row naming it, because that is the only moment at which the artifact, the machine and the entitlement to that machine are all known at once. It said nothing about *which* machine, because the one artifact it was about — the preserved `${appName}:v${version}` tag — already carried its own answer in `preservedImageServerId`. This ADR is the same question asked of the artifacts that do not, and it found the answer wrong or missing in three places at once:

- `DeploymentEngineService` clones an Application's source into `{applicationsDirectory()}/{appName}/code` on `buildServerId || serverId`, and both Delete paths ran their `rm -rf` on `serverId`. On an install with a dedicated build Server the removal was issued to a machine that had never held the directory: it exited non-zero, the best-effort `catch` around it swallowed the failure, and the build tree survived every delete for ever. ADR-0016's own list of non-goals names this exactly — *"the source tree under `applicationsDirectory()` when the build ran on a different machine from the removal"* — and left it as its own ticket. This is that ticket, and that bullet is amended in place rather than merely superseded here.
- Neither Delete path named a preview deployment at all. `preview_deployment.applicationId` is `onDelete: 'cascade'`, so deleting an Application, an Environment or a Project dropped every preview row in one statement while each preview's Swarm service kept running.
- `PreviewDeploymentsService.teardown` took one `serverId` for both of its steps, while `deployPreview` spreads the parent Application's row into `engine.deploy` so `buildServerId` survives into the clone. Same defect as the first, one table along, on the route an operator reaches by closing a pull request — but **latent where the first two are live**, and the difference is worth stating because it is what decides how much of this ADR is a bug fix. `deployPreview` forces `registry: null` and `buildRegistry: null`, and a preview exists only for `sourceType: 'github'`, so `assertBuiltImageReachesRunServer` throws *before the clone* for every preview whose `buildServerId` differs from its `serverId`: a preview on a dedicated build Server cannot be deployed at all, so its `rm -rf` was never actually sent to the wrong machine. This is therefore a consistency fix against a state `assertBuiltImageReachesRunServer` currently refuses, made because the two Servers are two and the state becomes reachable the moment a preview inherits a Registry or that refusal narrows. The bullet above it — no delete path naming a preview at all, leaving its Swarm service running on the run Server — is live on the default single-Server install, and is the security-adjacent one.

Settling those turned up a fourth, of a different kind and on every install: **the one teardown step whose failure nothing could see.** A Delete's presence read asks the *run* Server about a Swarm service, so it answers for the `docker service rm` and for nothing else. The `rm -rf` is on the build host, is the only thing in the product that removes that tree, and a failure of it — an unreachable builder, a permission the SSH user does not have — was caught by the best-effort `catch`, discarded, and named in no field of the response. On the commonest failure the presence read answers `absent` about the workload perfectly correctly, so the route answered a clean 200 having leaked a directory it knew it had not removed. That is the second half of this ADR's title.

**Cloudgate states the build-host rule once, in `deployment-engine/build-host.ts`'s `buildHostServerId`; every Delete asks each artifact which machine it is on rather than assuming the Service's own; and a teardown step the presence read cannot see says for itself what it left.**

## Why one rule and not one expression per call site

`buildServerId || serverId` is nine characters and was written out in exactly one place — the deploy — which is the place that could not get it wrong, because it is the place that creates the artifact. Every consumer either kept a paraphrase of it under a different name (`RollbacksService`'s `preservedImageServerId`) or kept no copy at all and reached for `serverId`, which is the answer to a different question: *where does the workload run*.

One of those consumers is a **write**, which is why the rule and not just the deletes had to be fixed. `ApplicationsService.uploadDrop` unpacks a `drop` archive into the same `{appName}/code` the clone writes, and it too reached for `serverId` — its own docblock said *"into the application's code directory on its build server"* while the code said otherwise. So a drop upload landed the tree on the runner and the build looked for it on the builder; and correcting only the Delete would have *moved* the leak rather than closing it, writing the tree to one machine and `rm -rf`'ing it on the other. Whoever creates an artifact and whoever destroys it have to answer *which machine* the same way, and the only way to guarantee that is for it to be one question with one answer.

The two questions have the same answer on the default single-Server install, where `buildServerId` is null and the fall-through returns `serverId`. That is why every one of these call sites was green in every test that exercised it, and it is the whole mechanism of the defect: **a wrong-machine bug is invisible to any test that asserts only the words of the command.** `rm -rf /etc/cloudgate/applications/web-app` is byte-identical whether it is sent to the builder or to the runner. So the tests that hold this now assert *which host was asked*, and assert that the other host was not — `test/applications/application-delete-machines.e2e-spec.ts` takes the "where the artifact is" half from the engine's own clone dispatch rather than restating it, so the expectation comes from the code that made the artifact.

`buildHostServerId` is a plain exported function rather than a method on `DeploymentEngineService`, on `common/service-cascade.ts`'s precedent: four modules ask it, and asking a service for a `||` would point `applications`, `common`, `preview-deployments` and `rollbacks` at `DeploymentEngineModule`.

## Consequences, all deliberate

- **A Delete now reaches two machines for one Service, and that is not an accident of configuration but the shape of the thing.** The Swarm service, the presence probe and the Traefik dynamic config belong to `serverId`; the source tree and the images belong to the build host. `CascadeChild` therefore carries both ids and `teardownStepsFor` decides per step which one it wants, rather than being handed one pre-collapsed id that hides the decision.

- **`buildServerId` is fetched where the cascade needs it, not added to the Environment read.** The obvious move was one line in `SERVICE_SOURCES.application`, and it is wrong twice: seven of the eight service tables have no build-Server concept, so seven arms of the union would carry a `null` literal to keep the shapes equal; and the union's row type *is* `EnvironmentServiceSummary`, served by `GET /environments/:id`, whose own contract is to be "deliberately uniform across the eight service types … a projection, not the service row". A cascade's teardown target has no business in a display read. So `listCascadeChildren` pays one extra select, skipped entirely when the tree holds no Applications.

- **A preview deployment is reclaimed by the Application's delete, in ADR-0016's slot rather than as a fourth teardown step.** It looks like a teardown step: it drops a Swarm service and a directory, exactly as the parent's own steps do. But those steps run *before* the presence read, and a Delete that is then refused answers 409 with the tree intact and tells the caller nothing was deleted. A preview teardown there would have destroyed the live preview environments of an Application the caller has just been told still exists — ADR-0016's "a recoverable refusal turned into silent breakage", at a second artifact. So it runs after the refusal and before the rows, which is also the only window in which `preview.appName` — the sole name either artifact has — still exists.

- **A surviving preview is reported, not refused over, and the reason is not that it matters less.** A preview's container is precisely ADR-0008's unmanaged container: with its row gone it resolves to no Service and becomes readable and actable through machine-level `docker:read` by every organization on the host, which is the earlier teardown finding reached through a table it never looked at, and "deleting a Project is one click" makes the bulk path the likely one. That finding named three acceptable answers — remove it, refuse while it exists, or say what is left behind — and this takes the first and the third: the Delete tears the preview down and names in `orphanedPreviews` any whose Swarm service it could not confirm gone. Refusing was rejected because `PreviewDeploymentsService.teardown`'s two existing callers, the closed-pull-request webhook and `DELETE /preview-deployments/:id`, are best-effort and drop the row regardless — a webhook has no operator to answer a 409 to — so making the Application delete refuse where the other two do not is where the rule drifts rather than where it holds. Whether all three should refuse is a question about `teardown` itself and is filed as one.

- **A directory the Delete could not remove is named in `unreclaimedDirectories`, and that is what makes the second half of the title true.** The teardown rule is *say what you leave behind*, and the source-tree removal was the one step exempt from it by accident: nothing refused, nothing reported, and the empty `catch` carried a comment saying what is left "is decided by the presence read" — which is true of the Swarm service and false of a directory on another machine. So the step now carries what it leaves if it throws (`common/teardown-steps.ts`'s `TeardownStep.leftBehindOnFailure`) and the three deletes answer with `{ appName, serverId, directory }` per tree, the parent Applications' and their previews' alike. **It reports rather than refuses**, on `reclaimPreservedImages`' two reasons: a leftover directory is disk and not ADR-0008's unmanaged container, which is the property `?force=true` exists to guard, and *forget this Application* must stay completable while a machine is down. **And it needs no second question asked of the machine**, which is why a probe — `test -d`, the shape `presenceProbeCommand` takes for a workload — was rejected: `rm -rf` exits 0 for a path that is not there, so a non-zero exit or a failed transport already means exactly *"this may still exist and I could not remove it"*. A healthy delete therefore reports nothing, and the field keeps meaning "these were left behind" rather than "this route can leak directories". `PreviewDeploymentsService.teardown`'s own two callers still drop the leak, because a webhook and a route that answers with the preview row have nowhere truthful to put it — the same asymmetry the refusal above records, and the same open question. **What still does not report, named so the title is read narrowly:** the Traefik dynamic-config removal, which is the third teardown step and has exactly the same shape — `rm -f` on the run Server, idempotent, so a failure means the file may still be there — and which no presence read covers either. It is left as its own item rather than folded in here because the artifact is a *file* and the field this bullet adds is about *trees*: naming both would mean one field called neither, and the harm differs (a stale router fragment routes a hostname at nothing, and `TraefikWriterService` is a boundary this ADR does not otherwise touch). So of a Delete's three machine steps, two now answer for themselves and the third is a filed gap. **Amended: the third step answers for itself too, and the field is renamed rather than doubled.** The gap this bullet filed is closed — the Traefik dynamic-config removal carries a `leftBehindOnFailure` (`applications/application-ops.ts`'s `removeTraefikConfigStep`) on both Application delete paths, so all three of a Delete's machine steps now say what they left and the title reads at full width. **The reason it could be folded in after all is that the objection was to a *name*, not to a shape.** This bullet declined to fold it because `UnreclaimedDirectory` was about trees and the config is a file, so one field would have been named for neither — and that is still true of *that* field, which is why the type is now `UnreclaimedArtifact` `{ kind, appName, serverId, path }`: `directory` becomes `path`, and a `kind` — `'source-tree' | 'traefik-config' | 'patch-repo'` — says which artifact an entry is. The response field is `unreclaimedArtifacts` on all three deletes, still absent rather than empty. **A second field beside the first was rejected, and the patch-repo clone is what settles it**: splitting on filesystem shape would put the clone in `unreclaimedDirectories` next to the source tree, indistinguishable from it unless a consumer parses `{applications,patch-repos}/…` out of the path — so a discriminant was needed either way, and once there is one, splitting the array as well is a second taxonomy answering a question nobody asked. The discriminant names the artifact rather than the shape for the same reason: what differs between the three is *what breaks*, and only one of them is not merely disk. A `'traefik-config'` left behind is a live router fragment on the run Server, so a public hostname keeps being advertised at a backend that is gone — the one entry here an operator has to act on now, and on a Project delete it is every hostname in the tree at once. Everything else this bullet decided is untouched: one mechanism (an idempotent removal whose non-zero exit already means *may still exist*), no probe, no second round trip, nothing reported on a healthy delete, and never a refusal.

- **One best-effort loop, in `common/teardown-steps.ts`, instead of three.** `ApplicationsService.remove`, `tearDownCascadeChildren` and `PreviewDeploymentsService.teardown` each ran the identical `for`/`try`/`catch` over an array of thunks, each with its own copy of the comment explaining the empty `catch`. Three copies of a rule that turned out to be right about two steps and wrong about the third is how the third stayed unreported, so the loop is stated once and a step is an object rather than a thunk — the step that knows what it is removing is the one that says so, instead of the loop guessing from a return value it cannot type (the compose arm's resolves to the teardown command's stdout, so *"a truthy answer is a leak"* would report a shell banner as a directory).

- **`orphanedPreviews` is its own field and never an entry in `orphaned`.** `orphaned` is what the 409 is decided on and what `cascadeRefusalMessage` counts against `children.length`; a preview is not a `CascadeChild` — it has no `service_type`, no row in the eight service tables and no `checkServiceAccess` of its own. Folding one in would make a forced delete indistinguishable from a clean one. Both fields are absent rather than empty on a healthy delete, which is `cascadeDelete`'s existing rule for `orphaned` and its stated reason.

- **`reclaimPreserved` and `tearDownPreviews` are both required parameters of `cascadeDelete`.** This is `teardownStepsFor`'s exhaustive switch one resource along, twice: a third cascade root that forgot either would destroy rows with no reclamation and nothing would say so. Two callbacks rather than one bundle because they are two artifacts with two owners, each named for what it does — and if a third joins them the pair should collapse into a `db` and a `PermissionCtx` on `CascadeDeps`, because at three the risk these required parameters exist to close is better closed by there being nothing to pass.

- **No `checkServerAccess` on the two ids a teardown execs against, and that is a difference from `reclaimPreservedImages` rather than an omission.** The rollback-context exposure is specific to `rollback.full_context`: a plain `json` column no foreign key constrains, whose ids were proved able to name another organization's rows, which is why ADR-0016 gates every machine it reaches. `application.serverId` and `application.buildServerId` are real foreign keys into `server`, authorized by `checkServerAccess` on the only paths that write them (`ApplicationsService.create` and `update`), and `buildServerId`'s `onDelete: 'set null'` means it cannot dangle. A gate on the build host and none on the run Server the same delete has been execing against would not be consistency but a second rule for the same column; if the FK-derived ids ever need re-checking at teardown time, both need it, and that is a change to the teardown contract rather than to this one.

- **What this still does not reclaim.** ADR-0016's non-goal list loses the source tree — amended in place, on that ADR's own bullet — and gains nothing: the `${appName}:latest` image on the build host, the buildkit cache beside it, the patch-repo clone and every deployment log file are all still left where they are, each its own ticket, with `docker image prune`/`docker builder prune` from Settings → Maintenance remaining the machine-wide sweep for the images among them. A preview's deployment logs go the same way as an Application's, for the same reason. **Amended: the patch-repo clone comes off this list for an Application, and stays on it for a Compose stack.** It was named here as its own ticket and that ticket landed. `PatchRepoService.ensureRepo` clones the entity's source a second time into `{patchReposDirectory()}/{type}/{appName}` on the build host so the patch editor can list and read the files a patch will land on — the same tree ADR-0016 reclaims two directories along, a private repository's contents included — and nothing reclaimed it: the only removal in the product is `cleanRepos`, a machine-wide glob on a Server an operator has to name and think to run, and that route's own docblock recorded the gap as a reason it may not be scoped per organization. So every clone outlived every delete under an `appName` no row named any more. It is now dropped by the delete that destroys the row naming it, in this ADR's own slot — after any presence refusal, before the rows — by `patch/patch-repo-clone.ts`'s `reclaimApplicationPatchRepos`, on `buildHostServerId`'s answer, and named in `unreclaimedArtifacts` as `kind: 'patch-repo'` when the build host could not be reached. **Two halves of it remain, deliberately.** A Compose stack's clone still outlives its row: `ComposeService.remove` is where that reclamation belongs, and doing it in the cascade alone would reclaim a stack's clone when its Project is deleted and not when the stack itself is — where a rule drifts rather than where it holds, which is the argument this ADR makes about a refusal one table along. And a clone whose build Server was unreachable at delete time is still on that machine; the delete now names it, which is all it can do. **Amended again, which is where this list ends.** The `${appName}:latest` image comes off it: all three deletes now reclaim it on `buildHostServerId`'s answer (`applications/built-image.ts`'s `reclaimBuiltImages`) and name it in `unreclaimedImages` when they could not, sharing that field with the preserved tags rather than taking a fourth `UnreclaimedArtifact` `kind` — an image reference is not a `path`, and what breaks is no different between a leftover `:latest` and a leftover `:v3`, which are `UnreclaimedArtifact`'s own two criteria for adding an arm. A docker-sourced Application reclaims nothing, because `builtImageName` answers the operator's own `dockerImage` there. The deployment logs come off it by a different mechanism, which is the half this bullet already predicted: they are stranded from birth rather than by any cascade, so ADR-0020 gives them a retention window and a nightly sweep of the tree instead of a teardown step — the only predicate that also reaches the logs whose rows this cascade destroyed years ago. **The buildkit cache stays, and that amendment turns it from a ticket into a refusal**: a BuildKit cache record has no image, tag or repository field to scope a prune by (measured on Docker 29.3.1 — `docker buildx du --verbose`'s field set names no output, and `--filter` answers `id`, `parents`, `description`, `type`, `until`, `unused-for` and three booleans while `ref=`/`image=`/`repository=`/`label=` match nothing), so one Application's delete cannot name its own cache and a machine-wide prune fired by one delete would be worse than the leak. `railpack` leaks none of *that* anyway — it `docker buildx rm`s a per-build container builder with no `--keep-state` — **which holds for a build that reaches one of its branches, and two later fixes disproved the wider reading for the kill path; the amendment at the end of this bullet carries it.** **Amended a third time, adding an artifact rather than removing one: a Compose stack's own built images.** They were never on this list because nothing had established what they are called, and the answer is not `${appName}:latest`: `docker compose build` names an image `${project}-${service}`, and the project is `appName` (`createComposeCommand` passes `-p ${appName}`; `getCreateComposeEnvFileCommand` writes `COMPOSE_PROJECT_NAME=${appName}`). Measured on Docker 29.3.1 / Compose v5.1.1 — a `build:` service with no `image:` tags `${project}-${service}:latest`, a `build:` service *with* `image: my-own-name:7` tags the operator's own reference, and a service with only `image:` builds nothing. So `ComposeService.remove` reclaims the first class on `compose.serverId` (`compose/compose-images.ts`' `reclaimComposeBuiltImages`) and names what it could not in `unreclaimedImages`, sharing the field with the Application's tags for the previous amendment's reason; and it refuses the second on that amendment's own docker-source reasoning, since `docker image rm` on a name the operator chose could untag a reference every other stack on the host is running. Two whole stack shapes name nothing and are refusals with the measurement rather than tickets: a `stack`-type stack, because `docker stack deploy` has no build phase, and a stack carrying `compose.command`, because that column replaces the whole `docker` subcommand so neither the project name nor whether a build happens is Cloudgate's to know. **The cascade still leaves them**, exactly as it still leaves a stack's patch-repo clone and for the same reason: `listCascadeChildren` would need each compose child's `composeType`, `command`, `sourceType` and `composePath` — the per-cascade `select` H-87 dropped — plus one `cat` per git-sourced stack ahead of the teardown's `rm -rf`. So a Project delete leaves a stack's images behind and a stack's own delete does not, which is where this rule holds and where it drifts. **And one thing this ADR's own build-host rule had a fifth uncited copy of, found by the second amendment and now asking `buildHostServerId`:** `DeploymentsService.resolveLogServer` and `initializeLog` are the read and the write of *which machine holds this log*, and both had written the `||` out. **Amended once more, with this ADR's rule applied to *roots* rather than machines.** Knowing which machine holds an artifact is only half of naming it: the platform tree has two roots — this instance's `CLOUDGATE_DIRECTORY` and the `/etc/cloudgate` literal `serverSetupCommand` creates on a Server — and all five call sites that touch an Application's source tree resolved the local one for every machine alike, so a build dispatched to a Server wrote under a root that did not exist on it. The rule this ADR states is what makes the fix atomic and is why the second amendment landed the helper (`cloudgateDirectoryOn`, `applicationsDirectoryOn`) without flipping anything: whoever creates an artifact and whoever destroys it have to answer the *same* question the same way, so converting the three destroyers while `DeploymentEngineService`'s `codeDirectory` and `ApplicationsService.uploadDrop` stayed local would have moved the leak rather than closed it — which is exactly what this ADR records `uploadDrop` doing for the machine half. All five moved together. The defect was **invisible by construction**, in the same sense as the wrong-machine one and measured the same way: with `CLOUDGATE_DIRECTORY` unset the two roots are the same string, and reverting all five sites to the local root leaves 59 tests across the three pre-existing delete suites green. The remaining instances of the same mistake are named on `deployment-engine.paths.ts` rather than fixed there, and one of them is a *third* machine answer — `applicationsDirectory()` as a Swarm mount source is resolved by the **run** Server's daemon, not the build host. **Amended, which is that worklist emptied and one correction to the root amendment's own count.** The four sibling helpers named there all now ask the machine: a patch-repo clone and a schedule's script tree (`patchReposDirectoryOn`, `schedulesDirectoryOn`), a compose stack's project tree (`composeDirectoryOn`, nine call sites across five files — `deployCompose`'s clone and `MountsService.baseFilesPath` write it, `composeTeardownCommand`'s closing `rm -rf` destroys it, and `getComposeFilePath`, `removeComposeContainersCommand`, `composeStartCommand`, `getBuildComposeCommand`, `ComposeService.stop` and `PatchService.generateApplyPatchesCommand` read it, all on `compose.serverId`, which for a stack is both the run Server and the build host since `findCompose` hard-codes `buildServerId: null`. `MountsService.remove`'s `rm -rf` of one file mount is a tenth **artifact** and not a tenth call site: it asks `baseFilesPath` for the same one expression the write asks, which is precisely why that mount cannot be written under one root and removed from another. This list said nine and then named ten, which is the defect already corrected on `deployment-engine.paths.ts` and corrected here too — a reader counting the names would have gone looking for a tenth site that does not exist), and the volume-backup staging tree with its lock (`volumeBackupsDirectoryOn`, `volumeBackupLockPathOn`). Each set moved as one, for this ADR's reason. **The local spelling of every converted tree is deleted rather than kept**, because a helper all of whose callers now pass a machine is a helper with no correct call site left, and the survivor is the trap the next site falls into. **The correction is that the root amendment's five were six.** `PatchService.generateApplyPatchesCommand`'s application arm is a second *writer* into the source tree — it `mkdir -p`s and `base64 -d >`s each patched file under `{applicationsDirectory()}/{appName}/code` on the build host — and the root amendment missed it because that pass enumerated the paths a **Delete** names. It is also the one instance of this class that is a *live failure* rather than a misplaced directory: `mkdir -p` succeeds, so `set -e` never fires, the patch lands in a second tree beside the clone, and the build reads the **unpatched** source and reports success. Measured: with the site reverted to the local root, `test/applications/source-tree-roots.e2e-spec.ts` — whose own docblock claims "a sixth call site resolving the root differently fails there" — is 8/8 green, so the site was invisible to the suite written to catch it. It takes the machine as a parameter rather than deriving one, and that is the general lesson: `findParentService` projects a Service's `serverId` and no `buildServerId`, so the only derivation available inside `PatchService` would have named the *runner* for an Application built on a dedicated builder — derivable and confidently wrong. **What stays deferred is the mount sources**, deliberately and with the same reasoning as above: `MountsService.baseFilesPath`'s application arm, `deployment-engine/mechanize.ts`'s `buildServiceSettings` — the site that hands the string to `docker.utils.ts`' `generateFileMounts`, cited here as `docker/mechanize.ts`, a path that has never existed, until now — and `databases/common/database-spec.ts` name `{applicationsDirectory()}/{appName}/files` as a bind-mount source the run Server's own daemon resolves, which is neither root this fork offers; writer and consumer agree there today and converting either alone would break that. The compose half of `baseFilesPath` converted because a stack has one machine, so the daemon that resolves its `volumes:` source is the daemon the file was written to. **Amended, which add what a *killed* build leaves and correct the railpack sentence above.** That sentence is true of a build that reaches one of its branches: `railpackStrategy` removes its per-build builder on both failure branches and at the end, and `nixpacksStrategy`'s `publishDirectory` branch removes its copy-out container the same way — so the leak is the path where **no branch runs**, a `SIGKILL`, a dropped SSH channel, a cancelled Deployment, and what is left is a *named* buildx builder with its state volume, or a `Created` container holding a writable layer, rather than the unattributable cache the bullet above refuses. Two later fixes reclaim it in the next build of the same Application, which bounds it at one leftover per Application; the delete closes it, in ADR-0016's post-refusal slot — and **this ADR's two questions are what that fix had to answer.** *Which machine*: `buildHostServerId`'s answer, asked rather than re-derived, because the sweep belongs where the build ran. A sweep issued to the run Server of a dedicated-build-Server install matches nothing and says so at exit 0, which is this ADR's invisible-by-construction failure exactly — the generated program is byte-identical whichever machine it reaches — so the tests assert *which host was asked*. *What was left when it could not be*: **nothing is reported, and that is a refusal of a fourth `UnreclaimedArtifact` kind rather than an omission.** The second amendment declined one for `${appName}:latest` because an image reference is not a `path`; a buildx builder name and a container name are neither, and the decisive half is that a **sweep** has no artifact to name even in principle — it exits 0 whether it matched nothing or everything, so a failed exec means *the sweep did not run* rather than *this was left behind*, which is the opposite of the `rm -rf` this bullet's own field exists for, whose non-zero exit already means *may still exist*. It is not a hole because the failure modes are correlated: the same delete's source-tree, patch-repo and `${appName}:latest` reclamations all already name that build host when it is the machine that cannot be reached. **A later fix adds the lane those fixes missed.** A preview is not a `CascadeChild` — the `orphanedPreviews` bullet above is why — so every sweep the deletes sent carried the parent's `appName`, while a killed preview build leaves `railpack-{preview.appName}-{nonce}` under a name the parent's length-not-prefix pattern can never match. The sweep is now a third step of `previewTeardownSteps`, on the same `buildHostId` the source-tree `rm -rf` beside it already uses, so all four preview delete paths reclaim it: the Application delete, both cascades, and `PreviewDeploymentsService.teardown`'s webhook and route. It is the one step of the three that goes as a **program** rather than as argv, because a `for`/`case` sweep over two `docker` listings has no argv to go as; the words that delete something are still argv. **A fourth artifact joins the list under the root fix, found by it rather than fixed by it: a Service's file mounts, `{root}/applications/{appName}/files` on the *run* Server.** Every removal of that tree names the **build host** — `ApplicationsService.remove`, `common/service-cascade.ts`'s application arm and `preview-teardown.ts` all `rm -rf` `{applicationsDirectoryOn(buildHostServerId)}/{appName}` — and the file mounts are written by `MountsService` to `parent.serverId`. The two coincide on every install with no dedicated build Server, which is this ADR's own mechanism one directory along, and where they do not the operator's config files outlive every delete under an `appName` no row names any more. `MountsService.remove` reclaims one mount when a caller deletes that row by hand; nothing reclaims the tree, because `mount.applicationId` is `onDelete: 'cascade'` and a cascade runs no commands. It is left as its own ticket rather than folded in here for the reason the root fix was kept separate from it: the root fix answered *which root*, and *which machine* is a second removal on a second machine plus an `unreclaimedArtifacts` `kind` of its own. **Closed by that ticket, which answers this ADR's two questions and one of `UnreclaimedArtifact`'s.** *Which machine*: `application.serverId`, the **run** Server, asked through `fileMountsDirectoryOnRunServer` so that the path the removal names and the path the report names are one expression and neither can name a tree `MountsService` does not write. *What was left when it could not be*: a fourth `UnreclaimedArtifact` `kind`, `'file-mounts'` — the first candidate to clear both of that type's criteria, where `${appName}:latest` failed the first and the build-leftover sweep failed both. It is a directory `rm -rf` on a named Server, so *a path on a machine* is not close; and what *breaks differently* is what is inside it. The three existing arms hold platform-generated content — two clones the next `ensureRepo` or build rewrites, and a router fragment the next deploy regenerates — each `rm -rf`-able without a thought, while this tree holds the bodies of the operator's own file mounts: `mount.content`, which ADR-0015 encrypts at rest precisely because a file body is where an operator puts a credential, materialized in plaintext, and re-materialized by nothing (`writeFileMount`'s only callers are `MountsService.create` and `.update`). `mount.applicationId` cascades, so by the time an operator reads the entry the encrypted rows are gone and the leftover directory is the last copy in existence; *read it before you remove it* is a different follow-up from *remove it*. Reusing `'source-tree'` would also have put two entries with the same `kind` and the same `appName` on two machines in one report, told apart only by parsing `/files` off a path — the state the discriminant was introduced to avoid. **And the slot is a decision this ADR had not had to make before.** The removal is *not* a fourth teardown step beside the source tree's: it runs in ADR-0016's post-refusal, pre-row slot, because a tree nothing re-materializes must not be removed ahead of a 409 — that would leave a live Application, one the caller has just been told still exists, with its config files gone. The source tree beside it may run early precisely because the next clone rewrites it. **Two destroyers, not the three the tree's `rm -rf`s suggested.** ADR-0018's atomicity rule binds a tree's writer to its destroyers, and the writer addresses `{parent.appName}/files` for a **Service row** — so the set is `ApplicationsService.remove` and the cascade. `preview-teardown.ts` is not in it: a preview has no row in any of the eight service tables, `findParentService` cannot resolve one, and nothing writes `{preview.appName}/files` at all. `deployPreview` spreading the parent's mounts over the preview's `appName` makes `mechanize.ts` name a bind *source* no writer created, which is a preview whose file mounts are wrong rather than a preview whose files are leaked — a separate question (ADR-0021), with `preview-teardown.ts` carrying what would have to change here if it lands. **What stayed on the list was the same artifact for a managed database.** `MountsService.baseFilesPath`'s non-compose arm answers this tree for a database as it does for an Application — the fork tests one value, `'compose'`, so its other arm covers `'application'` and all **six** database `serviceType`s (`serviceTypeEnum` binds eight values; the file-mounts fix said *seven database* types and there are seven *non-compose* ones, corrected here on the count correction's precedent) — and nothing reclaimed it on *any* install, not merely one with a dedicated build Server: `removeDatabaseService` drops the Swarm service and, before this, `src/databases/` held no `rm -rf` at all. **Closed for databases, and it is the simpler half of the file-mounts fix in every one of this ADR's questions.** *Which machine*: a database has no build-Server concept, so `serverId` is its run Server and there is no fork to get wrong — which is why the leak here needed no dedicated builder to be reachable and was strictly the worse of the two. *Which removal*: `common/teardown-steps.ts`' `reclaimFileMounts` unchanged, reused rather than written a second time, and the `'file-mounts'` `kind` reused with it — the file-mounts fix argued that kind on `UnreclaimedArtifact`'s two criteria and the argument transfers verbatim, since what is inside the tree is the same `mount.content` in plaintext whichever Service type owns the row. *Which slot*: ADR-0016's post-refusal, pre-row one again, and the argument transfers because it is an argument about the **writer** rather than about Applications: `writeFileMount`'s only callers are `MountsService.create` and `.update`, a database's deploy only reads the path back as a bind source (`database-spec.ts`' `generateFileMounts`) and `rebuild` drops the service and the data volume without touching it, so nothing re-materializes the tree and removing it ahead of the 409 would strip the init scripts off a database the caller is then told still exists. The refusal shape is the same: teardown, presence read, `ConflictException` unless `force`, then the row. *Which destroyers*: **both, in one change**, which was the whole point — `BaseDatabaseService.remove` (one method for all six engines, so no engine can be forgotten) and `common/service-cascade.ts`' `fileMountOwnersOf`. Closing it in the cascade alone would have reclaimed a database's file mounts when its Project was deleted and not when the database itself was, which is where a rule drifts rather than where it holds, this list's standing argument about a Compose stack's clone. **And the cascade's projection now states the set as the writer's own fork negated** — `serviceType !== 'compose'` — rather than as a list of the seven arms it covers. The file-mounts fix listed one arm and that is how the databases were left out; a list would also fall behind the day a ninth engine is registered, because the writer's default arm answers for a new `serviceType` from its first deploy while a list does not. The exhaustiveness a `switch` would give is traded deliberately: an unlisted engine here leaks a credential file, an unlisted engine in `teardownStepsFor` leaves a workload running, and only the second is better off failing closed. **A Compose stack still needs nothing, and that claim was re-measured rather than inherited**: `composeTeardownCommand` ends `rm -rf {composeDirectoryOn(serverId)}/{appName}` and `baseFilesPath`' compose arm writes `{composeDirectoryOn(serverId)}/{appName}/files` *inside* it, on the one machine a stack has (`findCompose` hard-codes `buildServerId: null`) — so it is the value the filter excludes, and an entry for it would re-remove a tree already gone and report an `UnreclaimedArtifact` for a directory the teardown step above it had already named. Invisible by construction in this ADR's usual way, and measured twice: **248 pre-existing tests stay green with the file-mounts fix's removal reverted, and 188 across the two unit suites and nine delete, cascade, root and mount e2e suites that cover its two sites stay green with the database fix's reverted** (priors 59, 248, 262, 256, 448, 475). Unlike the file-mounts fix, which had to update seven pre-existing tests once the fix was restored, the database fix updated none: no suite in the product asserted a whole command list for a database delete.

- **The rule binds a writer to a *consumer* as well as to a destroyer, and the root fix is where that is what it bound.** Stated for roots, the atomicity half of this ADR had so far always paired a write with an `rm -rf`: convert one and not the other and the tree is written under one root and removed from another, which moves a leak rather than closing it. A file mount's `{root}/applications/{appName}/files` is the first artifact whose other half is neither a removal nor on another machine — it is the Swarm spec's `Mounts[].Source`, resolved by the daemon on the very host the file was written to (`MountsService.baseFilesPath` writes it; `mechanize.ts` and `databases/common/database-spec.ts` mount it, both through `generateFileMounts`). Three sites spelling the same *wrong* root agree perfectly, so the pair worked and converting any one of them alone would have broken it — and `getCreateFileCommand` opens with `mkdir -p` while Docker *creates* a bind source it cannot find, as a directory, so two halves disagreeing is a container coming up with an empty directory where its config file belongs, silently, and only on an install that sets `CLOUDGATE_DIRECTORY`. They converted in one commit onto `fileMountsDirectoryOnRunServer`, which is a **second name** beside `applicationsDirectoryOn` rather than that helper called with the run Server's id: `{root}/applications/{appName}` spans two machines, the `code` half on the build host and the `files` half on the run Server, and the two bodies are indistinguishable while the two roots are the same literal until someone relocates one. What the fork cannot express, measured rather than assumed: `cloudgateDirectoryOn` reads its argument for truthiness, so two *Servers* are one root and aiming a mount source at the build host reds no test at all. That mistake is reachable only where exactly one of the two machines is the platform host, and what catches it is which daemon the spec is sent to rather than any path.

- **The rule now has a type as well as a function, and three copies of that type collapsed into it.** `buildHostServerId` stated *which machine* once; the projection handed to it did not. One batch of fixes added three build-host reclamations — the patch-repo clone, `${appName}:latest` and a killed build's leftovers — and each declared its own `{ appName, serverId, buildServerId }`, to the point where `common/service-cascade.ts` was passing `reclaimBuildLeftovers` the patch-repo reclamation's projection under a comment apologising for the borrowing. Three names over one structure check nothing in a structural type system: that cross-use compiled with no cast, and so would a fourth copy. They are now `common/teardown-steps.ts`' `BuildHostArtifactOwner`, named for the question rather than for the row — not "an Application", because `CascadeChild` carries `serviceType`, `serviceId` and a nullable `sourceType` on top of these three for eight service types of which seven have no build host, and `PreviewTeardownTarget` deliberately carries the answer already resolved beside the run Server. `BuiltImageOwner` extends it with the one column that is not about *which machine* at all: `sourceType`, required rather than nullable, because `builtImageTag` must withhold a name for the docker arm — which is why a `CascadeChild` cannot satisfy it and `builtImageOwnersOf` drops a child whose `sourceType` has gone. The two copies of the group-by-build-host loop collapsed with it into `groupByBuildHost`, which performs no I/O on purpose: the two reclamations that group have two failure contracts and two reporting contracts, and a helper that also took the per-machine turn would have to accept the stop rule and the report as parameters, which is how one silently acquires the other's.

- **Note: an AI model's weights volume, `<appName>-weights`, is always reclaimed** — by its own Delete and by its Environment's or Project's, on its run Server, whatever `deleteVolumes` says, because it is a cache of what can be downloaded again rather than the operator's data; one that could not be removed is a `'volume'` entry in `unreclaimedArtifacts` and the Delete goes ahead (`ai-models/weights-volume.ts`).
